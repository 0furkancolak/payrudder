# The payment provider contract

What a payment service provider (PSP) adapter in `pkg/payments/<provider>` must do, so that a new provider is an implementation of a checklist and not a new design. Written for plan 08 (`docs/plans/08-more-payment-providers.md`); the executable half is `pkg/payments/conformance`.

## The interfaces

`payments.Provider` = `PaymentProvider` (`Charge`, `Refund`, `Status`) + `Capabilities()`. Everything else is optional and an adapter implements what its API has: `Notifier` (confirm a webhook), `CheckoutProvider` / `InvoiceCheckoutProvider` (hosted page), `ReturnConfirmer` (the payer comes back from a page of the provider's with a form), `ThreeDSProvider` (authenticate a stored-card charge at the payer's bank), `CardStore`, `InstallmentQuoter`, `SubscriptionManager` / `SubscriptionAPI` (a provider that runs subscriptions), `CustomerAPI`, `Catalogue`, `DiscountAPI`, `DocumentLinker`, `HealthChecker`, `LiveModer` / `KeyModer` (live or test mode). `payments-worker` offers an operation only when the adapter implements its interface.

## What every adapter does

1. **Errors have exactly five meanings.** `*payments.DeclinedError{Code, Final}` the payment was refused (permanent, the customer's problem; the code is Payrudder's snake_case vocabulary, `insufficient_funds`, `expired_card`, `authentication_required`, `fraudulent`, and the provider's own word when there is no equivalent). `Final` (also `StatusResult.Final`) is set only when the provider's documentation says "do not retry" for what it answered (Stripe's `advice_code` `do_not_try_again`): dunning then stops. An adapter never infers it from a decline code. `*payments.TransientError` the provider failed and the same call may work later (5xx, 429, a documented "try again"; `RetryAfter` when the provider says how long). `payments.ErrTimeout` no answer: the outcome is **unknown**, never a decline and never retried blindly. `*payments.ActionRequiredError{Ref}` the provider will not take the payment without the customer present (3-D Secure): not a decline and nothing is charged; the saga mails the customer and waits (`StateActionRequired` from `Status` while it does). Anything else is a request the provider refused for a reason of ours (a wrong key, a field): a typed permanent error of the adapter, not a decline.
2. **The idempotency key reaches the provider on every charge and every refund**, as the provider's idempotency header where it has one and otherwise in a field it hands back (a conversation id, custom data). The notification and `Status` find the charge again by it. `Capabilities.IdempotentCharges` / `IdempotentRefunds` are true only when the provider documents that a repeated key returns the first result; when false `payments-worker` never sends a refund again under a key it has used and asks `Status` (or, for a provider that settles by notification, the ledger) before a re-charge. A charge is a repeat when any other command started a charge for the invoice under the same key (billing re-issues an unanswered charge with a new command id), at this account or under a failover key of it, or when the ledger already holds its outcome; a repeat that failed over goes on at the account it failed over to.
3. **`Status` is honest about what it cannot know.** `StateNotFound` means "the provider has no charge under this key" and allows a second charge, so an adapter whose lookup is eventually consistent (Stripe's search: "not found" is "not found yet") documents it and payments-worker does not re-charge on it before `PAYRUDDER_NOTFOUND_GRACE` and parks it after `PAYRUDDER_KEY_HORIZON`; an adapter that cannot look up by key at all (Paddle) answers `*payments.PendingError` and the notification decides. A lookup that failed is an error, never "not found". An adapter whose provider hands out its own reference with the first response (Stripe's PaymentIntent id) also implements `payments.RefStatuser`: payments-worker keeps the reference with the attempt (`payment_attempts.provider_ref`) and asks by it first, so the answer does not depend on a search index; the key stays the way to ask when there is no reference.
4. **A payment is paid when the provider says it is final.** A payment under review (iyzico `fraudStatus` 0) or one the provider settles later (Paddle) is `*payments.PendingError`; the notification settles it.
5. **Refunds do what was asked.** An amount less than the payment is a partial refund or an error; it is never a refund of the whole payment. `Capabilities.Refunds` false means `payments-worker` answers "refund outside Payrudder" without calling the adapter. Billing sends no charge id with a refund: `payments-worker` takes it from its ledger (the invoice's successful charge at the account that took it; with several it takes the one the refund's amount equals, else it refuses with `REFUND_CHARGE_UNCLEAR` and asks nobody).
6. **A webhook is believed only after it is confirmed**: the signature (Paddle, Stripe; iyzico when the account has the V3 signature enabled) and/or asking the provider what the named payment is (iyzico). A forged or replayed body that does not verify is `payments.ErrUnverified`. `ParseNotification` reads the event id and the key without trusting them; a duplicate delivery gives the same `Notification`, so the worker dedupes by `Ref.EventID`. The inbox's duplicate is final only for a delivery that finished: an event still `received` or `failed` after `PAYMENTS_WEBHOOK_RECLAIM_AFTER` (10 minutes) is taken over by the provider's retry and processed again, so a worker that died halfway does not lose the notification (every effect is idempotent: the ledger keeps a fact once, billing settles a payment once, a subscription follows the newest event).
7. **The mode is told before a request is sent**: `KeyMode` from the credentials' format, `Livemode` from the host; a host that is not the provider's documented one is "not known" and is refused when a person connects the account themselves. `CheckHealth` is one cheap authenticated read-only call and must tell bad credentials (permanent) from a provider that could not be asked (transient).
8. **Capabilities do not lie.** `HostedCheckout` iff the adapter has a hosted page, `OwnsRenewal` only with `CancelSubscription`, `OwnsDunning` only with `OwnsRenewal`, `Currencies` the intersection of the provider's and Payrudder's (empty = any).
9. **Nothing is invented.** Every call, field and event is read from the provider's current documentation (URL and date in the code comment and in `docs/<provider>-compatibility-matrix.md`); what the documentation does not settle is marked `UNVERIFIED` and the code does not act on a guess.
10. **The payer is the customer, and a form from the browser proves nothing (plan 07).** A provider that vets the payer says so with `Capabilities.NeedsBuyer`, and payments-worker then passes the customer record as a `payments.Buyer` (never made up: a field the record lacks is the account's explicit default or a named gap, `*payments.BuyerIncompleteError`; nothing is charged, and the worker declines the charge as `buyer_incomplete:<fields>` so that dunning goes on and each retry reads the customer again). A provider that sends the payer back with a form (`ReturnConfirmer`) is asked what the payment is: the form names a payment, the adapter checks that it is the attempt's (its token or payment id, its basket, its amount and currency) and returns a final state, `*PendingError` or an error, never a guess; the call that finalises a payment is made once and a lost answer is looked up. No adapter takes a card number: a card enters a provider's storage from whoever may hold it.
11. **A failure says what it can prove (plan 22 G8, [`provider-health.md`](provider-health.md)).** Payrudder fails a charge over to a second account only when the first provider *definitely* did not process it. So: a timeout, whatever the stage, is `payments.ErrTimeout` (never proof); any other transport error is a `*payments.TransientError` that carries the Go error (a dial or DNS failure is then recognised as "the connection never opened"); an HTTP 5xx or 429 is a `*TransientError` and proves nothing. An adapter returns a `*payments.NotProcessedError` **only** where the provider's documentation says a response means the request was refused before processing (none does today; UNVERIFIED). `CheckHealth` classifies the same way (`ErrUnreachable` for a provider that could not be asked, `ErrBadCredentials` for one that answered and refused), because the periodic health check and the circuit breaker read it. A provider that has the customer save a payment method on its own page for later charges implements `payments.SetupProvider` (Stripe: Checkout in setup mode); the method is learned from its notification (`KindPaymentMethod`), never from the customer's browser, and the notification carries the string `Charge` takes as its payment method. A provider whose API creates the endpoint its notifications go to implements `payments.WebhookRegistrar` (Stripe; Paddle's notification destinations are created by hand, UNVERIFIED whether its API can, and the adapter does not guess): the console's "Create the webhook endpoint" calls it and stores the signing secret the provider shows once. An adapter that can list what it settled implements `payments.SettlementReader` ([`reconciliation.md`](reconciliation.md)); one whose documentation does not settle a payout date does not.

## Conformance suite

`pkg/payments/conformance.Run(t, Harness)` checks 1, 2, 4 (as far as a fake can show them), 5, 6, 8 and 10 against an `httptest` fake that speaks the provider's wire format: a charge that succeeds, one that is declined, 5xx, 429, no answer, a refund, a partial refund, a duplicate and a forged notification, and, for a `ReturnConfirmer`, the return of a paid payment, of a refused one and of one that is not the attempt's (`Harness.Return`; `Harness.Buyer` is the customer every charge is made for). An adapter's `conformance_test.go` supplies the `Harness` (see `pkg/payments/{stripe,paddle,iyzico}/conformance_test.go` and `pkg/payments/conformance_test.go` for mock-psp). A scenario an adapter cannot show is listed in `Harness.Skip` with the reason.

A pass says the adapter handles what the provider's documentation says. It does not say the provider does: for that, each adapter should have a sandbox test (skipped without credentials). Paddle's (`PADDLE_SANDBOX_API_KEY`) checks the health call and a paged list, iyzico's (`IYZICO_SANDBOX_API_KEY`, `IYZICO_SANDBOX_SECRET_KEY`, `IYZICO_SANDBOX_CARD`) a status lookup, Stripe has none yet; none has **ever been run**, and a transcript of a sandbox run is part of "done" for a provider (plans 06, 07, 08).

## Adding a provider

Plan file `08x-<provider>.md` with the matrix first (every call, event, field, status: current / deprecated / removed / UNCLEAR, each with the documentation URL and the date), then the adapter, then `conformance_test.go`, then the console card and `docs/` page, then the sandbox transcript. Scope: charge, refund, webhook, reconcile.
