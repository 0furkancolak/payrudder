# plans-svc

## Responsibility

System of record for **tenants, API keys, customers, meters, plans, plan versions, prices,
entitlements and subscriptions**. It's the control plane: low write volume, read-heavy, strongly consistent.

## gRPC API (sketch)

```proto
syntax = "proto3";
package payrudder.plans.v1;

service PlansService {
  rpc CreateCustomer(CreateCustomerRequest) returns (Customer);
  rpc GetCustomer(GetCustomerRequest) returns (Customer);          // by external_id
  rpc ResolveCustomer(ResolveCustomerRequest) returns (Customer);  // internal, hot path, cached by callers
  rpc ListCustomers(ListCustomersRequest) returns (ListCustomersResponse);

  rpc SetPaymentMethod(SetPaymentMethodRequest) returns (Customer); // sandbox: the pm_sandbox_* scenarios, or a provider's test-mode method (pm_... / cus_...:pm_...)
  rpc CreateMeter(CreateMeterRequest) returns (Meter);              // quantity_scale (0..6) + unit_label, fixed per code
  rpc GetMeter(GetMeterRequest) returns (Meter);                   // by code, latest version
  rpc ListMeters(ListMetersRequest) returns (ListMetersResponse);

  rpc CreatePlan(CreatePlanRequest) returns (Plan);
  rpc PublishPlanVersion(PublishPlanVersionRequest) returns (PlanVersion); // immutable after publish
  rpc GetPlanVersion(GetPlanVersionRequest) returns (PlanVersion);

  rpc CreateSubscription(CreateSubscriptionRequest) returns (Subscription);
  rpc CancelSubscription(CancelSubscriptionRequest) returns (CancelSubscriptionResponse);
  rpc ListSubscriptionsFeeDue(ListSubscriptionsFeeDueRequest)
  rpc AdvanceSubscriptionFee(AdvanceSubscriptionFeeRequest)
  rpc ListSubscriptionsForPeriod(ListSubscriptionsForPeriodRequest)
      returns (stream Subscription);                                // used by billing-svc
}

service AdminService {                                               // operator token only
  rpc CreateAccount(CreateAccountRequest) returns (Account);       // creates the sandbox + live tenant pair
  rpc UpdateTenantSettings(UpdateTenantSettingsRequest) returns (Tenant); // grace period, tier (currency, timezone immutable)
  rpc CreateApiKey(CreateApiKeyRequest) returns (CreateApiKeyResponse);   // returns plaintext once
  rpc RevokeApiKey(RevokeApiKeyRequest) returns (ApiKey);
  rpc ResolveApiKey(ResolveApiKeyRequest) returns (ResolvedApiKey);       // gateway only
}

message CreateAccountRequest {
  string name = 1;
  string currency = 2;        // required, any active ISO 4217 currency (phase 40: 153 codes with their exponents); no default
  string timezone = 3;        // required, IANA name (e.g. "Europe/Istanbul"); defines period boundaries; no default
  google.protobuf.Duration grace_period = 4;  // required, 0..7 days
  string tier = 5;
}
// Both tenants of an account get the same currency/timezone/grace. CreateAccount rejects a missing field with
// INVALID_ARGUMENT: the operator (or the onboarding form in the admin UI) must choose explicitly.

message Price {
  string meter_code = 1;
  oneof model {
    PerUnit per_unit = 2;              // unit_price as decimal string in minor units, e.g. "0.002"
    TieredGraduated tiered = 3;        // tiers: up_to (nullable = ∞), unit_price, flat_fee_minor
    Package package = 4;               // package_size, package_price_minor
  }
}
message Entitlement {
  string meter_code = 1;
  string limit = 2;                    // per period, decimal string in meter units (stored as scaled units)
  repeated int32 alert_thresholds_pct = 3; // e.g. [80, 100]
}
```

## Owned data (`plans_db`)

`accounts`, `tenants`, `api_keys`, `customers`, `meters`, `plans`, `plan_versions`,
`plan_prices`, `plan_entitlements`, `subscriptions`, `outbox`. DDL is in [05-data-model.md](../05-data-model.md#plans_db).

Rules:
- `meters` and `plan_versions` are **append-only**. Changing a price means publishing a new version. A version needs a price, a base fee or a quota: a free tier is a version with a fee of nothing and quotas only.
  This is what makes historic invoices reproducible and re-rating explicit.
- A customer has **at most one active subscription** at a time (exclusion constraint on `tstzrange`).
- Tenant `currency` and `timezone` are **immutable** (DB trigger). Changing them would re-cut periods and re-price history.
  `grace_period` may change and applies from the next period (snapshotted by aggregator).
- A meter's `quantity_scale` is fixed for its code: a new meter version with a different scale is rejected.

## As built: contracts for the seller's customers (plan 21)

`contract_versions` (immutable), `contract_settings`, `contract_acceptances` (append-only, UPDATE of `ip` and `user_agent` only for the erasure job), `contract_snapshots` and `contract_withdrawals` are tenant tables with their twins in `migrations/tenant` (public 00008, tenant 00006). `ContractService` (`internal/contracts`) serves them to the gateway for the tenant API and, with the tenant of the invoice, for the hosted pages; `contracts.Check` is the gate of `CreateSubscription`; the erasure job runs daily on the system role over the pooled schema and each cell. Events: webhooks `contract.accepted`, `contract.version_published`, `contract.withdrawal_requested`, and the outbox fact `contract.accepted.v1` for the customer's mail. See [19-contracts.md](../19-contracts.md).

The follow-ups (migrations public 00011, tenant 00009): `contract_settings` gains `withdrawal_refund` (`full`/`none`, default `full`), `renewal_notice_days` (0 to 60, default 7), `renewal_cancel_texts` (language to the seller's words) and `withdrawal_function` (default on); `contract_withdrawals` gains `credit_note_id`, `refund_state`, `refund_note`, `refund_at`; the acceptance's `context_kind` may be `portal`; `contract_renewal_notices` (primary key tenant, customer, `renews_at`; the stored copy of what a customer was told). `ClaimContractWithdrawalRefund` and `RecordContractWithdrawalRefund` are the two halves the gateway uses to route an accepted withdrawal to billing's credit-note path (a row lock and the state `requesting`; a claim older than five minutes is taken over and says `reclaimed`); plans-svc never calls billing. `SetContractWithdrawalStatus` emits `contract.withdrawal_decided`. `CreateContractWithdrawal` takes `customer_id` and, for source `hosted` with a customer who has an address, writes the fact `ContractWithdrawalReceived` (`contract.withdrawal-received.v1`) in the same transaction. `contracts.Renewer` (`renewals.go`, listed in `pkg/tenantdir/jobs.go`, run every 10 minutes in every replica) lists on the system role, across tenants and in each cell's schema, the advance-billed subscriptions Payrudder runs whose `fee_due_at` falls within the seller's notice days for a customer with an address who accepted an agreement and was not noticed of that renewal, and for each one, in its tenant's transaction after the row lock, inserts the notice and writes the fact `RenewalNotice` (`subscription.renewal-notice.v1`; the price is the plan's fee for the interval and quantity less the subscription's coupon). A sandbox reset deletes the notices with the customers they name. Security review 9 (migrations public 00023, tenant 00016): the unique index `contract_withdrawals_one_open_hosted` on `(tenant_id, invoice_id)` for the hosted withdrawals that name an invoice and are not rejected; a second insert is a unique violation, which `convert.Err` answers as `AlreadyExists` / `plans.common.already_exists`. The migration first rejects (as `system`, with a reason) the later undecided duplicates a race may have left; a decided one is never touched.

## Consumed messages

None.

## Failure modes

| Failure | Behaviour |
|---|---|
| DB unavailable | All writes fail with `UNAVAILABLE`. Gateway and ingest use cached reads |
| Outbox relay lag | limits-svc sees entitlement changes late. Bounded by relay lag alert (> 30 s) |
| Concurrent `CreateSubscription` for same customer | Exclusion constraint → one wins, the other gets `ALREADY_EXISTS` |

## Scaling notes

Low QPS except `ResolveCustomer` / `GetMeter`, which callers cache (LRU 10k entries, 5 min TTL,
and invalidation is unnecessary because meters are immutable and customers are only ever added).
Two replicas for availability.

## As built: entitlement outbox (Phase 04)

`CreateSubscription` and `CancelSubscription` insert the `plans.entitlements.v1` rows in their own transaction
(`outbox.ingested_at`, the column `pkg/outbox` expects) and `NOTIFY outbox_new`. The relay (`pkg/outbox`, run with the
system pool) starts when `PAYRUDDER_KAFKA_BROKERS` is set.

## As built: subscription lifecycle (Phase 13)

`CreateSubscription` takes `trial_days` (0..365; unset takes the plan version's own default, `PlanVersion.trial_days`, set when the version is published; `0` is no trial whatever the default is) and `currency` (default: the customer's billing currency, then the tenant's). A plan version also carries `prorate_after_trial` (migration `00015`): when a trial ends inside a billing period, billing-svc charges that period's fixed fee from the trial's end instead of in full ([ADR 0028](../adr/0028-money-rules-credit-note-tax-surplus-trial-year.md) section 4); a version published without saying has it on, every version that existed before the migration has it off. The
currency must have a fixed fee on the plan version, and a plan version with metered prices needs a usage price set in it. New RPCs:
`GetSubscription`, `PauseSubscription`, `ResumeSubscription`, `ScheduleCancellation` (`cancel=false` withdraws it) and `ChangePlan`. State
moves through `pkg/subscription` (`Next`). `ChangePlan` ends the subscription at the change instant and starts a new one on the other
plan version with `changed_from_id` set and the same billing anchor; it returns the old and new plan's share of the month's fixed fee.

A subscription is invoiced on the calendar months of the tenant: `billing_anchor` is the first instant of the month it started in.
`PublishPlanVersion` accepts `fees` (a fixed fee per currency **and interval**) and `currency_prices` (usage prices in the
same currencies, covering exactly the meters of the base prices).

## As built: yearly plans and fees in advance (Phase 19)

A plan version's fixed fee is per interval and currency: the monthly fee in the tenant's currency is `base_fee_minor`, every other
combination is a `plan_version_fees` row (`interval` is part of its key, so a yearly fee in the tenant's currency is listed in `fees`).
A subscription is created `month` or `year`, needs a fee for that interval in its currency, and has a `fee_timing`:

- `advance` (the default): the fixed fee is invoiced at the start of each billing period. The billing anchor is the subscription's start
  (the trial end for a trial), so periods are anniversaries (`pkg/subscription.PeriodEnd` clamps a 29 February or a 31st). `fee_due_at` is
  the start of the next period to invoice.
- `arrears`: the behaviour of phases 13–18 (the fee rides on the calendar month's usage invoice, calendar-month anchor). Monthly only.
- A subscription whose provider renews it itself (Paddle) is always `arrears` here and has no `fee_due_at`: the provider bills its fee.

`ListSubscriptionsFeeDue(now, after, page_size)` is billing-svc's work list: advance, Payrudder-renewed, not cancelled, `fee_due_at <= now`
and still running at that period's start, each with the period `start, end)` and the fee. `AdvanceSubscriptionFee(subscription_id,
period_start)` moves `fee_due_at` to the period's end by compare-and-set, so calling it twice, or with a time that is not the next period,
changes nothing (the latter is refused). `ChangePlan` of an advance-billed subscription is refused: those are changed with `ChangeSubscription` (phase 20). The subscription report
counts a yearly fee as a twelfth in MRR. MRR is the plan's fixed fee times the subscription's quantity (seats), per currency, for active and past-due subscriptions; usage charges are not part of it. It therefore agrees with what the advance fee invoices charge.

## As built: plan and interval changes (Phase 20)

`ChangeSubscription` and `PreviewSubscriptionChange` (same request) move an advance-billed, Payrudder-renewed subscription to another plan version and/or interval.
`pkg/subscription.QuoteChange` is the one calculation behind both: the preview returns it, the change performs it. Defaults by direction: an upgrade
(or an equal-priced switch) and monthly-to-yearly are **immediate and prorated**; a cheaper plan and yearly-to-monthly **wait for the end of the paid period** and move no money.
`timing` (`IMMEDIATELY`, `PERIOD_END`) and `proration` (`PRORATE`: credit the unused old time and, within an interval, charge the new fee for the rest of the period, keeping the cycle;
`FULL`: credit the unused old time and start a new cycle now at the full price; `NONE`: no money now, new fee from the next period) override the defaults.
An immediate change of interval always starts a new cycle (the year starts now) so it needs `PRORATE` or `FULL`.

An immediate change ends the old subscription and starts its successor in one transaction (`changed_from_id`, the quote's anchor and next fee period, `fee_due_at`). The money it moved
(credit = the unused, prepaid part of the old fee; charge = the new fee) is written to `subscription_adjustments` for billing-svc. A change that waits is a pending
`subscription_changes` row (one per subscription; a new change replaces it; `CancelScheduledChange` withdraws it) that `ApplyScheduledChanges(now)` applies when its time comes: it ends
the old subscription at the period end and starts the new one with `fee_due_at` at that instant, so the new plan's first fee is invoiced by the next fee run. A change is cancelled
instead of applied if the subscription ended, is paused, past due, or ending by then. A change during a trial moves no money (the trial and the first fee date stay). A change is refused with
`ABORTED` while the fee of the current period has not been invoiced yet (there would be nothing to credit), with `FAILED_PRECONDITION` for arrears, provider-owned, paused, past-due or ending subscriptions, and
`INVALID_ARGUMENT` for combinations that make no sense. `ListSubscriptionAdjustments` and `MarkSubscriptionAdjustmentBilled` are billing-svc's work list. `Subscription.scheduled_change` shows a waiting change.

## As built: price changes (plan 15)

`SchedulePriceChange` (`POST /v1/plans/{code}/price-changes`) moves every Payrudder-run subscription on one plan version to another **at its next renewal**, when that renewal is at least `notice_days` away (default 30 until the operator changes it, at least 14, at most 365; a longer minimum for a customer's country comes from the operator's table, see below). Each one is a scheduled change of the kind above; the customer's mail is a `PriceChangeScheduled` fact in the outbox (`subscription.price-change.v1`, see [messaging](../04-messaging.md)) that the notifier turns into the mail in the customer's language.

The run is a **record** (`price_changes`, with `price_change_items` per subscription; migration `00006`, tenant twin `00005`): who asked (`created_by`, from the gateway), the notice of the latest run, `effective_at` (the first renewal a price changes on; until one is scheduled, the end of the notice), `open` or `withdrawn`, and per subscription either the `subscription_changes` row that carries it or the reason it was skipped. The state of a scheduled item is the state of that row (`pending` is *scheduled*, `applied`, `cancelled` is *withdrawn*), joined and never copied, so a withdrawal by hand or a plan change by the customer shows without any bookkeeping. One price change per plan and pair of versions is open at a time (partial unique index): **running it again continues it**, the skipped subscriptions are tried again, and the ones it scheduled before are counted in `already_scheduled` and are neither scheduled nor mailed a second time (the fix for "a rerun reports its own schedules as `has_pending_change`"). A subscription whose change of this price change was withdrawn is not scheduled again by a retry. `has_pending_change` now means only a change that someone else asked for.

`RetryPriceChange` runs an open price change again with its notice (it also picks up subscriptions that joined the version since); `WithdrawPriceChange` closes it and cancels every change of it that is still waiting, one subscription at a time (a change that was applied stays, a mail that was sent is not taken back; calling it again finishes an interrupted call). `ListPriceChanges` / `GetPriceChange` (`GET /v1/price-changes` the latest 100, `/{id}` its subscriptions a page at a time: `page_size` 1 to 500, default 500, `page_token` a keyset on the customer's id and the subscription) are the seller's view of who was told when. A run that scheduled at least one subscription sends the `price_change.scheduled` webhook event once ([webhooks](../16-webhooks.md)).

**The kill switch (plan 15).** One row of the pooled database, `price_change_pause` (migration `00020`, not tenant data: no twin, and a tenant placed in a cell reads it through the system pool, never from its own transaction). The operator pulls and releases it with `PUT /admin/v1/price-change-pause` (`{"paused", "reason"}`, `GET` reads it; recorded in `audit_events` as `price_change.paused` / `price_change.resumed`; the console shows it on the operator's tenant list). While it is on: `SchedulePriceChange` and `RetryPriceChange` answer 409 `plans.price_change.paused` (a dry run still counts; `WithdrawPriceChange` still works, because it is the way to stop a change that is scheduled), a run in progress checks it every 100 subscriptions and stops with the same answer (what it reached is scheduled and recorded; the price change stays open and a retry continues it), and the notifier's price-change consumer **holds the mail** (it asks plans-svc `GetPriceChangePause` once per 3 seconds, waits up to 15 seconds in the handler, then hands the batch back: nothing is sent, the offset does not move, the notices go out after the release). **A change that is already scheduled is still applied at its renewal** (default, not agreed: it was announced, and stopping it silently would bill the old price against a notice of the new one); a seller or the operator withdraws the price change to stop it. A pause longer than the notice leaves customers renewing at the new price with the notice delayed: withdraw instead.

**The date model and the notice rules (plan 15, leftovers; defaults, not agreed).** `SchedulePriceChange` takes an optional `effective_from` (`price_changes.effective_from`, migration `00029`, tenant twin `00021`): the date the new price starts from. `Priced.NotBefore` (`changes/query`) moves the quote of a change at the end of the period to the **first period end of the subscription on or after that date** (it counts the periods of the old interval from the billing anchor in the tenant's zone, so a monthly subscription renews at the old price until then and a yearly one may wait months); only the date moves, the fee of the new plan does not depend on it. The date must be at least `notice_days` from now and at most two years. The customer is mailed when the run schedules the change, which is at least the notice before the new price starts, **not** held back until N days before (the notifier sends at once; a held mail would need a timer that does not exist). Subscriptions already scheduled keep their dates, so a run that continues an open price change must name that price change's date (or none if it has none): another is 409 `plans.price_change.date_differs`, and the way to change a date is to withdraw and make a new price change. A retry carries the date of the price change itself. Fees are applied as before: the fee run applies due changes first, so a change months ahead is applied by the first run on or after its date.

**The notice rules** are platform data the operator edits: `price_change_notice_rules` (country, `*` for any other, least days, a note) and `price_change_notice_settings` (the default notice a run uses when its request names none; 30 as seeded), migration `00029`, no twin (read through the system pool like the kill switch). `GET`/`PUT /admin/v1/price-change-notice` read and replace the whole table in one transaction (recorded in `audit_events` as `price_change.notice_rules_set`); a row can raise the code's floor of 14 days for a country and never lower it. A run uses, for each subscription, the **longer of its notice and the floor of the customer's country** (`customers.country`; a customer with no country takes the `*` row, else 14): the subscription whose first possible date is closer than that is skipped as `renews_soon`, which is the reason that already exists. **The seeded row (`*`, 14 days) is the code's own guess. Every row is UNVERIFIED and not legal advice: nobody with the right to say what a country requires has read them, and the console says so.** The seller sees the effect (a skip) and the longer notice in the API description; there is no seller-side read of the table.

**Subscriptions run by Paddle (read 2026-11-02, UNVERIFIED, nothing built).** Paddle's update-subscription page has `items` and `proration_billing_mode` (`prorated_next_billing_period` and `full_next_billing_period` "schedule" the *billing* of the change "on the next renewal"), `next_billed_at` ("include to change the next billing date") and `scheduled_change`, which is only set to `null` there and is created by the pause, cancel and resume operations. No page says that the **items** change later, or that an item change can be scheduled for a date. A price change for a Paddle subscription would therefore either change the items at once (a different thing from what a seller of Payrudder-run subscriptions is promised) or guess at the next-billing-period modes, which the compatibility matrix lists as F5 (UNVERIFIED, needs an account). Paddle subscriptions stay skipped as `run_by_provider`. Paddle's own notification of a price change to its customers was not found in the pages read either.

## As built: seats, a quantity on the subscription

A subscription has a `quantity` (seats, licences; `subscriptions.quantity`, 1 to 100000, default 1). It is a **plain multiplier of the plan's fixed fee**: `plansqry.SubscriptionFee` (the fee run, the early-cancel credit) and the quote of a change price `FeeIn(plan version, interval, currency) × quantity` (`plansqry.TimesQuantity`). Usage prices, quotas and entitlements are not multiplied. `CreateSubscription.quantity` (0 is 1) and `ChangeSubscriptionRequest.quantity` (0 keeps it) set it; both refuse a negative quantity or one above 100000 with `INVALID_ARGUMENT`, and a quantity above 1 on a subscription that is not Payrudder-run and billed in advance with `plans.subscription.quantity_needs_advance` (the arrears fee and re-rating are not quantity-aware, and a provider prices its own quantities).

A change of quantity is a change like any other: `Price` quotes the old sum (plan fee × old quantity) and the new one (× new quantity) through the same `subscription.QuoteChange`, so the preview is what is made. When the plan version and interval stay, the default is **immediate and prorated in both directions** (more seats: the unused time of the old seats is credited and the new seats are charged for the rest of the period, so the net is the added seats for the time left; fewer seats: the net is a credit that billing turns into a credit balance), `timing = PERIOD_END` schedules it instead. A change of plan keeps the direction rule (a cheaper total waits for the period end). The credit and the charge are after the coupon in force, as for a plan change (`couponsqry.InForce`), and the successor keeps the coupon. A waiting change stores the quantity it was priced at (`subscription_changes.quantity`; NULL for one made before, which keeps the subscription's own) and `ApplyScheduled` applies it. Every other successor (`SwitchTo`: provider sync, cutover, plan change) keeps the quantity of the subscription it replaces. `ChangeQuote.quantity`, `ScheduledChange.quantity` and `Subscription.quantity` carry it in the API and the webhook events. The console shows and sets it (see [the admin UI](../13-admin-ui.md#subscriptions-and-seats)); an invoice's fee line already says "× N seats" in its description, and the lines' own quantity column stays empty for a fee, so the PDF and the e-invoice are unchanged.

## As built: following a provider's plan changes (Phase 21)

`SyncProviderSubscription` also takes `plan_version_id` and `interval`. For a provider-owned subscription whose provider now bills another plan version or interval, the subscription switches to a successor (`changed_from_id`, same anchor, `fee_timing = arrears`, owner and provider id carried over; the ended one gives the id up, since it is unique) at the provider's event time, with no money and no adjustment: the provider billed the change. Events keep naming the subscription Payrudder first linked, so the call resolves them along the chain to the one that holds the provider id; a subscription outside that chain that names a taken provider id is still refused.

## As built: coupons and tax rates (Phase 22)

`CreateCoupon`, `ListCoupons`, `DeactivateCoupon`; `ApplyCoupon`/`RemoveCoupon` (or `coupon_code` on `CreateSubscription`). A coupon is a percentage (`percent_bps`) or an amount in a currency, `once`, `repeating` (N fees) or `forever`, with an optional redemption limit and expiry; redeeming counts in one statement so two redemptions cannot take the last one. A subscription has at most one; it moves to the successor in a plan change. Only subscriptions Payrudder invoices in advance take one. `ListSubscriptionsFeeDue` returns the discount of the due fee (`pkg/subscription.CouponDiscount`), and `AdvanceSubscriptionFee` counts the period when it advances it.
A coupon is a discount on a fee Payrudder invoices in advance, so a move to a successor that cannot hold one (a provider-run one, or one billed in arrears) would lose it. A provider migration therefore refuses a subscription that has one with `plans.migration.coupon_blocks_move`: `StartProviderMigration` for a provider-run target (the customer subscribes there later, too late to refuse), and the cutover itself for any successor `subscriptionscmd.CarriesCoupon` says cannot carry it. Remove the coupon first (`RemoveCoupon`), knowing the discount ends. A Payrudder-run, in-advance target carries the coupon with its periods used.
`GetTaxRates`/`SetTaxRates` hold the tenant's rates by customer country (`tax_rates`; empty country = every other country), replaced as a whole. Billing reads them when it raises an invoice.


## As built: promotion codes and the redemption ledger (Phase 46)

A **coupon** is the definition of a discount (`percent_bps`, `amount_minor` + currency, or `bonus_percent_bps` extra credits on a credit purchase; `applies_to` says where it works: subscription fee, credit purchase, payment link or invoice). A **promotion code** is what a customer types: many codes point to one coupon, each with its own `max_redemptions`, `expire_time`, `first_purchase_only`, `one_per_customer`, a minimum amount, `allowed_plans` / `allowed_packs` / `allowed_currencies` and `restore_on_reversal`. Codes are compared in any letter case (`upper(code)` is unique per tenant). A new coupon also gets a code with its own text unless `without_default_code`;

`coupon_redemptions` is the ledger: one row per use, with the coupon, the code, the customer, the target (`subscription`, `credit_purchase`, `payment`; the id is the subscription or the invoice), the discount or bonus credits, the currency, `reversed_at`. `coupons.redeemed` and `promotion_codes.redeemed` are the count of it. Claiming is two conditional `UPDATE`s (`ClaimPromotionCode`, `ClaimCoupon`: `... WHERE redeemed < max_redemptions`) inside the checkout's transaction, so 50 checkouts racing for the last 7 places give exactly 7 (tested); the code's row lock also serialises the one-per-customer check. A unique index on `(target_kind, target_id)` of live rows makes asking twice for one purchase one redemption. A void or full refund calls `ReversePromotion`: the row is marked reversed, and the place goes back to the count only for a code with `restore_on_reversal` (default no, as before). `RemoveCoupon` reverses a subscription's redemption the same way, so the subscription can take another coupon.

`RedeemPromotion` is what a checkout calls (billing-svc, or a tenant's own page through `POST /v1/promotions/quote` with `preview`): it checks the rules (`coupons/model`, pure and table-tested), quotes the discount or bonus and, unless `preview`, claims it. A discount never takes the total below zero; an amount coupon applies only in its currency (`coupon.currency_mismatch`); a percentage rounds half to even. One coupon per subscription or purchase. Refusals carry `coupon.*` keys: `not_found`, `inactive`, `expired`, `exhausted`, `not_applicable`, `currency_mismatch`, `already_used`, `first_purchase_only`, `below_minimum`, `customer_required`, `already_applied`, `code_taken`.

**Affiliate hook (phase 47).** `GrantCustomerCoupon` (`customer_coupons`) puts a coupon in wait for a customer, once per `(customer, source, source_ref)`; the customer's next eligible checkout that types no code uses it. A referral programme calls it with `source = "affiliate"`; nothing in this schema needs to change for that. `coupons.id` is the stable identity a programme stores.

**Onboarding record** (`GetMyOnboarding`, `UpdateMyOnboarding`; module `internal/identity/onboarding`, table `user_onboarding`). ## As built: the trial-ending reminder

A trialing subscription is reminded **once per trial end**, `PAYRUDDER_TRIAL_REMINDER_DAYS` days before the trial ends (default 3, 1 to 30; one value for the whole service: the trial itself is the plan version's `trial_days` or the request's own, and a per-subscription reminder date would need a column on every subscription): the `subscription.trial_will_end` webhook event (`data.subscription` as the API returns it, with `trial_end_time`) and an e-mail to the customer. A trial shorter than the window is reminded at the first pass after it starts.

- Module `internal/trialnotices` (`model` the pure rules: the window, which trials are due, the event id and the fact; `command` the job). `command.Job` runs in every plans-svc replica every `PAYRUDDER_TRIAL_REMINDER_EVERY` (default 10 minutes). It lists, on the **system pool**, across tenants, the trialing subscriptions that Payrudder runs (`owner` is not `provider`: a provider reminds its own customers), are open-ended and not set to cancel at the period end, whose `trial_ends_at` is after now and within the window and for which no notice exists (`SystemListTrialsEndingSoon`, oldest end first, 200 at a time; a full batch runs again at once).
- Each candidate is then handled in its **own tenant's transaction on the app pool** (`pgxx.InTenantTx`): the subscription row is locked and re-checked (`Trial.Remindable`), then `subscription_trial_notices` gets its row, the event is queued through `webhooks/command.EmitSubscription` (only if an endpoint wants the type) and the `TrialWillEnd` fact is written to the `outbox` (topic `subscription.trial-will-end.v1`, relayed like `plans.entitlements.v1`, so the mail waits in the outbox while `PAYRUDDER_KAFKA_BROKERS` is unset). The notice, the event and the fact are in the same transaction: all three or none.
- **Idempotency.** `subscription_trial_notices (tenant_id, customer_id, trial_ends_at, subscription_id, notified_at)`, primary key `(tenant_id, customer_id, trial_ends_at)`, forced RLS, `plans_app` SELECT and INSERT, `plans_system` SELECT (the list) and DELETE (the sandbox reset). The insert is `ON CONFLICT DO NOTHING` and comes after the row lock, so a second pass, or a second replica, finds the notice and does nothing; a replica that loses the race waits on the lock and then also finds it. The key is the customer and the **end** of the trial, not the subscription: a plan change during a trial makes a new subscription with the same trial end and is not reminded again; a trial that is extended or started afresh has another end and is reminded again.
- A trial that is already over when the job comes (it was down) is not reminded; a paused, cancelled, scheduled-to-end or provider-run trial is not either.
- `subscription_trial_notices` is customer-side history (it has a foreign key to `customers`), so a **sandbox reset deletes it** with the subscriptions (`internal/sandbox`, `Tables`, `ResetTrialNotices`), unlike configuration such as `tenant_mail_integrations`, which is kept.
- The `TrialWillEnd` fact (`proto/payrudder/events/v1/trial_will_end.proto`): `event_id` is `uuidv5(tenant|customer|trial_end)`, so the notifier's dedup absorbs a repeated publish. notifier turns it into the mail (`trial_will_end.v1`, [workers](workers.md#notifier)).

## As built: renaming and deleting an app

`RenameMyApp` and `DeleteMyApp` on `IdentityService` (gateway: `PATCH` and `DELETE /app/v1/apps/{id}`, session routes; code in `identity/command/apps.go`; `apps.archived_at` and the table `app_audit`). Like every `My*` call they take the person from the session and find the app through the person's membership, so a stranger's app is "not found".

- **Rename**: owners and admins; a viewer gets `403 identity.account.forbidden`. The name is trimmed, 1 to 200 characters. It is the name of the app **and of its tenants** (the sandbox one with the suffix ` (sandbox)`), which is what the seller line of a *new* invoice says; invoices already issued keep the name they were issued under. The slug (the address) does not change. Audited (`app_audit`, action `renamed`, from and to).
- **Delete**: **owners only** (an admin manages an app but does not end it; `403` otherwise). **Rule: deleting archives, always, and never erases.** An app's tenants hold customers, subscriptions, invoices, payments and usage that accounting and the retention rules keep, and splitting "only sandbox data" from "has live money data" would add a second path whose mistake destroys a billing record; one rule cannot. The archive (`apps.archived_at`, `archived_by`) happens in one transaction under a row lock on the app: the slug is rewritten to `<slug>-archived-<12 hex of the id>` (a new app may take the old name and slug), every active key of both tenants is revoked, and an `app_audit` row (action `archived`, the number of keys revoked) is written; the gateway's key cache is evicted after the commit.
- **What "archived" means**: gone for the account. The account's lists, `GetMyApp`, `ResolveMyTenant` (so no session can act on the tenant), keys, go-live, promote, sandbox reset and rename all answer "not found" (`GetAppForUser` and `GetTenantForUser` leave archived apps out); the app no longer counts against the plan's app quota or the 20-app limit. **Ingest is refused**: its keys are revoked and evicted, `Issue` refuses a key for a tenant of an archived app (`plans.api_key.app_archived`, also for the operator), and the trigger `api_keys_app_not_archived` refuses an active key whatever the code does. The operator's `ListApps` still lists it, with `archive_time`.
- **What does not stop**: billing-svc and payments-worker keep working on what exists (`ListTenants` still walks the tenants): subscriptions renew, a customer who owes is invoiced and charged, an issued invoice can be paid, webhooks of the live tenant are delivered. Deleting does not cancel subscriptions; the console says so and the owner cancels them first when billing should stop. There is no un-delete in the console (the operator can clear `archived_at` in the database).
- Tests: `domain` unit test of the name; `-tags integration` `AppRenameAndDelete` (roles, tenant names, lists, keys revoked and evicted, no new key by member or operator, the trigger, customers and subscriptions kept, operator view, audit rows, slug reuse, quota); the gateway's `TestAppRenameAndDeleteRoutes`; `e2e-mock/app-manage.spec.ts`. The routes are session routes, so they need no entry in `pkg/apikey` `RequiredPermission` (that table classifies the routes an API key can reach; `TestEveryTenantRouteNeedsAKnownPermission` is unaffected).

## As built: the help desk (plan 12)

`SupportService` (`internal/support`; tables `support_tickets`, `support_messages` and `support_events`, all global like `users`, on the system pool). People open tickets for their account and answer on them (every member of the account sees the account's tickets); the operator works the whole queue. A ticket opened out of hours starts its clock when the next business day opens; a change of priority moves the deadline (until the first answer) the same way. No holiday calendar yet. `domain.SupportFirstResponseDue`.
- **Mail** (`usermail`, in the six languages, in the person's locale, after the transaction commits): a new ticket to every address of `PAYRUDDER_OPERATOR_EMAILS` (the gateway's list; an address that has a user reads that user's language, else English); the operator's public answer, and a status the operator sets, to the person who opened the ticket. Not mailed: an internal note, a change of priority or assignee, what the person does themselves. A customer's reply to the operator is **not** mailed yet. The links open the ticket in the console (`/app/support?sheet=ticket:<id>`, `/support?sheet=ticket:<id>`). Replies by e-mail are not read.
- **History.** `support_events` (append-only: `plans_system` has no UPDATE or DELETE) gets a row for every change of status, priority or assignee, with who made it (customer, operator, or the system job). `GetSupportTicket` returns it as `events`; `GetMySupportTicket` returns only the kinds on the allow-list `personEventKinds` (`status`, `priority`): the tags and the operator's assignee are the operator's own, and so is every kind added later until it is added to the list (a unit test names the list, an integration test inserts a line of every kind the table's check constraint accepts and reads the history as the person). The console draws it in the thread.
- **Unread.** `opener_seen_at` is NULL while the person who opened the ticket has an operator answer or status change they have not read; reading the ticket as that person (not another member) or writing on it clears it. `SupportTicket.unread` is true only for the opener.
- **Limit.** At most 20 tickets waiting (open or pending) per account; the 21st is `429 support.tickets.too_many`. The count and the insert are serialised per account with an advisory lock.
- **Auto-close.** `PAYRUDDER_SUPPORT_AUTOCLOSE_AFTER` (default 168h, 0 switches it off) and `_EVERY` (1h): a ticket that has been pending (waiting for the person) since before then, counted from the last time it became pending (else its last message), is closed, the history says "system", and the opener is mailed. Safe on several instances (`FOR UPDATE SKIP LOCKED`).
- **The deadline by plan, and the days off (round 4; defaults, not agreed).** `domain.SupportFirstResponse(tier, priority)` is a table: **free** (the plan every new app starts on, and the one table the desk had before plans counted) urgent 1 h, high 4 h, normal 9 h (a business day), low 27 h; **standard** 1 h / 2 h / 6 h / 18 h; **enterprise** 30 min / 1 h / 4 h / 9 h; an unknown plan counts as free. The plan is the one of the ticket's app's **live tenant** (`tenants.tier`; the best live plan among the account's apps when the ticket names none; free when the account has no app), kept on the ticket (`sla_tier`, with `sla_app_id`, the app whose zone and days off the clock uses) so that a change of priority counts the new deadline the same way. The clock also skips the app's **days off** (`support_holidays`, one row per app and calendar day in the app's zone, kept by the operator with `GET`/`PUT /admin/v1/support/apps/{app_id}/holidays`, at most 200 days within three years, in `audit_events` as `support.holidays_set`). A ticket already open keeps its deadline when days are added; changing its priority counts it again with the days as they are then. The person is not told the plan (`sla_tier` is empty in the "My" calls). Not built: a table the operator edits (it is in code), a calendar for the operator's own staff, a plan per ticket.
- **Merge.** `MergeSupportTickets` (`POST /admin/v1/support/tickets/{id}/merge`, operator): two different tickets of **one person in one account**, neither merged already, the target not closed (`409 support.ticket.cannot_merge`). Under both locks (in the order of their ids) the messages and the files of the first move to the second (`UPDATE (ticket_id)` on `support_messages` and `support_attachments` is the one change `plans_system` may make to them; migration `00030`), the first is closed with `merged_into` set and takes no reply or change (`409 support.ticket.merged`), a person's message that waited for the operator reopens a target that was pending or solved, the earlier first-answer deadline holds while neither was answered, a `merge` line goes into both histories (the person reads it: it is on the allow-list) and into `audit_events` (`support.merged`), and both tickets are unread for the person. The combined files may exceed the ten a ticket takes; the limit only stops more.
- **Rating.** `RateMySupportTicket` (`POST /app/v1/support/tickets/{id}/rating`): any member of the account, 1 to 5 and a comment of at most 1000 characters, only on a solved or closed ticket (`409 support.ticket.not_solved`); a second call replaces the first. `support_tickets.rating`, `rating_comment`, `rated_at`. The operator's report counts the ratings of the last 30 days (how many, the average, how many gave each) and the operator reads the rating on the ticket; the person sees their own.
- **Search over the words of the messages.** `support_messages.tsv` (`to_tsvector('simple', body)`, generated, GIN index; `simple` because the messages are in any language, so no stemming and no prefixes). The operator's `search` matches the subject, the number or any message **including the internal notes**; the person's list has the same `search` over the **public messages only**, and over the tickets of the person's own accounts only. The text is read with `websearch_to_tsquery` (quotes, `or` and `-` work, nothing a person types is an error) and cut at 200 characters.
- **Links.** `support_ticket_links` (a customer by external id, an invoice or a subscription by its UUID, in an app environment of the ticket's account; at most five): given when the ticket is opened (`links`) and replaced by the operator (`PATCH` with a `links` key). Only the **pointer** is stored: whether the object exists is not checked (invoices live in billing-svc), the app must be one of the account's, not archived, and the console opens the object under the viewer's own access, so a link cannot show data the viewer cannot already see. The lists carry no links; one ticket does.
- **The operators' desk (plan 12, third step; migration `00021`).** *Mail on the person's answer:* when the person answers and the ticket was last answered by an operator (waiting for them, or solved), every operator address gets `ticket_customer_reply`, in the language of its user; a second message in a row sends nothing (the ticket is in the queue already) until an operator answers again. *Unread:* `CountMySupportUnread` (`GET /app/v1/support/unread`) is the number of the person's tickets with news they have not read, the badge on the help link in the sidebar. *Tags:* `support_tickets.tags` (at most 5, `^[a-z0-9][a-z0-9-]{0,29}$`, lower-cased and de-duplicated by `domain.NormalizeSupportTags`), set by `PATCH /admin/v1/support/tickets/{id}` with a `tags` key (an empty list clears them), filtered with `?tag=`, written to the history as kind `tags`, and **never returned by the person's calls** (`ticket()` and `list()` clear them, and the assignee with them, when a viewer is named; the history kind `tags` is not on the person's allow-list; tests hold it). *Assignee:* one of `PAYRUDDER_OPERATOR_EMAILS` (`GET /admin/v1/support/operators`, with the user's name where there is one), or empty, or what the ticket already has (a free-text name from before stays until somebody changes it): anything else is `plans.request.invalid` on `assignee`. *Canned replies:* `support_canned_replies` (title up to 100 characters, text up to 10,000, who saved it last), shared by all operators, `GET/POST /admin/v1/support/canned-replies`, `PUT/DELETE .../{id}` (`support.canned_reply.not_found`). *Report:* `GET /admin/v1/support/report`: waiting (open), late (open, no first answer, past the deadline), every ticket by status, the waiting ones by priority, and for the tickets opened in the last 30 days how many were answered, how many in time, and the median and average first-answer time in wall-clock seconds. *The gauge:* `support_waiting_tickets` and `support_sla_breached_tickets{priority}` (see [observability](../08-observability.md)); the alert is `SupportFirstAnswerOverdue`. **Attachments are not built**: see [the plan](../plans/12-support-system.md).
- **Attachments** (`support_attachments`, migration `00022`; `internal/support/attachments.go`). A message may carry png, jpeg, pdf or plain-text files, at most 5 MiB each, 10 per ticket, 50 MiB per organisation (`domain.SupportMax...`, defaults not agreed). The bytes are in assets-svc under the **first tenant of the ticket's account** (the live tenant of the oldest app that is not archived; `409 support.attachment.no_app` while the account has no app) with the purpose `support_attachment`, which assets-svc leaves out of `ListAssets` unless asked for by name and the tenant API cannot name. The table is the record (never edited or deleted: `plans_system` has `SELECT, INSERT`). The gateway moves the bytes in three steps: `AuthorizeSupportAttachment` (may this caller add to this message, is there room, which tenant), the upload to assets-svc for that tenant (assets-svc checks type, size and content type), `AddSupportAttachment` (the limits again under the ticket's lock; a file whose record fails is deleted again). A person attaches only to a message they wrote and not to a closed ticket; the operator only to the operator's own messages, notes included; the person's reads never include the files of an internal note, and a note's file asked for by the person is `404`, the same as one that is not there. A download is `GetSupportAttachment` and then a presigned link from assets-svc for the tenant it names. **Known limits:** the files count against the storage quota of that tenant (a full tenant refuses them with `support.attachment.storage_full`); they are not scanned for malware (assets-svc sniffs the content type only); a file stays when its ticket does (no retention yet).
- Not built (plan 12): email-to-ticket, malware scanning and retention of attachments, an SLA by plan.

## As built: the audit log and two-factor sign-in (plan 22, G4 and G9)

See [audit-log-and-two-factor.md](../audit-log-and-two-factor.md). `audit_events` (migration `00012`, twin in `tenant/00010`) is written by `pkg/audit` in the transaction of API key, member, plan, webhook endpoint, customer block, tenant status and settings, and sign-in security changes; `internal/auditlog` is its `AuditService` source (the pooled database through the system pool, plus the tenant's schema when the tenant is in a cell). Two-factor (migration `00013`): `user_totp`, `user_recovery_codes`, `login_challenges` and `accounts.require_two_factor`; `identity/totp` is RFC 6238 and the recovery codes, `identity/command/twofactor.go` the commands. `openOrChallenge` is the end of the first step of `SignIn`, `VerifyLoginCode` and `SignInWithIdentity`.

## Retention, schedules and appeals of a live tenant (plan 14)

Two global tables of the pooled database (migration 00033; no tenant twin: they are about a live tenant, like `tenant_status_events`): `tenant_lifecycle` (one row per tenant that has one: `retention_until` and `retention_due_at` of a banned tenant, `scheduled_status` with its time, category, reason and who) and `tenant_appeals` (an owner's statement against a hold and the operator's decision; one open per tenant). `tenants/command` holds the logic: `trackRetention` runs in the transaction of every status change (a ban starts the period of `PAYRUDDER_BAN_RETENTION_DAYS`, default 90; leaving the ban ends it), and `RunLifecycle` (one loop in the service's workers, every minute) applies the schedules that are due and marks the retention deadlines that passed. A schedule is applied through `setStatus` with `onlyFrom = active` as the operator `system`; marking a deadline due writes the audit entry `tenant.retention_due` and deletes nothing. An owner's appeal and the hold they may see are `identity/command` (`SubmitAppeal`, `AppHold`); the operator's list and decision are `tenants/command` (`ListAppeals`, `DecideAppeal`; accepting reinstates with the mail of the appeal, not of the reinstatement). Audit actions: `tenant.status_scheduled`, `tenant.status_schedule_cancelled`, `tenant.status_schedule_applied`, `tenant.status_schedule_skipped`, `tenant.retention_due`, `tenant_appeal.submitted`, `tenant_appeal.decided`.
