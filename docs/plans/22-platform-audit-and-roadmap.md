# 22 — Platform audit and roadmap: financial correctness first

## The request
Owner, 2026-11-01: analyse the existing code (not propose features that exist), find gaps and technical risks, and produce a plan in this order: **financial correctness → payment reliability → production readiness → reconciliation → developer experience → advanced intelligence**. Vision: revenue infrastructure without vendor lock-in. Analysis and plan only; no code in this step.

## How this was made, and its limits
Two read-only passes over `main` (2026-11-01) with file evidence. **Nothing was run**: "exists" means the code and tests are present, not that they pass today. Anything not grepped to a conclusion is marked **UNVERIFIED**. The first thing the work below does is turn UNVERIFIED items into confirmed or refuted ones.

## A. Executive summary
**Maturity.** A real multi-service platform with unusual strengths for its age: payment saga with an explicit unknown-outcome state and a status query before any re-charge; idempotency keys at every provider that supports them; append-only saga/credit/payment tables by grants; forced RLS with a startup-independent verifier; gap-free invoice numbers under concurrency; late-usage and re-rating paths; chaos suite with invariants. It is not yet production-proven: nothing is verified against real provider sandboxes. (2026-11-02: the second half of the 2026-11-01 sentence, "DR has no point-in-time recovery", is no longer true for the compose Postgres, see G5.)

**Top 5 technical risks** *(2026-11-02: all five are built, against fakes and containers, none against a real provider; each line says where)*
1. **Redelivered refunds are not guarded for iyzico and Paddle** (no ask-first as there is for charges; neither provider is idempotent in our adapter). High, partly UNVERIFIED (provider behaviour on a repeat). **Built: G1 (#279, #329).** Whether iyzico and Paddle really refund twice on a repeat is still UNVERIFIED.
2. **iyzico lost-response window**: a charge committed late can read `NotFound` and be re-charged under the same `conversationId`, which iyzico may not dedupe (UNVERIFIED). High. **Built: G2 (#279).**
3. **Financial rows are immutable by grants only** (*fixed 2026-11-01, see Status*): `billing_system` can UPDATE `invoices` (totals, snapshot) and DELETE most billing tables (granted for the sandbox reset); `payment_ledger` is deletable by `payments_system`. No triggers. A bug or a wrong environment can rewrite history. High.
4. **No point-in-time recovery**: daily `pg_dump`, "you lose up to a day"; no stated RPO/RTO; unconsumed events are lost on a broker loss. High. **Built for the compose Postgres: G5 (#281, drilled in CI); not for Kubernetes, and the raw usage events in Redpanda still have no copy (plan 16).**
5. **No financial anomaly alerting and no broad audit log**: alerts cover usage correctness and infrastructure, not charge failure rate, refund spikes, invoice-vs-payment mismatch or provider webhook failures; the audit trail is narrow (`app_audit`, `go_live_audit`, saga events). High. **Built: the alerts G6 (#281, #309) and the audit log G4 (#299, #343); no real alert receiver yet.**

**Top 5 product gaps** *(2026-11-02: all five are built; the notes say how far)*
1. Customer-facing **event correction** (only an operator replay exists). **Built: G12 (#315).**
2. **No 2FA** for console sign-in (nothing found for TOTP/WebAuthn; account lockout exists via `users.failed_logins`/`locked_until`, and email-code and Google sign-in exist, so 2FA must wrap all methods). **Built: G9 (#299): TOTP and recovery codes on all three sign-in methods; WebAuthn is not.**
3. **Reconciliation is read-only**: no mismatch workflow, no schedule (UNVERIFIED), no **settlement/payout/fee ingestion** (the `payout` ledger kind exists, nothing writes it). **Built: G7 (#298, console #313): persisted discrepancies with a review queue and a schedule, settlement ingestion for Stripe only (Paddle and iyzico reports go in by CSV).**
4. **Upcoming-invoice / cost preview** for usage (listed missing in `docs/hosted-pages.md`). **Built: G14 (#315): the API, the SDKs and the console; not on the customer's portal.**
5. **Runtime provider health, circuit breaker and failover** (the registry and per-country routing exist; health is a connect-time credential check). **Built: G8 (#298, console #313): health per account, a circuit breaker, failover only on a definite failure.**

**Before production:** items 1–5 of the risks *(built)*; real sandbox runs for Stripe, Paddle, iyzico (plans 06–08) *(open: no account of any provider has been used)*; a restore drill that checks data, not only table existence *(built: `make backup-drill`)*; real alert receivers *(open: Mailpit and a webhook sink only)*.

## C. Gap analysis
(Format per gap: current state · problem · proposed fix with least change · priority · dependencies · size.)

**G1 Refund redelivery guard (iyzico, Paddle).** Current: charge asks the provider first when it is not idempotent; refund does not. Problem: billing resends a refund up to three times after five minutes (`creditnotes/command/refund.go`) with a new command id and the same key; `payment_attempts` is keyed by command id, so a resend never looks redelivered, and `handler.go` discards the `redelivered` flag for refunds. iyzico allows repeated refunds and the Paddle adapter sends no key, so a resend can refund twice. Fix: for providers without idempotent refunds (new capability `IdempotentRefunds`), check the payment ledger and `payment_attempts` by idempotency key (not command id) before `Refund`; if the outcome is unknown never repeat it, park it for the operator; add a provider-side lookup only where the compatibility matrix documents one. (`payment_attempts` is set to DONE by `workerx` after a reply is stored; the remaining windows are a crash between the provider call and the store, transient errors, and the resend.) **Critical.** The compatibility matrices from #270 and #275 already hold the provider facts. **M.**

**Status G1 (2026-11-01): done in PR #279 (`fix/refund-guard`); fake providers only, nothing run against a real iyzico or Paddle account.** Built: capability `IdempotentRefunds` (true for Stripe, which sends the key as `Idempotency-Key` and keeps it at least 24 h; true for mock-psp and for a provider that declares nothing; false for iyzico, Paddle and bank transfer). For the others `payments-worker` (`handler.guardRefund`) looks, before `Refund`, at the payment ledger and at `payment_attempts` **by key**, not by command id: a refund the ledger or an earlier attempt shows as made is answered with its result (and a missing ledger row is written then); an earlier attempt that was only started, timed out or cannot be read is an unknown outcome, not repeated, answered `REFUND_OUTCOME_UNKNOWN`; one the provider refused may be asked again. No migration and no new state: the credit note goes to `failed` with that code in `refund_error` (the saga's void refund exhausts its steps into `REFUND_FAILED`), and `retryRefund` keeps the key after `TIMEOUT`, `REFUND_OUTCOME_UNKNOWN` and no answer (it took a new key after a timeout before, which could refund twice at any provider). The false comment in `creditnotes/command/refund.go` is fixed. A failed ledger write after a successful refund is retried twice, counted (`ledger_write_failures`), logged, and never fails the command; the stored reply answers any resend. Not built, still open: (1) a lookup at the provider: neither matrix documents one (Paddle's list adjustments by transaction exists in its API but is not in the matrix, so UNVERIFIED); (2) an operator action to resolve an unknown refund (mark it refunded, or allow a new key after checking at the provider): today the operator refunds outside Payrudder and the note stays failed; (3) a transient error (5xx, reset) on a refund to iyzico or Paddle now parks instead of retrying, since the adapters cannot say "definitely not processed" (a 429 is); (4) alerts on `ledger_write_failures` and on notes failed with `REFUND_OUTCOME_UNKNOWN` (done in G6, below); (5) whether iyzico and Paddle really refund twice on a repeat is still UNVERIFIED; the guard assumes the worst.

**G2 iyzico `NotFound` re-charge window.** Current: a not-found status after a timeout leads to a re-charge. Note: iyzico `Status` returns NotFound only if `Settings.NotFoundCodes` lists the error code, and the default is empty, so by default an unknown outcome retries and then parks; the risk exists once an owner or sandbox sets `NotFoundCodes`. Fix: add an age check in `sagas/model/table.go` and `sweep.go`: a NotFound younger than a grace period retries, one older than the provider key horizon parks; keep `NotFoundCodes` empty by default. This also applies to any provider with a retention-limited key (Stripe 24 h, UNVERIFIED): refuse to re-charge older than the key horizon. **Critical.** Needs: iyzico docs/sandbox. **M.**

**Status G2 (2026-11-01): done in PR #279 (`fix/refund-guard`); tested with stub workers and a test clock, not against a provider.** Built: a `StatusNotFound` in `PAYMENT_UNKNOWN` is read by the age of the charge under its key (the latest entry into `PAYMENT_REQUESTED` that was not a re-charge, from `saga_events`): younger than the grace period the saga stays in `PAYMENT_UNKNOWN` with no command outstanding and its step deadline set to the end of the grace period, so the sweeper's first re-issue asks the status again (`EffRecheck`); between grace and horizon the charge is sent again under the same key as before; older than the horizon the saga parks (`last_error` says why, no deadline, the operator's Retry asks again, Settle and Void still work). Settings, all **default (not agreed)**: `PAYRUDDER_NOTFOUND_GRACE` 10 minutes, `PAYRUDDER_NOTFOUND_GRACE_SANDBOX` 10 seconds (sandbox runs on compressed time like dunning), `PAYRUDDER_KEY_HORIZON` 24 hours (Stripe's retention); `NewEngine` refuses a grace that is not shorter than the horizon. iyzico `NotFoundCodes` stays empty by default. Open: iyzico's key retention and its not-found error code are UNKNOWN (matrix), so one horizon serves every provider; the `PAYMENT_PENDING` → not found → charge row is unchanged (no lost-response window there); the e2e `cus_tnot` scenario now waits for the sandbox grace (10 s) and was not run.

## D. Roadmap
**Phase 0 — critical production risks.** Goal: nothing can charge or refund twice, and history cannot be rewritten. Work: G1, G2, G3, G15 (the tests that prove them). Depends: provider docs and sandbox accounts for G1/G2 (plans 06–08). Output: tests that fail without the fix; migration with triggers. Risks: triggers break the sandbox reset (design the reset path first). Success: chaos A1–A9 plus new refund/charge races green; an attempted UPDATE of a finalised invoice is rejected by the database.

**Phase 1 — production foundation.** Work: G4, G5, G6, G9, G10, G11, G13; the real alert receiver. Output: audit log, PITR with a stated RPO/RTO and a data-checking restore drill, anomaly alerts, 2FA. Success: a drill restores to a chosen minute and passes invariant checks; every money/security action appears in the audit log.

**Phase 2 — payment orchestration.** Work: G8, plan 10 (integrations page), plans 06–08. Success: timeout → query → reconciliation path proven by chaos with a fault-injecting provider; failover only on definite failures.

**Phase 3 — reconciliation.** Work: G7. Success: every charge in a period is matched to a provider transaction and a settlement, or is an open item with an owner; "paid" and "settled" are different states in the console and API.

**Phase 4 — developer experience.** Work: G16, G14, G12, plans 18–20. Success: a developer integrates in under 30 minutes from the docs, TypeScript first, then Go, then Python.

**Phase 5 — advanced revenue infrastructure.** Usage intelligence, cost attribution, profitability and pricing intelligence — only after phases 0–3, and not started by this plan. Not scoped.

## Security review (2026-11-02): gateway findings

A review of the gateway found nine problems, all verified against the code. Each fix has a test that failed first, except where an item says that the behaviour already held and the test now keeps it. Four pull requests: [#377](https://github.com/0furkancolak/payrudder/pull/377) (1, 2), [#379](https://github.com/0furkancolak/payrudder/pull/379) (3, 4, 5), [#382](https://github.com/0furkancolak/payrudder/pull/382) (6, 7, 8) and [#387](https://github.com/0furkancolak/payrudder/pull/387) (9). Defaults below are **default (not agreed)**. Status is "fixed in the pull request"; none of it was run against a real deployment.

1. **HIGH, a leaked checkout key refunds cards: fixed in #377.** `PUT /v1/contract-withdrawals/{id}/status` and `POST .../{id}/refund` needed only `customers:write` but make a credit note with `refund_to_card`. `pkg/apikey.RequiredPermission` now asks `invoices:write` (the permission `POST /v1/credit-notes` needs) of the refund route, and the status handler asks it for `accepted` while the setting `withdrawal_refund` is `full` or cannot be read (fail closed), before anything is decided. Recording a withdrawal, rejecting one, and accepting with the setting `none` stay `customers:write`; a console session carries no key permissions and is unchanged. This overturns the default written in [21](21-contracts.md). Tests: `TestRequiredPermission`, `TestAKeyThatOnlyWritesCustomersCannotRefundAWithdrawal`.

2. **MEDIUM, no two-factor rule for operators: fixed in #377.** `operatorAllowed` now applies the setup-required rule of every session route (an operator who owns an account that requires two-factor sign-in and has not set it up is refused on `/admin/v1/*`), and `PAYRUDDER_OPERATOR_REQUIRE_2FA` makes every operator session need it (the gateway marks the user `two_factor_setup_required`, so `/auth/me` sends the console to the security page). **Default (not agreed): on unless `PAYRUDDER_ENV` is `local`, `ci` or `kind`**; a compose or Helm install on a real host runs as `local`/`kind` and must set it. The machine token is no person and is not asked. The refusal reuses the owners' error key, whose console text says "an organisation you own". Tests: `TestAnOperatorWhoMustSetUpTwoFactorReachesNoOperatorRoute`, `TestTheDeploymentCanRequireTwoFactorOfEveryOperator`, `TestOperatorTwoFactorSetting`.

3. **MEDIUM, unauthenticated load on plans-svc: fixed in #379.** An unknown or revoked key prefix and an unknown session token are remembered in the replica's memory (`internal/negcache`, a hash, **30 s, 4096 entries**); every refused credential counts against the caller's address, and at **30 a minute** the address is answered `429 identity.auth.rate_limited` before any key or session lookup (the machine operator token is exempt; the same unknown credential again is not a new guess and does not count). `gateway_auth_failures_total` gains the reasons `session`, `operator_token` and `throttled`. Valid credentials from an address that is being refused are refused too until the minute passes. Tests: `internal/auth`, `internal/negcache`, `authguard_test.go`.

4. **MEDIUM, per-address limits keyed on the full IPv6 string: fixed in #379.** `limitKey` counts an IPv6 address by its /64 in the sign-in, sign-up, one-time-code, second-factor, password-reset, token, Google, hosted-page and hosted-pay limits and in the failure throttle; the address recorded in an audit entry or an acceptance is still the full one. Tests: `TestLimitKeyGroupsAnIPv6NetworkByItsSlash64`, `TestPublicLimitsCountAnIPv6SlashSixtyFourOnce`, `TestHostedLimitsCountAnIPv6SlashSixtyFourOnce`.

5. **MEDIUM, an API key with no role and no scope resolves to admin: fixed in #379.** The lookup dropped the scope and an empty entry read as the scope "" of a key from before roles, which means full. The scope is carried (so an older plans-svc's ingest-only key stays ingest-only in a mixed-version rollout) and an entry with neither role nor scope holds nothing. Tests: `TestAKeyWithNeitherRoleNorScopeHoldsNothing`, `TestTheScopeOfAnOlderPlansSvcIsCarried`.

6. **LOW, raw gRPC messages reach API callers: fixed in #382.** The text of a raw `Unavailable`, `DeadlineExceeded`, `ResourceExhausted` or `Aborted` error (a dial error with an internal address in it) is replaced by a plain sentence with the request id; code, status and key stay, and the text goes to the log. **Default (not agreed): an error a service wrote itself with a key keeps its message** (a quota's explanation); making all four codes generic is one line. Tests: `TestRawUpstreamTextOfTheRetryableCodesNeverReachesTheCaller`, `TestAnUnreachableBackendAnswers503WithoutItsAddress`.

7. **LOW, the inbound-invoice secret in the URL: fixed in #382.** `X-Payrudder-Inbound-Secret` is accepted and documented as the way; `?secret=` still works and is documented as deprecated (a provider that can only post to an address needs it); the query of that route is taken off the request before the router, the tracing or any log sees it. Tests: `TestInboundSecretIsPreferablySentInAHeaderAndTheQueryIsNotKept`, `TestMoveInboundSecretTakesTheQueryOffTheRequest`.

8. **LOW, notifier requests signed over the body only: fixed in #382.** `pkg/webhooksig` v2 signs the method, escaped path, raw query, timestamp and body; the gateway and `fakenafru` sign v2 and the notifier refuses v1 unless `NOTIFIER_MAIL_EVENTS_ACCEPT_V1` is set for a rollout (notifier first, then the gateways, then remove the flag). Customers' webhooks and the e-invoice webhook stay v1. Tests: `webhooksig`, `TestASignatureOfOneRequestIsNoGoodForAnother` (a captured GET of the list refused on a DELETE), `TestVersionOneSignaturesAreAcceptedOnlyWhenAsked`.

9. **LOW, no uniqueness guard for a hosted withdrawal; the customer's words: fixed in #387.** Migration `00023` (tenant `00016`) adds a unique index over the hosted withdrawals that name an invoice and are not rejected, after rejecting (as `system`) the later undecided duplicates a race may have left; the loser is told it was received already. **Default (not agreed): API and console records are not limited.** The customer's name and words are recorded as one line each. The 200/1000-character limits and the escaping of the statement in the acknowledgement mail already held; tests now keep them (the mail's in all six languages). Tests: plans-svc `ContractWithdrawalOpenOnce`, `TestWithdrawalMigrationRejectsDuplicatesThatWereLeftByTheRace`, gateway `TestWhatACustomerTypesCannotStartALineOfItsOwn`, notifier `TestWhatTheCustomerTypedIsMailedAsTextInEveryLanguage`.
