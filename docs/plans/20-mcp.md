## Progress (2026-11-02, branch `feat/dx-docs-mcp`)

Done:
- **A real stdio test** (`mcp/src/stdio.test.ts`): it builds the server, starts `dist/main.js` as a child process the way an assistant does, and talks MCP over its stdin and stdout to a local HTTP server that plays the API (tools listed, a call made with the key from the environment, the answer tagged; writes only with `PAYRUDDER_MCP_WRITES=1`; no key means exit 1 with the message on stderr and nothing on stdout).
- **The nine read tools are generated from `api/openapi/v1.yaml`** by `mcp/scripts/generate.mjs` at build, test and typecheck time (the output is not committed, so it cannot be stale): name from the `operationId`, arguments with their limits from the path and query parameters, description from the summary. The allow-list is `mcp/scripts/read-tools.config.mjs`; only a plain `GET` of `/v1/*` can be listed and the generator fails for anything else. The mapping test checks every tool against the OpenAPI file (route, parameters, required, enum, minimum, maximum, pattern, rename) and that the generated file is what the generator makes now. The two write tools stay hand-written; the nine tools keep their names and arguments (the existing tests passed unchanged). `mcp.yml` now also runs when the OpenAPI file or the public docs change.
- **Untrusted fields are tagged:** strings under the keys the customers, payers and staff write (names, e-mail, notes, address lines, references, …; a closing tag inside such a text is broken) come back inside `<untrusted>…</untrusted>`, in reads and in the answers of writes; the server's instructions and every read tool's description say what the tag means. The generator fails when an allow-listed answer has a free-text field that is neither listed as people's text nor as an identifier the model must copy exactly, so a new field is classified before a model sees it.
- **Streamable HTTP** behind a flag (`PAYRUDDER_MCP_HTTP_PORT`): `POST /mcp`, stateless, JSON responses, **each request carries the caller's own API key as a bearer token** and that key alone is used for its calls to the API (`401` without one, nothing shared between callers, the API address is the server's), 127.0.0.1 unless told otherwise, a 1 MiB body limit. Tested over a real client and server (the keys of two concurrent callers never mix).
- **Resources:** `payrudder://openapi` (the tenant API only, with the components it reaches) and the public guides (`payrudder://docs/<page>`: the pages of `docs-site/content` and the documents `docs/publication.yaml` marks public), written to `mcp/assets/` at build.

Defaults (not agreed): API-key bearer authentication (no OAuth); the allow-list is exactly the nine tools that existed; the write tools stay off unless the person who starts the server turns them on, for every caller of an HTTP server alike; the HTTP mode listens on 127.0.0.1.

Not done: OAuth with the console's sign-in, a rate limit per key, an audit log of what an assistant did (all three are needed before this is hosted for others), prompts (monthly revenue review, customer over a limit), the operator MCP, the risk table per tool for the owner to sign, and any new read tool (add an operation to the allow-list and classify its fields).

### The limit per key in the gateway (built 2026-11-03, branch `feat/per-key-rate-limit`; not run against Redis or Postgres here)

Design (default, not agreed): `api_keys.rate_percent` (integer 1 to 100, NULL = no limit of its own). The gateway's `charge` adds a second GCRA bucket `gw:rl:{tenant}:{class}:key:{key_id}` whose limit is that percentage of the tenant's tier limit for the class and refuses with the same `429 gateway.rate_limit.exceeded` + `Retry-After` (no new error key); a key without a percentage costs nothing extra (no Redis call). A percentage rather than an absolute number follows the tenant's tier when it changes.

Built:
- **plans-svc:** migration `00034_api_key_rate_percent.sql` (`rate_percent integer CHECK (BETWEEN 1 AND 100)`; `api_keys` lives only in the pooled database, so there is no tenant twin), `InsertApiKey` / `ResolveApiKey`, `Commands.Issue` takes the percentage and validates it (0 = none, 1 to 100, else `INVALID_ARGUMENT` with the field violation `rate_percent`, the repo's `domain.Invalid` pattern; no new error key), a rotation gives the replacement the old key's percentage, the audit event `api_key.created` carries it.
- **proto:** `ApiKey.rate_percent`, `CreateApiKeyRequest.rate_percent`, `CreateMyApiKeyRequest.rate_percent`, `ResolveApiKeyResponse.rate_percent`; `gen/go` regenerated (buf, sqlc).
- **gateway:** `auth.Entry.RatePercent` (in the 60 s cache entry; an entry from an older release reads as none) into `Principal.RatePercent`; `Limiter.AllowKey`; `Server.charge` calls it **first**, and only when the principal is an API key with a percentage, then the tenant bucket as before. **Order:** key first, so a key that has spent its share is refused without taking from the tenant's budget (the other keys' room); a request the tenant then refuses leaves its cost with the key (a stricter key, never a looser one). The key's burst is at least 1 and a batch above it costs the whole burst. Redis failing: each bucket falls back to this replica's share in memory, as the tenant's does (so with N replicas and Redis down a key gets its share per replica). REST: `POST /app/v1/apps/{id}/api-keys` takes `rate_percent` (400 `gateway.request.invalid` outside 1 to 100), the operator `POST /admin/v1/tenants/{id}/api-keys` takes it through the proto body.
- **API and clients:** `api/openapi/v1.yaml` (`AppCreateApiKeyRequest`, `CreateApiKeyRequest`, `ApiKey`), `web/admin/src/shared/api/schema.d.ts`. The four SDKs were regenerated and **did not change**: they cover the tenant API only, and key management is a console/operator route outside them.
- **Console:** the new-key sheet has "Rate limit (% of plan)" (optional, 1 to 100, the button is disabled and a message shows for anything else), the key list and the permissions sheet show it; six locales.
- **Docs:** `docs/03-services/gateway.md`, `docs-site/content/authentication.md`, `mcp/README.md` ("Rate limits").
- **Tests:** limiter (key bucket refuses while the tenant bucket has room, no percentage = no Redis call and no bucket, Redis-failure fallback, burst floor and large batch), auth (the percentage reaches the principal through the cache), gateway (the percentage reaches `AllowKey` before the tenant charge; a refusal is the same 429 and does not charge the tenant; the create body is validated and passed on), plans-svc (validation, NULL for 0), console (`parseRatePercent`, `ratePercentOf`), and an integration test (`itest/keyrate_integration_test.go`: create, resolve, rotate, refused outside 1 to 100, the column's CHECK).

Defaults (not agreed): the 1 to 100 range and NULL/0 = none; the percentage is set at creation only (no edit; rotate or make a new key to change it); the same percentage for every route class; ingest is charged per event against the key bucket as against the tenant's; a rotation keeps the percentage; operator-token and signed-in-person requests are not API keys and have no key bucket.

**NOT VERIFIED:** nothing here ran against a real Redis (the Lua script is the tenant bucket's, called with a different key and limit) or Postgres (the migration, the CHECK, the integration test were compiled and vetted but not run); no end-to-end request through a running gateway; the PHP SDK generator was not run (it needs Docker/composer; the other three produced no change). ### OAuth design (default, not agreed; not built)

Read on 2026-11-02: the MCP specification, authorization chapter, revision **2026-07-28** (`modelcontextprotocol.io/specification/latest/basic/authorization`); its sub-pages on authorization-server discovery, client registration and security considerations were **not** read, so what follows about them is from the overview and must be checked before building.

What the specification asks, in short: authorization is optional and applies to HTTP transports only (stdio should read credentials from the environment, which is what this server does). An MCP server is an **OAuth 2.1 resource server**; it MUST publish Protected Resource Metadata (RFC 9728) and answer a request without a valid token with `401` and `WWW-Authenticate: Bearer resource_metadata="…"` (and SHOULD name the `scope`); an authorization server MUST offer RFC 8414 or OpenID discovery, PKCE, and SHOULD support Client ID Metadata Documents (dynamic client registration, RFC 7591, is kept only for compatibility); the client MUST send the `resource` parameter (RFC 8707) in the authorization and token requests; the server MUST accept only tokens issued **for it** (audience check) and MUST NOT accept or pass on any other token; `403` with `error="insufficient_scope"` for a token that lacks a scope.

Design for Payrudder:
1. **Who is the authorization server.** The identity service, behind the gateway at `/oauth/*` (`/.well-known/oauth-authorization-server`, `/oauth/authorize`, `/oauth/token`, `/oauth/revoke`, `/oauth/jwks` only if tokens are JWTs). Sign-in and consent are a page of the console (`/oauth/authorize` in the SPA): the person signs in the way they do today (password, Google, two-factor), then **chooses the app and environment** the assistant may act on and sees the scopes. Nothing about sign-in changes.
2. **Scopes are the API-key permissions** that already exist (`customers:read`, `invoices:read`, …, `pkg/apikey`), plus the roles as shorthands (`read_only`, `billing`, `ingest_only`). The token carries the intersection of the scopes asked for and what the person's role in the account allows (a viewer can never get a write scope); this is the same rule the gateway applies to a session acting as a tenant.
3. **Tokens.** Opaque, prefixed (`qo_`), stored hashed, bound to the person, the tenant (app + environment) and the audience (the MCP server's canonical URL, from `resource`). Access token one hour, refresh token thirty days, rotated at each use, revocable from the console's security page and by the person leaving the account. Live environments need the person to have verified e-mail and, for an account that obliges it, two-factor sign-in (the existing `requireSecondFactorSetup` rule).
4. **No token passthrough.** The specification forbids the MCP server to pass the assistant's token on. So the server **introspects** the token at the authorization server (RFC 7662; the answer says tenant, role, scopes, expiry) and calls the tenant API with a credential the authorization server mints for the API audience from it (token exchange, RFC 8693), short-lived and never shown to the assistant. The gateway then accepts that credential like a session acting as a tenant today, with the same permission check and an audit actor that names the client and the person. The alternative, an API key made at consent and kept by the MCP server, is simpler but leaves a long-lived secret in a process that is hosted for others: not recommended.
5. **Clients.** Client ID Metadata Documents first (the specification's preference), pre-registered clients for the assistants the owner names; dynamic registration only if a client the owner wants cannot do the first. Redirect URIs must be exact; `localhost` ports allowed for desktop clients.
6. **The MCP server's side** (a mode next to the key-per-request one, `PAYRUDDER_MCP_AUTH=oauth`, which needs `PAYRUDDER_MCP_PUBLIC_URL`): serves the metadata document, answers `401` with the challenge, validates audience and expiry on every request, and keeps the per-key limit above per person-and-tenant instead of per key.

What this needs from the owner before anyone builds it: **where the MCP server is hosted and by whom** (a hosted server for other people's assistants is what makes OAuth worth its cost; for one developer's own machine a key is enough), whether the identity service may become an authorization server (it holds the sessions today), and whether a person may let an assistant act on a **live** environment at all (the default of the key-based mode is no). Not verifiable here: any of it with a real client (Claude Desktop, Claude Code, ChatGPT) and a real browser sign-in.
