### The limit per key in the gateway (built 2026-11-03, branch `feat/per-key-rate-limit`; not run against Redis or Postgres here)

Design (default, not agreed): `api_keys.rate_percent` (integer 1 to 100, NULL = no limit of its own). The gateway's `charge` adds a second GCRA bucket `gw:rl:{tenant}:{class}:key:{key_id}` whose limit is that percentage of the tenant's tier limit for the class and refuses with the same `429 gateway.rate_limit.exceeded` + `Retry-After` (no new error key); a key without a percentage costs nothing extra (no Redis call). A percentage rather than an absolute number follows the tenant's tier when it changes.

Built:
- **plans-svc:** migration `00034_api_key_rate_percent.sql` (`rate_percent integer CHECK (BETWEEN 1 AND 100)`; `api_keys` lives only in the pooled database, so there is no tenant twin), `InsertApiKey` / `ResolveApiKey`, `Commands.Issue` takes the percentage and validates it (0 = none, 1 to 100, else `INVALID_ARGUMENT` with the field violation `rate_percent`, the repo's `domain.Invalid` pattern; no new error key), a rotation gives the replacement the old key's percentage, the audit event `api_key.created` carries it.
- **proto:** `ApiKey.rate_percent`, `CreateApiKeyRequest.rate_percent`, `CreateMyApiKeyRequest.rate_percent`, `ResolveApiKeyResponse.rate_percent`; `gen/go` regenerated (buf, sqlc).
- **gateway:** `auth.Entry.RatePercent` (in the 60 s cache entry; an entry from an older release reads as none) into `Principal.RatePercent`; `Limiter.AllowKey`; `Server.charge` calls it **first**, and only when the principal is an API key with a percentage, then the tenant bucket as before. **Order:** key first, so a key that has spent its share is refused without taking from the tenant's budget (the other keys' room); a request the tenant then refuses leaves its cost with the key (a stricter key, never a looser one). The key's burst is at least 1 and a batch above it costs the whole burst. Redis failing: each bucket falls back to this replica's share in memory, as the tenant's does (so with N replicas and Redis down a key gets its share per replica). REST: `POST /app/v1/apps/{id}/api-keys` takes `rate_percent` (400 `gateway.request.invalid` outside 1 to 100), the operator `POST /admin/v1/tenants/{id}/api-keys` takes it through the proto body.
- **API and clients:** `api/openapi/v1.yaml` (`AppCreateApiKeyRequest`, `CreateApiKeyRequest`, `ApiKey`), `web/admin/src/shared/api/schema.d.ts`. The four SDKs were regenerated and **did not change**: they cover the tenant API only, and key management is a console/operator route outside them.
- **Console:** the new-key sheet has "Rate limit (% of plan)" (optional, 1 to 100, the button is disabled and a message shows for anything else), the key list and the permissions sheet show it; six locales.
- **Docs:** `docs/03-services/gateway.md`, `docs-site/content/authentication.md`, `mcp/README.md` ("Rate limits").
- **Tests:** limiter (key bucket refuses while the tenant bucket has room, no percentage = no Redis call and no bucket, Redis-failure fallback, burst floor and large batch), auth (the percentage reaches the principal through the cache), gateway (the percentage reaches `AllowKey` before the tenant charge; a refusal is the same 429 and does not charge the tenant; the create body is validated and passed on), plans-svc (validation, NULL for 0), console (`parseRatePercent`, `ratePercentOf`), and an integration test (`itest/keyrate_integration_test.go`: create, resolve, rotate, refused outside 1 to 100, the column's CHECK).

Defaults (not agreed): the 1 to 100 range and NULL/0 = none; the percentage is set at creation only (no edit; rotate or make a new key to change it); the same percentage for every route class; ingest is charged per event against the key bucket as against the tenant's; a rotation keeps the percentage; operator-token and signed-in-person requests are not API keys and have no key bucket.

**NOT VERIFIED:** nothing here ran against a real Redis (the Lua script is the tenant bucket's, called with a different key and limit) or Postgres (the migration, the CHECK, the integration test were compiled and vetted but not run); no end-to-end request through a running gateway; the PHP SDK generator was not run (it needs Docker/composer; the other three produced no change). ### OAuth design (default, not agreed; BUILT 2026-11-04, never tried with a real client)

**Status (2026-11-04, branch `worktree-agent-aa63c3c0667247e66`, not pushed): built** by an agent while the owner was away, who said to take the defaults of this section and mark them "default (not agreed)". Every choice below and in "What was built" is **default (not agreed)** until the owner says otherwise. Nothing was tried with Claude Desktop, Claude Code or ChatGPT or with a real browser sign-in; the pieces are tested one by one against fakes and, for the grants, codes and tokens, against a real Postgres (`TestPlansSvc/OAuth`).

Read on 2026-11-02: the MCP specification, authorization chapter, revision **2026-07-28** (`modelcontextprotocol.io/specification/latest/basic/authorization`). Its three sub-pages (`…/authorization/authorization-server-discovery`, `…/client-registration`, `…/security-considerations`) were **read on 2026-11-04**, before building. Where they differ from what the first reading of the overview said, the text below is corrected and this list says how:
- **Authorization-server discovery.** The MCP server MUST put `authorization_servers` (at least one) in its Protected Resource Metadata, and MUST offer either the `WWW-Authenticate` `resource_metadata` challenge or the well-known address; a client tries the challenge first, then `/.well-known/oauth-protected-resource/<path of the endpoint>`, then the root form. The authorization server's metadata is looked up at `/.well-known/oauth-authorization-server` (RFC 8414, path inserted for an issuer with a path) and then OpenID's address, and the `issuer` inside MUST equal the address it was fetched for. Consequence taken: the MCP server serves the metadata at all three addresses, and the gateway's issuer (`PAYRUDDER_PUBLIC_URL`) **must have no path** (checked at start). The first reading said "`/oauth/jwks` only if tokens are JWTs": they are opaque, so there is none.
- **Client registration.** Priority for a client: pre-registered, then a Client ID Metadata Document if the metadata says `client_id_metadata_document_supported`, then dynamic registration if `registration_endpoint`. The `client_id` is an https URL **with a path** whose document MUST contain `client_id` (equal to the URL), `client_name` and `redirect_uris`; the server MUST validate all three and the redirect URI of each request against the document, SHOULD cache by HTTP headers, and SHOULD protect itself against SSRF. Dynamic client registration is **deprecated** ("kept for old authorization servers"). Corrected: the first reading made pre-registered clients a second default; **not built** (below). The server MUST also **display the redirect host** and SHOULD **warn about a `localhost` redirect**, because a metadata document cannot stop another program on the machine from listening on the port: the consent page does both.
- **Security considerations.** (1) The authorization response SHOULD carry `iss` (RFC 9207, to stop mix-up attacks) and the metadata then says `authorization_response_iss_parameter_supported: true`: **not in the first reading; built.** (2) `code_challenge_methods_supported` MUST be in the metadata or clients refuse to proceed: built (`["S256"]`). (3) A client's redirect URIs MUST be https or `localhost`, and the server MUST match exactly: built; the one exception is RFC 8252's loopback port (a desktop client takes a free port), which I took as a default. (4) Refresh tokens for public clients MUST be rotated: built (and reuse ends the grant). The MCP server SHOULD NOT put `offline_access` in its challenge or `scopes_supported`: it does not. (5) An insufficient-scope response SHOULD carry `scope`, `error_description` **and `resource_metadata`**, and SHOULD name every missing scope at once, and the server MUST account for scope hierarchies: corrected in item 6 below; the hierarchy question does not arise because the shorthands (`read_only`, …) are expanded into plain permissions when the token is issued. (6) A malformed authorization request is `400`; invalid or expired tokens are `401`. (7) The MCP server MUST NOT pass the client's token to an upstream API; it may use "a separate token issued by the upstream authorization server": that is what the token exchange of item 4 does.

What the specification asks, in short: authorization is optional and applies to HTTP transports only (stdio should read credentials from the environment, which is what this server does). An MCP server is an **OAuth 2.1 resource server**; it MUST publish Protected Resource Metadata (RFC 9728) and answer a request without a valid token with `401` and `WWW-Authenticate: Bearer resource_metadata="…"` (and SHOULD name the `scope`); an authorization server MUST offer RFC 8414 or OpenID discovery, PKCE, and SHOULD support Client ID Metadata Documents (dynamic client registration, RFC 7591, is kept only for compatibility); the client MUST send the `resource` parameter (RFC 8707) in the authorization and token requests; the server MUST accept only tokens issued **for it** (audience check) and MUST NOT accept or pass on any other token; `403` with `error="insufficient_scope"` for a token that lacks a scope.

Design for Payrudder:
1. **Who is the authorization server.** The identity service, behind the gateway at `/oauth/*` (`/.well-known/oauth-authorization-server`, `/oauth/token`, `/oauth/revoke`, `/oauth/introspect`; no `/oauth/jwks`, the tokens are opaque). **Corrected when building:** `authorization_endpoint` is the console's own page `<PAYRUDDER_APP_URL>/oauth/authorize`, not a gateway route that redirects (a redirect from the gateway would be one more place for an open redirect, and the page needs the person's session, which lives in the console). Sign-in and consent are that page: the person signs in the way they do today (password, e-mailed code, Google, two-factor; the address they came to is kept through the sign-in), then **chooses the app and environment** the assistant may act on and sees the scopes. Nothing about sign-in changes. The page asks the gateway to validate the request (`GET /app/v1/oauth/request`) and sends the decision (`POST /app/v1/oauth/consent`); the answer is the address to open.
2. **Scopes are the API-key permissions** that already exist (`customers:read`, `invoices:read`, …, `pkg/apikey`), plus the roles as shorthands (`read_only`, `billing`, `ingest_only`). The token carries the intersection of the scopes asked for and what the person's role in the account allows (a viewer can never get a write scope); this is the same rule the gateway applies to a session acting as a tenant.
3. **Tokens.** Opaque, prefixed (`qo_` access, `qr_` refresh, `qm_` the credential of item 4), stored hashed (SHA-256 of 256 random bits), bound to the person, the tenant (app + environment) and the audience (the MCP server's canonical URL, from `resource`, which must be one of the gateway's `PAYRUDDER_OAUTH_RESOURCES`). Access token one hour, refresh token thirty days, rotated at each use (a refresh token used twice, or an authorization code used twice, ends the grant), revocable from the console's security page (**Connected assistants**), by the client (`/oauth/revoke`, RFC 7009) and by the person leaving the account (the membership and the role are looked at again on every introspection, so no revocation has to run). Codes live one minute, work once and are spent by the first try, right or wrong. **Live environments are off by default**: `PAYRUDDER_OAUTH_ALLOW_LIVE=on` turns them on, and then the person needs a verified e-mail address and, for an account that obliges it, two-factor sign-in (the existing `requireSecondFactorSetup` rule applies to the consent page's calls like any session call). Storage: `oauth_grants`, `oauth_codes`, `oauth_tokens` (migration `00037`, plans-svc, person tables without a tenant twin; `oauth_grants` is on the RLS allowlist like `api_keys`). Default: a grant never ends by itself while its refresh tokens are used within thirty days of each other.
4. **No token passthrough.** The specification forbids the MCP server to pass the assistant's token on. So the server **introspects** the token at the authorization server (RFC 7662; the answer says tenant, role, scopes, expiry) and calls the tenant API with a credential the authorization server mints for the API audience from it (token exchange, RFC 8693: `POST /oauth/token` with the shared secret, `audience` = the API, plus `resource` = the MCP server's own address as an extension so one server cannot trade in a token issued for another), five minutes at most and never longer than the access token, never shown to the assistant. The gateway then accepts that credential (`qm_`) on the tenant API as a **custom-role key** of the person's scopes: the same permission check as an API key's on every route (a route no permission covers needs an admin key, so it stays closed), the person's membership looked at on every call, and an audit actor that names the person and the client (shortcut: the audit log has no client field, so the actor's e-mail reads `ada@example.com via Example Assistant`). The alternative, an API key made at consent and kept by the MCP server, is simpler but leaves a long-lived secret in a process that is hosted for others: not recommended.
5. **Clients.** Client ID Metadata Documents only (the specification's preference; **built**). Pre-registered clients and dynamic client registration (RFC 7591, deprecated in the specification) are **not built**: dynamic registration would need a table, an open endpoint to rate-limit and a policy on who may register, and no client the owner named needs it; a client that cannot publish a document cannot connect until someone builds it. The document is fetched through the same SSRF-safe client as webhooks (public addresses only, no redirects, 5 s, 32 KiB), validated (`client_id` equals the URL, a `client_name`, 1 to 10 redirect URIs that are https or loopback http, public client only, `authorization_code`), and cached for five minutes (a flat time, not the HTTP cache headers). Redirect URIs must match **exactly**; the one exception is a loopback redirect, whose port may differ (RFC 8252; default, not agreed). There is no trust list: any https client can ask and the person decides on what the page shows (name, the host of the client's address, the host of the redirect, a warning for a redirect to their own machine).
6. **The MCP server's side** (a mode next to the key-per-request one, `PAYRUDDER_MCP_AUTH=oauth`, which needs `PAYRUDDER_MCP_PUBLIC_URL`, `PAYRUDDER_MCP_OAUTH_SECRET` and the HTTP transport): serves the Protected Resource Metadata (at the path-inserted address, the root form and `/mcp`), answers `401` with `WWW-Authenticate: Bearer resource_metadata="…", scope="read_only"` (no `error` when there were no credentials, `error="invalid_token"` when there were), **validates active/audience/expiry on every request** (the introspection answer is reused for 30 s, the audience and expiry are checked again on each use; a revoked token can therefore work up to 30 s), answers `403` with `error="insufficient_scope"`, every missing `scope` of a call or batch, and `resource_metadata` **before** the tool runs (each tool names its permission; the reads' come from the path, `mcp/src/scopes.ts`, the writes' by hand, and a test checks they are real permissions), and keeps the per-key limit above **per person and tenant** instead of per key. A `qk_` key, a refresh token and the exchange credential are refused in this mode. A live token is refused unless `PAYRUDDER_MCP_ALLOW_LIVE=1`.

#### What was built, and what was not (2026-11-04; all default, not agreed)

- `pkg/oauth` (shape and hash of codes and tokens, PKCE S256, resource and redirect rules, the Client ID Metadata Document, scopes) with unit tests; migration `00037`, `queries/oauth.sql`, IdentityService RPCs and `internal/identity/oauth` in plans-svc, integration-tested as `TestPlansSvc/OAuth` (consent cut to the role, live gates, a code works once with the right verifier and ends the grant when replayed, refresh rotation and reuse detection, introspection that follows the role and the membership, the API credential, revocation by the client and by the person, only hashes stored); gateway `httpapi/oauth.go` (metadata, token, revoke, introspect, the two consent routes, the grants list and revoke, the `qm_` credential on the tenant API, the token endpoint limited to 30 requests a minute per address, the introspection to 1200) with fakes-based tests and the OpenAPI entries; the console's consent page (`/oauth/authorize`) and **Security → Connected assistants**, six locales, a mock end-to-end spec; the MCP server's `oauth` mode with unit and HTTP tests and a built-binary test.
- Environment: gateway `PAYRUDDER_OAUTH_RESOURCES` (empty = off), `PAYRUDDER_OAUTH_RESOURCE_SECRET`, `PAYRUDDER_OAUTH_ALLOW_LIVE` (default off); MCP `PAYRUDDER_MCP_AUTH`, `PAYRUDDER_MCP_PUBLIC_URL`, `PAYRUDDER_MCP_ISSUER`, `PAYRUDDER_MCP_OAUTH_SECRET`.
- **Not built:** dynamic client registration, pre-registered clients, a client trust list, the HTTP cache headers for client documents, a client field in the audit log, a revocation that reaches the MCP server's 30 s cache (a revoked token works here for up to 30 s), OpenID Connect discovery (only RFC 8414), `offline_access`, an expiry on a grant that is never refreshed, rate limiting of the consent routes beyond the session limit every console call has, a check that `PAYRUDDER_MCP_PUBLIC_URL` and the gateway's `PAYRUDDER_OAUTH_RESOURCES` agree (a mismatch shows as `invalid_target` on the consent page). Not verified: any of it with a real client, a real browser sign-in (Google, two-factor) in front of the consent page, a real DNS name for the client document, the Helm chart and compose files (the new variables are not in them).
- Known limitation: the consent page reads the request from the address, and the sign-in in front of it keeps the address through `next` (up to 4000 characters for this page, 500 elsewhere); a client with a longer request loses it at sign-in and the person starts again from the assistant.

What this needs from the owner (it was needed before building; the build used the defaults): **where the MCP server is hosted and by whom** (a hosted server for other people's assistants is what makes OAuth worth its cost; for one developer's own machine a key is enough), whether the identity service may become an authorization server (it holds the sessions today), and whether a person may let an assistant act on a **live** environment at all (the default of the key-based mode is no). Not verifiable here: any of it with a real client (Claude Desktop, Claude Code, ChatGPT) and a real browser sign-in.
