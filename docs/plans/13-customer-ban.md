## Done (2026-11-01, branch `feat/block-and-tenant-status`)

Defaults the implementer chose, because the owner said not to ask (**default, not agreed**; the owner may overturn any of them):

1. **"Ban" = block new purchases** (done in #252, #260, #276) **+ a reason category + an optional end** (`blocked_until`). Categories: `fraud`, `chargeback`, `abuse`, `request`, `other` (empty allowed). The end must be in the future; every check reads it, so a block **stops holding at that time with no job** (the row keeps saying "blocked" until somebody lifts it; the console and the API say it ended). 3. **One gate.** `pkg/paymentgate.Check(op, tenantStatus, block, now)` decides for every path; callers only turn its verdict into their own error key (`plans.customer.blocked`, `billing.customer.blocked`, and `plans.tenant.on_hold` / `billing.tenant.on_hold` for a tenant the operator has taken out of service, plan 14). The actor is the signed-in person's address, `key:<api key id>` for an API key, or `operator`; the gateway sets it, a body cannot.
5. **Webhooks** `customer.blocked` (`customer_id`, `customer_external_id`, `category`, `reason`, `blocked_until`) and `customer.unblocked`, through the whole checklist (model, four SDK enums and data types, console list, `docs/16-webhooks.md`, the OpenAPI schemas). Blocking a customer who is blocked sends nothing. **The end of a block by itself sends no event** (no job exists to send it); lifting a block that had ended does.
6. **Out of scope, as the review addendum said:** the blocklist across customers, the platform-wide fraud list, notices to the customer, appeals, cancelling everything.

## Done (2026-11-02, branch `feat/suspend-alerts-health-ui`): suspend service

Defaults the implementer chose (**default, not agreed**):

1. **Suspending is an option of the block**, not a second state: `POST /v1/customers/{id}/block` takes `suspend_service` (bool, default false). A block already in force is kept as it is (including its suspension): to change it, lift it and block again, which writes both to the history. The customer carries `service_suspended`, and each history row `suspend_service`; both are read together with `block_time` / `blocked_until` (a block that ended by itself no longer suspends anything).
2. **Entitlement checks deny.** `LimitStatus.suspended` (REST `suspended` on `EntitlementStatus`) is true on every meter of the customer and `allowed` is false whatever the limit, the mode (soft and notify too) and the usage, also on a meter the plan does not limit. A meter that does not exist is still `NOT_FOUND`. The seller's service has to ask before it serves; Payrudder does not stop the seller's own service.
3. **Ingestion still accepts and counts** (the question of the task: *accepted, flagged, or refused?* Default: **accepted, not flagged**). A usage event is a fact that already happened and the seller is owed for it (invoicing is unchanged); refusing it would leave a hole in the period when the suspension ends, and flagging it would make ingest-svc read the entitlements topic, which it deliberately does not. The `used` figure of a suspended customer keeps growing. If the owner wants ingestion refused, it is a gateway check against the block (the gateway already resolves the customer) and an error key; nothing here prevents it.
4. **The record.** `plans.entitlements.v1`, key `{tenant}/{customer}/` (an empty meter), an `EntitlementState` with `suspended = true`, `valid_from` the time of the block and `valid_until` the block's end when it has one. `entitlements/command.Suspend` and `Unsuspend` write it to the outbox **in the transaction of the block or the lift** (a tombstone for the lift). A block that ran out and is replaced by one that does not suspend writes the tombstone too. limits-svc reads it into `Store.suspended` and the Redis mirror `lim:ent:{tenant}:{customer}:`; because it carries `valid_until`, the suspension ends with the block with no job (as every other check of a block does). The customer's limits are never touched, so lifting the block restores exactly what was there.
5. **Webhooks and history.** `customer.blocked` carries `suspend_service`; the history row records it. The console block form has a switch, the sheet's banner says "Service suspended" while it holds, the history lists it. Six locales; no new error key (the answer is data, not an error).
6. **Tests.** limits-svc: `TestSuspension` (unit: from, until, lift by a record or a tombstone, not an entitlement); integration `TestLimits/SuspensionComesFromTheTopic` (a real Redpanda and Redis: the record on the key of an empty meter, a meter with a limit and one without, usage still counted, the tombstone) and `TestQuotas/ASuspendedCustomerIsAllowedNothing` (soft limit, `GetLimitStatus`, another customer untouched, an ended suspension). plans-svc: `CustomerBlockDetails` (the record published with its `valid_until`, no record for a plain block, a tombstone on lift and on a plain block after one that suspended, nothing on a repeated block, the webhook data). Gateway: the request field and the response field. The limits test fails without the change (checked once by forcing `Suspended` to false).
7. **Not verified here:** the portal and the console in a real browser (the mock e2e ran), an upgrade with the old limits-svc running: an older limits-svc reads the record, finds an empty meter and logs "skipping invalid entitlement" without failing, so roll limits-svc out before the first suspension.

### The first charge of an invoice finalized before a hold (plan 14): built 2026-11-02 (below); the analysis that follows is why it needed a state

`PdfRendered --Continue--> PaymentRequested` (effect `charge`) cannot hold today without a new place to wait. Holding it in the table needs a state or a guard (`PAYMENT_HELD` with a retry date, or the existing `PAYMENT_DECLINED` + dunning, which would count the held charge as a dunning attempt and show a decline that never happened), the engine asking `Hold` when it fires the charge, the retry sweep to learn the state, the diagram in `billing-svc.md` and the exhaustive table tests, the console's state labels, and a decision about an invoice held for long (void? dunning?). That is a change to the payment saga, which this plan keeps out of the same PR as the customer switch; **default (not agreed):** a tenant frozen between a finalize and its charge is charged once, as plan 14 already says.

## Leftovers built (2026-11-02, branch `feat/payments-hold-first-charge`): the held first charge

Defaults the implementer chose (**default, not agreed**):

1. **The first charge is held.** `PDF_RENDERED --Continue--> PAYMENT_REQUESTED` asks the one gate (`pkg/paymentgate`, op pay an invoice, `Engine.Config.Gate`, replacing `Config.Hold`) before it sends the charge; where the gate says no (the tenant is suspended, frozen or banned, or the customer is blocked for **fraud or a chargeback**) the saga goes to the new state **`PAYMENT_HELD`**: no command, no provider call, no dunning attempt used, the invoice stays open, the sweep looks again an hour later. It is not a decline (the analysis above wanted a new place to wait rather than `PAYMENT_DECLINED`, which would count a dunning attempt and show a decline that never happened). **Released** by the dunning sweep when the gate lets it through (charged as the first charge, attempt 0 and the key it always had) or by the seller's **Retry** (`POST /admin/v1/invoices/{id}/retry`, which asks the gate again and so cannot charge a customer the gate still refuses); **ended** by **Void** or by money recorded by hand. A link-collected invoice and an invoice of nothing are not the saga's to charge and are not held. The console shows the state ("first charge held") in the invoice list, the sheet's history and the dunning report; **the buttons for the seller's Release and Void came with `feat/leftovers-4-payments` (the last section below)**. Migration billing `00011` (the dunning index), the dunning report enum (API, four SDKs, console).
2. **The dunning sweep applies the same gate to the retry of a declined charge** (row 9 above): a customer blocked for fraud or a chargeback is no longer dunned. A block for another reason leaves what is invoiced payable and dunned as before.

Tests: model `TestFirstChargeHeldByThePaymentGate` (the table, every guard context incl. `Held`); billing `TheFirstChargeIsHeldByThePaymentGate` (held, Retry while the gate says no, the sweep while it says no, released as the first charge, void; fails without the change: checked once by making the gate unasked), `DunningWaitsForATenantOnHold`. **Not verified here:** the customer lookup in the gate against a real plans-svc under load (one `GetCustomer` per first charge and per due retry); the rollout order (an older billing-svc does not know the state PAYMENT_HELD: roll billing-svc out before the first freeze).

## Leftovers built (2026-11-02, branch `feat/leftovers-4-blocklist`): the blocklists

Defaults the implementer chose (**default, not agreed**; the owner may overturn any of them):

1. **Kinds: e-mail address, tax id, external customer id.** A card fingerprint is **not built, because the data does not exist**: no service of Payrudder stores one for a customer (payments-worker keeps provider references and reconciliation fingerprints of findings, never a card), and what a provider's API calls a fingerprint (Stripe's `card.fingerprint`, for one) is UNVERIFIED here and was not read from a real response. It needs a decision on holding provider card data first (plan 08).
2. **Two lists, one gate.** `customer_blocklist` is the app's (the tenant API `GET/POST /v1/blocklist`, `DELETE /v1/blocklist/{id}`, `customers:read` / `customers:write`, four SDKs; the console page *Blocklist* in the sidebar after Customers). `platform_blocklist` is the operator's (`/admin/v1/blocklist`, the console's *Platform blocklist*), held against every app except the platform's own SaaS customers, and an app is never told which list refused. Both are checked by one function (`blocklist.Lists.Check`) where the matrix's paths that **make or re-identify a customer** are: creating a customer, changing the e-mail address of the contact and changing the tax id. Refusal: `plans.customer.blocklisted` (FAILED_PRECONDITION; six locales).
3. **Only what is new is checked on a change**, and **nothing that exists is touched**: a customer who was listed after they came can still change their name, keep their subscriptions and pay what they owe (the matrix of "Path by gate" is for a *blocked* customer, and a blocklist entry does not block one). To act on a customer who matches, block them from the customer list. (Auto-blocking the matches of a new entry is not built: **default, not agreed**.)
4. **No other path creates a customer.** Hosted pages, payment links and the portal need an existing customer; the only other creator is the SaaS sweep (the platform tenant's customers), which skips the operator's list on purpose so that a banned person cannot stop the billing of their organisation. Usage ingestion is unchanged (it never creates a customer).
5. **Normalisation is plain**: lower case for an address (no removal of `+tag` or of dots: a person can still vary the address; that is a limit, not a decision), `pkg/taxid.Normalize` for a tax id, exact for an id. At most 1000 entries per list (`plans.blocklist.full`), so lists are not paged; the console reads the whole list and filters it in the browser.
6. **Audit** (plan 22 G4): `blocklist.entry_added` / `entry_removed` and `platform_blocklist.entry_added` / `entry_removed` through `pkg/audit`, in the transaction of the change, **without the value** (the kind only; an address or a tax id is personal data). The note is the owner's own and is never shown to the person.
7. **A sandbox reset keeps the list** (it is configuration, like coupons and webhook endpoints).

Tests: `internal/blocklist` (`Normalize`, the subject), plans-svc integration `Blocklist` (normalised and idempotent add, list, another app does not see it; a listed e-mail address in other capitals and a listed external id refused at creation with no customer made; a new listed address or tax id refused on a change while a name change of a listed customer is not; removing; the platform list refused in two apps, not shown to an app, the SaaS skip, removing it; fails without the gate: checked once), `RLSIsolationEveryTable` and the cells tests (`customer_blocklist` is a tenant table and moves with the tenant; `platform_blocklist` is a global table); console mock e2e `blocklist.spec.ts` (read, filter on its button, add, remove after a question, a viewer, the operator's page) and the `blocklist` entry of `list-contract.spec.ts`. **Not verified here:** the pages in a real browser by a person (the mock e2e ran in Chrome), Arabic right to left on these two pages, an upgrade with an older plans-svc running (it has no table to read: roll plans-svc out first, then add entries).

## Leftover built (2026-11-02, branch `feat/leftovers-4-payments`): the invoice's sheet says why a first charge is held, and the seller can release or void it

Defaults the implementer chose (**default, not agreed**):

1. **The existing saga commands, for the seller.** `Retry` and `Void` are the operator's (`/admin/v1/invoices/{id}/retry|void`); the person's console cannot use `/admin`, so two tenant-API routes carry the same saga events: `POST /v1/invoices/{id}/release` (`ReleaseHeldInvoice`, event `Retry`, cause `seller:release`) and `POST /v1/invoices/{id}/void` (`VoidHeldInvoice`, event `Void`, cause `seller:void`), both `invoices:write`. **Only while the saga is `PAYMENT_HELD`**, checked under the row lock; anything else is `409 billing.invoice.not_held`. That restriction is the point of not exposing the general Void: a void of a paid invoice refunds the card, which a key with `invoices:write` (a checkout's server) must not be able to start (finding 1 of the security review, #377). The operator keeps the general ones.
2. **Release does not override the gate.** It asks the gate again, as the hourly sweep does: where the customer is still blocked for fraud or a chargeback, or the environment is on hold, the invoice stays held and the answer says `PAYMENT_HELD`. To charge a customer the seller blocked, the seller lifts the block first (then release now, or wait for the sweep). The alternative, a seller's override of their own block, was not built: it would be a second meaning of "blocked" on the payment path (the table above), and for a tenant on hold it would let a banned tenant charge.
3. **Why it is held** is `GET /v1/invoices/{id}/payment-wait`: the gate asked now (`customer_blocked`, `tenant_on_hold`, `none`, unknown), the time the saga entered the state and `next_attempt_at`. Not stored with the saga: a stored reason would be up to an hour stale and the hold changes when the seller lifts a block.
4. **Console.** `PaymentWaitCard` on both invoice sheets (the seller's and the operator's). Release and Void each ask first and name the invoice and the amount outstanding. A viewer sees why and gets no button; nobody gets one while the operator has the environment on hold (the gateway refuses every write then). The strings are in six languages.
5. **Audit.** `invoice.release` and `invoice.void`, in the transaction of the change, by the actor of the request (the person, or the API key): `detail` holds the saga state before and after, so a release the gate refused is in the log too (`to` still `PAYMENT_HELD`).

Tests: billing integration `TheSellerReadsAndEndsAHeldCharge` (the reason for each verdict and the times, the state alone for a paid invoice, another tenant gets not-found, a completed invoice cannot be released or voided, release leaves it held while the gate says no and charges it as the first charge (attempt 0) when it lets it through, void ends a held invoice with no refund command and one audit entry); gateway `TestPaymentWaitIsReadWithTheWindowFromPaymentsWorker`, `TestReleaseAndVoidAreWritesOfTheInvoicesPermission` (a read-only key, a key without `invoices:write` and a frozen tenant are refused before billing is asked); console `paymentWait.test.ts` and `e2e-mock/payment-wait.spec.ts`. **Not verified here:** a real freeze or block on a running stack, the console beyond the mock e2e (headless Chrome), the rollout order (an older gateway has no routes; an older billing-svc answers `UNIMPLEMENTED` to the three calls).

## Leftovers built (2026-11-02, branch `feat/leftovers-4-block-tenant`): the notice to the customer

Defaults the implementer chose (**default, not agreed**; the owner may overturn any of them):

1. **A mail category that is off until the app switches it on.** `customer_notices` (`pkg/mailcategory`) is the sixth category of the app's mail page. Every other category is on until switched off; this one is the other way round, so a seller is never surprised by a mail that tells a person they are blocked. It is stored as `tenant_mail_settings.customer_notices_on` (public migration 00031, tenant 00022; the `disabled` array and its CHECK are unchanged), listed in `GET /v1/mail-settings` like the rest (`enabled: false` for a tenant that never chose), switched with the same `PUT`, audited as `mail_settings.changed`, and read by the notifier through the switch it already asks (`Permitted`). The promote flow (sandbox to live) compares what **differs from the default** (a category switched off, but for this one, switched on), so a live app that never chose still takes the sandbox's choice (`promote/query` `Mail`, with a test for the notices).
2. **Two mails, in six languages** (`customer_blocked.v1`, `customer_unblocked.v1`; `docs/email-template-contract.md`). The first says the seller restricted the account, until when (in the seller's time zone, in the customer's language) when the block has an end, that purchases and plan changes stop, and **adds a line when the block also suspends the service** ("their service is suspended" is that line, not a mail of its own); the second says the restriction is lifted. A block that ran out and was cleared by the sweep sends the second one.
3. **It never says why.** The category (`fraud`, `chargeback`...) and the seller's note are the seller's: they are not in the fact (`CustomerBlockNotice`, `proto/payrudder/events/v1/customer_block_notice.proto`), not in the template data, and a test fails if the raw bytes of the fact contain either. The mail also says nothing about what stays payable (that depends on the category, which it must not reveal): "subscriptions and invoices you already have are not cancelled by this notice", and where to write: the seller.
4. **How it travels.** `customers/command.Block` and `liftBlock` (so the sweep too) write the fact to the outbox in the transaction of the block or the lift (topic `customer.block-notice.v1`, key `{tenant}/{customer}`, whether or not the app has the mail on); the notifier's consumer (`blocknotice`, group `notifier-block-notices`, own DLQ, `sent_notifications.kind = 'customer_notice'`, notifier migration 00006) asks the mail switch and sends one mail per fact (dedup key: the fact's `event_id`). **A fact read while the category was off is not sent later** (switching it on does not mail the blocks that went before), so a lift can reach a customer who was never told of the block if the switch was turned on in between. A tenant on hold sends no customer mail at all (the rule that already exists), a sandbox tenant's notice goes to the sandbox sink.
5. **The webhooks carry what the notice needs.** `customer.blocked` has `customer_id`, `customer_external_id`, `blocked_until`, `suspend_service` (and the seller's `category` and `reason`, which stay out of the mail); `customer.unblocked` has the ids. The notice does not depend on them (the fact is written in the same transaction), so no webhook field was added and the four SDK webhook files and `docs/16-webhooks.md` are unchanged.
6. **Not built:** a per-block "do not tell this one" choice; a notice for a block that is only extended; text a seller can edit (the seller's own wording is a template of its own: plan 11's Nafru-rendered mail would do it).

Tests: `pkg/mailcategory` (`DefaultOff`, the two templates' category); plans-svc integration `MailSettings` (six categories, the notices off for a new tenant, on and off again without disturbing the others) and `CustomerBlockDetails` ("a block and a lift queue the customer's notice, with none of the seller's reasons": the fact on the outbox for the block and for the lift, a repeated block queues none, nothing of the reason in the bytes; it fails without the call: checked once); notifier unit `blocknotice` (the data, both mails in six languages, no reason, the category) and integration `TheNoticeToABlockedCustomerIsOffUntilSwitchedOnThenSentOnce` (a real Redpanda and Mailpit: nothing sent while off and the offset moves, then one mail per fact in the customer's language, the kind recorded); console `mail.spec.ts` (the switch is off, labelled and switches on with a partial `PUT`). **Not verified here:** the texts by a native speaker of each language; a real mailbox or relay; the rollout order (create the topics, deploy the notifier with its migration, then plans-svc: facts written before the consumer exists wait on the topic for 90 days and are read when it starts).

## Leftovers built (2026-11-03, branch `feat/customer-block-appeal`): the appeal

The analogue of the tenant appeal ([14](14-tenant-management.md#leftovers-built-2026-11-02-branch-featleftovers-4-tenant-lifecycle-appeal-retention-scheduled-suspension)) for a customer the **seller** blocked. Defaults the implementer chose (**default, not agreed**; the owner may overturn any of them):

1. **How the customer reaches the form: the portal link they already have.** No new way of signing in. The portal page (`/c/{token}`, the seller's portal link, `docs/hosted-pages.md`) shows "Appeal this restriction" to a customer whose block is in force (the gateway asks plans-svc for the customer, a block with an end in the past counts as ended); it leads to `GET|POST /c/{token}/appeal`. A customer who is not blocked, or whose block ended, gets the "nothing to appeal" page (404) and no link. **Not built:** a link in the block notice mail (the notifier makes no portal link, and inventing one there would be a new credential; a blocked customer who lost their portal link asks the seller for a new one); an appeal for a customer who never had a portal link.
2. **What the customer can do.** Send one statement of 1 to 2000 characters (counted as characters, not bytes). One appeal is open per customer, and so per block (a customer is blocked once at a time): a partial unique index on `(tenant_id, customer_id) WHERE status = 'open'`; a second is refused `plans.customer_appeal.exists` (the page says the first one waits). After a **rejection** the customer may appeal again (the same default as the tenant appeal); the portal shows the seller's answer to the last rejected one. A customer who is not blocked is refused `plans.customer_appeal.not_blocked`. **The category and the note of the block are never shown**: the page, the appeal and the API answer carry neither (a test looks for both).
3. **Rate limit:** the POST counts as the other public form posts that write (`hostedPayAllowed`: 10 a minute and 60 pages a minute per address, `public_limits.go`); the page is a read like any hosted page.
4. **The statement is untrusted text.** Stored as written (trimmed, NUL removed), printed through `html/template` on the portal and escaped by Vue in the console (a box that keeps line breaks, labelled "untrusted"); the console test types `<img onerror>` and checks nothing ran. The API documents it as untrusted too.
5. **The seller decides** (`GET /v1/customers/{external_id}/appeals`, `POST /v1/customers/{external_id}/appeals/{id}/decision`, `customers:read` / `customers:write`; the console's customer sheet shows the latest appeal under the block banner with Accept and Reject, **hidden from a viewer and from a peek over another sheet**, `useCanWrite`). **Accept** lifts the block through `liftBlock`, the same code as `POST .../unblock` and the sweep: the history row, the end of a service suspension, the audit entry `customer.unblocked`, the `customer.unblocked` webhook event and the customer's notice (when the app has that mail on), in the **same transaction** as the decision, so one never exists without the other. **Reject** needs an answer (up to 1000 characters) and changes nothing else. Deciding twice, or an appeal that was closed, is `plans.customer_appeal.not_open`. An appeal still open when the block is lifted by any other means (the seller's lift, the sweep) becomes `closed` (decided by `system`).
6. **Audit:** `customer_block.appeal_submitted` and `customer_block.appeal_decided` (no new audit table; the statement is not in the entry). **No webhook event** is sent for a submitted or rejected appeal (the seller sees it in the console and through the API); the accept sends the existing `customer.unblocked`. **No mail to the seller when an appeal arrives** (as in plan 14: the mail helper for members is the identity module's, not the customers module's; the console shows it on the customer's sheet, there is no badge or count). **No mail to the customer for the answer to a rejection**; they read it on the portal.
7. **Storage:** `customer_block_appeals`, tenant-scoped with RLS (`tenant_isolation`, forced), pooled migration 00035 and its tenant twin 00024 (`plans_app` select/insert/update, `plans_system` select/delete for the sandbox reset, which deletes the appeals before the customers). It is in the sandbox reset's table list.
8. **Tools:** the tenant API, the four SDKs (Go, TypeScript, Python generated; the PHP files written by hand in the formatter's style because `composer` is not on this machine), `api/openapi/v1.yaml`, the six console locales (`billing.customers.appeal.*` and `errors.plans.customer_appeal.*`) and the six hosted-page languages (`appeal_*`, UNVERIFIED: written by the model, no native speaker).

Tests: plans-svc unit (`customers/command/appeals_test.go`: every refusal that comes before the database), plans-svc integration `CustomerBlockAppeals` (refused when not blocked, empty, too long; 2000 characters of two-byte letters accepted; a second open appeal refused; the appeal carries neither note nor category; reject needs an answer and keeps the block; another customer's appeal is not found; accepting lifts the block with its history row, audit entries and the customer's notice on the outbox, once; deciding twice refused; an appeal open when the seller lifts becomes closed) and the RLS seed of every table (`RLSIsolationEveryTable` writes a row in `customer_block_appeals`); gateway (`hosted_appeal_test.go`: the link and form only for a blocked customer and never the note or category, the statement forwarded for the token's customer and escaped back, every answer of plans-svc as words, the seller's answer escaped, the rate limit, the actor from the key; the render test draws both pages in six languages, the OpenAPI route test); console vitest (locale parity, the error keys) and mock e2e `customer-block-appeal.spec.ts` and the viewer case in `viewer-gating.spec.ts`.
