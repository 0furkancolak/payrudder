**Leftovers (2026-11-02, PR #348, merged):** (1) [the inventory](../runbooks/stateful-components.md) of every stateful component (Postgres, Redpanda, RabbitMQ, Redis, ClickHouse, MinIO, secrets keys, configuration, observability data) with what is backed up, how it comes back, RPO/RTO and what was verified; it found that **the raw usage events (`usage.events.v1`, 400 days) are only in Redpanda, with no copy**: the largest hole, a decision for the owner. (2) [Failover and the game day](../runbooks/failover-game-day.md): a scenario per lost component and a stepwise game day with a results table (there is no automatic data failover; "failover" for Postgres is a restore). (3) The drill now checks **the migrations version** (`migrations-version.sh`: equal / behind / ahead against the highest migration the code ships; `schema.sh` keeps goose's book) and **that the services' roles work on the restored copy** (`testdata/roles.sh`: RLS for the app role, the system role, passwords, grants); `make backup-drill` passed with both (33 s RTO on the laptop). Starting billing-svc and plans-svc themselves on the copy was **not** done: their `/readyz` also pings Kafka (and RabbitMQ), which the drill's stack does not run (a full stack does: step 5 of the game day, open). (4) Helm: `payrudder-infra` renders the alert rules as a `PrometheusRule` and/or a ConfigMap (`monitoring.rules`) and the Alertmanager route as a Secret (`monitoring.alertmanager`); `tests/helm` checks that they are the repository's files, runs promtool (`check rules` and all unit tests) on the **rendered** rules and amtool (`check-config`, routes) on the rendered config; nothing was installed on a cluster. (5) The alert-firing list: `tests/alerts` fails on a rule without a firing promtool test or without a place in the docs; it found five rules with no test (`BackupNeverReported`, `RestoreNotVerified`, `PostgresDown`, `PostgresConnectionsHigh`, `AlertmanagerNotifyFailing`), one whose "firing" test only tested quiet (`RestoreDrillFailed`) and one undocumented (`ServiceDown`); all fixed, and the first responses of the nine oldest alerts added to the runbook table. (6) Backups of the other stores: `object-backup.sh` (`mc mirror` of the buckets, a delete in the source never reaches the copy, `verify`, `restore`; compose service `object-backup`, Helm CronJob, alert `ObjectBackupStale`) and `clickhouse-backup.sh` (native `BACKUP`/`RESTORE` to S3), both tested against throwaway MinIO and ClickHouse (`make test-store-backups`, in the CI `backup` job); Redpanda, RabbitMQ and Redis are documented as not backed up, with the consequence of each. Defaults (not agreed): object copy every 24 h and never deleting; ClickHouse backup has no schedule installed; `ObjectBackupStale` is a warning.

**Broker loss and the rpk export (2026-11-02, branch `feat/deploy-ops-3`):** the failover runbook said the consumers' offsets are lost with the broker; they are not (the aggregator's and the notifier's are in Postgres, limits-svc's in Redis), and a consumer that resumes at an offset of the old log in a new, shorter one silently skips events. `TestAggregator/ALostBrokerNeedsTheConsumerProgressDeletedBeforeTheOutboxIsReplayed` (integration, Redpanda and Postgres containers) recreates a topic empty, replays and shows both the loss and the fix (delete the progress as the database owner: the service role cannot, by design); the runbook is corrected, the `rpk` export/import of a topic is written and was run on a throwaway pair of topics, and the escrowed key is proved with `secrets reseal --dry-run`. The notifier's and limits-svc's steps are untested.

**Still open / NOT verified:** real S3 (only MinIO), a cluster (the Helm chart has the dump jobs and the invariants, no PITR), real receivers (PagerDuty, Slack, SMTP, a heartbeat monitor), a crash instead of a clean stop, a multi-day run (lifecycle expiry, `archive_timeout` driving the shipping), tuning the alert thresholds on real traffic, the other stores (work item 3), the game day (below).

## Done means
A scripted **game day**: destroy a scratch environment, restore from backup to a chosen time, services healthy, RTO measured and written down; each alert has a runbook entry and has been fired once on purpose. (`make backup-drill` does the restore, the invariants, the migrations version, the service roles and the RTO for the databases; each alert has a runbook entry and fires in a unit test, enforced by `tests/alerts`. Not done: the services started on the restored database, a crash instead of a clean stop, an alert fired through to a real receiver: steps 4 to 6 of [the game day](../runbooks/failover-game-day.md#the-game-day).)

## Risks
