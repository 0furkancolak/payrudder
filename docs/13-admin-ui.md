# Operator console

`web/admin` is a small Vue 3 and TypeScript console (Vite, TanStack Router, TanStack Query, vue-i18n) for an operator: it makes the state of the system visible during a demo and
offers the two actions an operator needs most, redriving dead letters and reading a saga. It is served by the Compose `app` profile at
<http://localhost:42301> and talks to **the gateway only**: no database, broker or service port.

| View | What it shows |
|---|---|
| Sign-in | None of its own. An operator is a **person** who signs in on the one sign-in page ([below](#sign-in-methods)) with an address listed in `PAYRUDDER_OPERATOR_EMAILS` and has verified it; the console is then at `/operator`, a door in the side bar that only operators see. |
| Tenants | Every tenant: environment, tier, currency, time zone. |
| Tenant | A header and its tabs. **Overview**: its invoices (kind, period, total, status, saga state) and a lookup for replay and re-rating jobs by id. The other tabs are the billing pages below. |
| Customers | List and create (customer id, name, e-mail, country, billing currency). The **Quotas** row action opens the customer's own limits (overrides of its package's, per meter: limit, window, mode, alerts) with its usage in force. |
| Meters | List (search, category and aggregation filters) and create, or publish the next version of a code: aggregation (sum, count, maximum), quantity property, a free unit, a free category, decimal places (fixed per code) and property filters. |
| Packages | Packages with their latest version's fixed fee and fees in other currencies; publish a version (amounts typed in major units, sent as minor units; a package that exists gets a new version) with **usage prices** (per unit, graduated tiers or per package, each with an included free quantity; unit prices typed in major units) and **quotas** (limit per hour, day, week or billing month; hard, soft or notify only; alert percentages). |
| Subscriptions | List, create (customer, package, currency, trial days, provider or "by the routing rules"), and a panel to pause, resume, cancel at the period end, end now, change package and **move to another payment provider** (a subscription a provider runs is only moved), with the customer's **usage against the package's limits** this period. |
| Payments | The payment ledger across providers, and a **reconciliation** of a period's paid invoices against it. |
| Apps | The apps of the tenant's account, each with its sandbox and live tenant; create an app (name, optional slug, currency, time zone, grace period); per environment **create an API key** (the secret is shown once) and **revoke** keys (the API cannot list keys, so those made in the visit are listed, any key can be revoked by id). Rename and delete need operator routes that do not exist yet. |
| Seller address | The address printed as the seller on every invoice: country first, then the fields that country asks for, the backend's validation, and a **preview** of the seller block as the invoice prints it. |
| Providers | The tenant's provider accounts (credentials are sealed and never shown again), the **routing rules** with a preview, and the subscriptions the providers run. |
| Reports | Revenue by period, provider and country; subscriptions and monthly recurring revenue; unpaid invoices. A row per currency, never one total. |
| Invoice | Lines, a link to the PDF (presigned for five minutes) and the **saga timeline**: every transition with its cause and time, from `saga_events`. |
| Playground | The guided sandbox walk-through described below. |
| Dead letters | The depth of every RabbitMQ `*.dlq`, a peek at one queue's messages, and **Redrive** (with a confirmation) which moves them back with the retry counter reset. |

## Sign-in methods

There are exactly three ways to sign in, all on `/signin` (and the same three on `/signup`), and nothing else: **e-mail and password**, **a one-time code** mailed to the address (passwordless; for an address without an account the code creates one), and **Google** ("Continue with Google", shown only when the deployment has set it up; `GET /auth/methods` tells the page which are on). The design, the threat model and the tests are in phase 42.

**Operators.** `PAYRUDDER_OPERATOR_EMAILS` (a comma list on the gateway; empty by default, so nobody is an operator; the dev stack lists `user1@example.com`, the dev seed's first user) names the people who are platform operators. The gateway decides **on every request**, from the session: the user's address is on the list **and verified**. A client claim is never read (a header, a body field or the browser's own storage opens nothing), the flag is not stored on the user, and a session of anybody else is `403 identity.operator.forbidden`. The page learns the verdict from the sign-in answer and `/auth/me` (`operator: true|false`) and only uses it to show the side-bar door and the console's pages. `PAYRUDDER_OPERATOR_TOKEN` is **no longer a sign-in**: it stays as the machine credential of the API, `payrudderctl`, the demo, the playground's server side and the tests, and no page asks for it or serves it.

**Setting up Google** (real Google was not exercised by the tests, which use the in-repo stand-in; follow these steps once and try it):

1. In the [Google Cloud console](https://console.cloud.google.com/) create or pick a project, then *APIs & Services → OAuth consent screen*: user type External (or Internal for a Workspace), app name, support e-mail, the scopes `openid`, `email` and `profile` (all non-sensitive, so no verification review is needed), and add yourself as a test user while the app is in *Testing*.
2. *APIs & Services → Credentials → Create credentials → OAuth client ID*, application type **Web application**.
3. **Authorized redirect URIs**: the console's public address plus `/gw/auth/google/callback`, exactly, scheme and port included. The console forwards `/gw/*` to the gateway, so the browser, the cookie and the callback all stay on one origin. Locally: `http://localhost:42301/gw/auth/google/callback` (Google accepts `http://localhost` for development). In production: `https://app.example.com/gw/auth/google/callback`. If the gateway is reached at another address, set `PAYRUDDER_GOOGLE_REDIRECT_URL` to that callback URL and register that. *Authorized JavaScript origins* can stay empty: the flow is entirely server side.
4. Copy the **client ID** and **client secret** into `PAYRUDDER_GOOGLE_CLIENT_ID` and `PAYRUDDER_GOOGLE_CLIENT_SECRET` on the gateway (the secret is an environment variable only: never YAML, never logged), set `PAYRUDDER_APP_URL` to the console's public address, restart the gateway. The button appears; `GET /auth/methods` says `"google": true`.

**Trying the flow without Google.** `docker compose -f deploy/compose/compose.yaml --profile oidc up -d mockoidc`, then start the gateway with `PAYRUDDER_GOOGLE_CLIENT_ID=mock-client-id PAYRUDDER_GOOGLE_CLIENT_SECRET=mock-client-secret PAYRUDDER_GOOGLE_ISSUER=http://mockoidc:8099` (for `make dev`, issuer `http://localhost:42899`). "Continue with Google" then opens a page at <http://localhost:42899> where you type any address; it is a stand-in, never to be exposed.

## Playground

`/playground` (an operator page) is a guided walk through the product: create a sandbox account (currency, time zone and grace period are required, nothing is
preselected), create a meter, a plan with a base fee and a per-call price, a customer and a subscription, choose the mock payment outcome, send usage, close the period, and watch the
invoice go through its saga (with a link to the full timeline). It calls the same public API a customer would, with the sandbox tenant's own `qk_test_` key, so it exercises the real system end
to end; it never touches a live tenant. A declined payment leaves the invoice open in `PAYMENT_DECLINED` while dunning retries it. Playwright runs both the paid and the declined path.

## The billing tabs

They show a tenant's data through the tenant API the tenant itself uses, with the operator's session plus `X-Payrudder-Tenant: <tenant id>` ("act as", gateway `authenticate`; the machine token acts the same way): the
same endpoints, rate limits and validation, no operator-only copy. Provider accounts, the ledger, the reconciliation and provider moves are operator routes and go as the operator.
The pages are the features `customers`, `packages`, `subscriptions`, `payments`, `providers`, `reports`, `webhooks`, `apps` and `seller-address`; the tenant layout (`features/tenants`) hosts them as child routes.
Their tests (`e2e-mock/`, `npm run e2e:mock`) run the built console against a **mocked gateway** (every `/gw` request is answered by the test), so they need no stack and run in the console's CI
job; `e2e/` still drives the real stack.

## How it is built

- **Feature-based layout.** `src/features/<feature>` owns everything about one part of the product: its pages (`*.vue`), its TanStack Query hooks (`api.ts`), its route
  declarations (`routes.ts`) and a small public `index.ts`. The features are `auth`, `tenants`, `invoices`, `dead-letters`, `playground`, `customers`, `packages`, `subscriptions`, `payments`, `providers`, `reports`, `webhooks`, `apps` and `seller-address`; `src/app` only composes them (router, query client,
  i18n, layout) and `src/shared` holds what several features need (the API client, the session token, money and label helpers). A feature imports another only through its `index.ts`
  (the tenant page shows `invoices`' table).
- **TanStack Router** (`@tanstack/vue-router`, code-based routes). Every feature exports a function that creates its routes under a parent; the app mounts all but the sign-in page under one
  pathless route whose `beforeLoad` redirects a visitor to the sign-in page and a person who is not an operator to their home (the server decides again on every request). The router is not registered for global type inference: registering it makes pages and the route tree
  depend on each other's types, a cycle TypeScript reports as an implicit `any`, so route paths are plain strings and the Playwright tests are what catches a wrong one.
- **TanStack Query** (`@tanstack/vue-query`) for every read and write. `unwrap()` turns an `openapi-fetch` result into data or an `ApiError` (the gateway's code and message), which is what a query function
  must throw; queries are keyed per tenant and invoice, a refused token or a missing resource is not retried, and the playground's invoice list polls while the saga runs.
- **Languages.** `vue-i18n` with six locales (English, Türkçe, Deutsch, Español, Français and العربية, which switches the page to right-to-left): `src/locales/*.json`. The language is the
  saved choice, else the browser's first supported language, else English; the switcher in the navigation changes `lang`, `dir` and the title, and remembers the choice. Backend enum values
  (invoice status and kind, environment, tier) are translated when the locale has a label and shown as they are when it does not, so a new backend value still appears. Amounts are
  formatted from minor units with the currency's exponent and the locale (`shared/lib/money.ts`; the digits are moved as text, never through a float). A unit test fails if a locale misses a key
  or changes a `{placeholder}`. Technical identifiers (saga states, ids, causes) are not translated.
- **Error keys.** The API sends a stable `error.key` ([error-keys.md](error-keys.md), [ADR 0020](adr/0020-modules-cqrs-errors-config.md)) with an English message. Every page shows an error through one function, `errorText` / `useErrorText()` in `shared/lib/errors.ts`: the message is `errors.<key>` in the locale file (nested, `errors.billing.credit_note.not_paid`) with the first error detail as `{field}` and `{detail}`, and the server's message when the locale has no entry, so a key newer than the console still shows something. A unit test reads `docs/error-keys.md` and the `common.*` defaults of `pkg/errkey` and fails when any of the six languages lacks a key (or keeps one the backend dropped). Adding an error in Go therefore means: regenerate the doc, add the six translations.

- **Typed client.** `npm run gen` generates `src/lib/schema.d.ts` from [`api/openapi/v1.yaml`](../api/openapi/v1.yaml) with `openapi-typescript`;
  the client is `openapi-fetch` over those types, so a route or field that does not exist in the spec does not compile. CI regenerates the file and fails on a
  diff, and the ESLint config forbids `any`. The gateway does not serve the spec: the file in the repository is the source.
- **Same origin.** The browser calls `/gw/...`; in production a Cloudflare Worker (`worker/`, [ADR 0021](adr/0021-console-on-cloudflare-workers.md)) strips `/gw` and forwards the request to `API_ORIGIN` with its cookies and `Authorization` header; Vite's dev server and `vite preview` (the compose `admin-ui` container used by the e2e job) do the same to `GATEWAY_URL`. The gateway needs no CORS configuration.
- **Deploy.** `npm run build` writes `dist/`; `wrangler.jsonc` serves it as Workers static assets (single-page-app fallback, `public/_headers` for the CSP, security headers and the one-year cache of hashed files). `npm run cf:dev` runs it locally, `cf:deploy:staging` / `cf:deploy` publish it; first deploy and secrets: [runbook](runbooks/console-first-deploy.md). Runtime settings (`window.__PAYRUDDER__`, from `/env.js`) come from the Worker's `BRAND_NAME` / `CONSOLE_DEMO` vars.
- **Operator routes added for it** (all behind operator access: the machine token or an operator's session, in the OpenAPI file): `GET /admin/v1/tenants`, `GET /admin/v1/tenants/{tenant_id}/invoices[/{invoice_id}[/pdf|/saga]]`,
  `GET /admin/v1/dead-letters`, `POST /admin/v1/dead-letters/redrive`. The tenant-scoped reads run the billing call in the tenant named in the path; the dead-letter
  and saga operations are `BillingAdminService` RPCs (billing-svc owns the saga log and the RabbitMQ topology).
- **Scope kept small on purpose.** Read-only views plus the redrive. The Kafka dead-letter topics are `payrudderctl dlq --broker kafka`; starting a replay or a re-rating is the
  admin API or `payrudderctl`, the console only looks jobs up. Who may open it is decided by the gateway from the session (see [Sign-in methods](#sign-in-methods)); people use the product app instead.

## UI kit

Styling is Tailwind CSS 4 (`@tailwindcss/vite`, no config file; tokens live in `@theme` in `src/app/styles.css`, dark mode follows `prefers-color-scheme`).
`src/shared/ui/` holds [shadcn-vue](https://www.shadcn-vue.com) components (new-york style, built on reka-ui, `cva`, `tailwind-merge` and `@lucide/vue` icons):
button, input, textarea, label, checkbox, switch, select, dialog, dropdown-menu, tabs, tooltip, table, card, badge, alert, separator, skeleton and sonner (toasts).
They are copied into the repository, not imported from a package, so they are ours to edit. `components.json` points the shadcn-vue CLI at this layout:

```sh
cd web/admin && npx shadcn-vue@latest add popover   # drops the component into src/shared/ui/popover
```

Check what the CLI changed afterwards: it adds dependencies with `^` ranges (pin them) and may guess the `cn` import wrongly (it must be `@/shared/lib/utils`).
The console is one light theme (soft grey canvas, white cards, dark green actions, lime highlights); there is no dark mode. Every page is built from the kit.

`make dev` runs the Go services on your machine (against the infrastructure containers that `make setup` started) and the Vite dev server on port 3001, both with reload; `make dev-docker` runs the services in Docker instead, and `make logs` (or `make logs S=gateway`) follows their logs.

In development the playground account form comes pre-filled: the Vite dev server does it by default, the compose stack through
`PREFILL_PLAYGROUND=true` (served as `/env.js`). Leave it `false` anywhere that is not a throwaway local stack. No credential is ever served to the browser.

## Tests

`web/admin/e2e/smoke.spec.ts` (Playwright, run by CI's end-to-end job against the Compose stack, `make web-e2e` locally) creates a sandbox account, closes a period and waits for
a paid invoice, then drives the browser: open the console as the operator user (a session from the real sign-in routes: the dev seed's `user1@example.com` with its password, else a one-time code read from Mailpit; the dev stack lists that address in `PAYRUDDER_OPERATOR_EMAILS`), open the tenant and the invoice, and check that the saga timeline has at least five transitions ending in
`COMPLETED`; a signed-out visitor is sent to the sign-in page (which has no token form, and the machine token is no password), a person who is not an operator gets 403 from the API and is sent home by the page; a valid notification command put into `notification.send.dlq` appears in the dead-letter view
and disappears when redriven (the notifier delivers it; the saga it names is already final, so its reply is ignored).

`make web-check` runs install, ESLint, the type check (`vue-tsc`), the unit tests (Vitest: locale parity, error-key coverage, address rules and money formatting), the OpenAPI type check and the build.
`web/admin/e2e/i18n.spec.ts` checks that the language follows the browser, can be changed and remembered, that Arabic is right-to-left, and that the signed-in pages and the playground are translated.

## Not covered

The console is not part of the Helm charts (reach it with `kubectl port-forward` of a locally built image, or run `npm run dev`); on Kubernetes the gateway's `/admin` routes are
the same ones and can be blocked from outside the namespace by a NetworkPolicy.

## The product app and the shared look (Phase 38)

The same Vite app now has two audiences. **People** sign up and sign in at `/` and `/signup` and work under `/app` (organisation home, app dashboard with a sandbox/live switch, API keys shown once, settings); their session token (`qs_…`) is kept in `sessionStorage`. **The operator** keeps the token page, now at `/operator`, and everything under `/tenants`, `/playground` and `/dead-letters`. Both share one set of design tokens (`src/app/styles.css`), the dark icon rail and the card, badge, button and input primitives, with light and dark themes. A person reaches a tenant's customers, payment links, credits and webhooks through the same feature pages the operator uses, mounted under `/app/t/{tenant}`. Details, routes and the security stance: phase 38.

Phase 39 adds the pages the mails open and the account flows around them: `/forgot`, `/reset#token=…` and `/verify#token=…` (the token is read from the URL fragment once and removed from the address bar), the "confirm your e-mail address" banner with a resend button on every signed-in page, and a live-key button that explains why it is disabled until the address is confirmed. The settings page now manages the team (invite by e-mail, open invitations with resend and cancel, role changes, remove or leave with a confirmation, rename the account), `/invite#token=…` is the page an invitation opens, and a person with several accounts has an account switcher. See phase 39.

The tab bar of an environment (`/app/t/{tenant}`) now also has Invoices (list with status filter, invoice with lines and PDF), Payments (the folded ledger from `GET /v1/payments`), Packages, Pricing and Reports. They speak the tenant API only; the console's invoice and payments pages (saga, transfers, raw ledger, reconciliation) remain operator pages, and a test fails if a page mounted in the app mentions an `/admin/v1` route. A viewer sees the pages read-only.

## The frame, privacy mode and the pickers (Phase 41)

Every signed-in page (the person's under `/app`, the operator's under `/tenants`) sits in one frame, drawn from one description of the navigation (`src/app/layout/nav.ts`).

- **Sidebar.** Open by default on a wide screen (1024 px and up): icons and labels, grouped in sections. It folds to an icon rail (labels stay for screen readers and as tooltips); the choice is kept in `localStorage` (`payrudder.sidebar.collapsed`), guarded by `try`/`catch` so a browser that blocks storage still gets the open sidebar. Below 1024 px it is a drawer from the start edge (the right in Arabic): a modal dialog, focus moves in, stays in, Escape closes it and focus returns to the menu button.
- **It follows the route** and the scope in the address; see [The app shell and the scope](#the-app-shell-and-the-scope-phase-51) for what it lists. The active item carries `aria-current="page"`; the breadcrumbs (organisation, app, page) come from the same data. A page is in the sidebar only when its route exists (`PERSON_PAGES`), so the navigation never leads to "not found".
- **Header.** Breadcrumbs, a slot for the tour button, the **privacy switch**, the **sandbox / live switch** and the person's menu (which holds the language and the theme); see the app shell below. On a phone the header wraps. A sandbox page has a stripe across the top and a banner under the header; live has neither. An app opens where the person last was; a live environment that is not active shows its go-live checklist instead of zeros ([ADR 0023](adr/0023-live-and-sandbox-guards.md), section 8).
- **Privacy mode** (eye button, or Alt+P). While it is on, every amount is replaced by `••••` (the currency stays) and customer e-mail addresses by `a•••@domain`. It is done in `formatMinor`, the one function every amount goes through, so the figures are not in the page at all (not hidden by a style): they are not in a screenshot, in the print preview or in what a screen reader says. Remembered per browser (`payrudder.privacy`), kept across navigation and reload, and followed by other tabs through the `storage` event. CSV exports are not masked: they are a deliberate download.
- **Pickers.** Currency and time zone are searchable fields (the `Combobox`, below) in every form. Currencies: all 153 the backend accepts, with the name in the page's language, the symbol and a search over all of them. Time zones: every zone the browser knows (`Intl.supportedValuesOf("timeZone")`, about 420) with its offset from UTC now; the search knows the modern spellings engines still list under old names (Kathmandu for Katmandu). Amounts are formatted with `Intl.NumberFormat` and the currency's real number of fraction digits (none for yen, three for dinar). `tests/currencies_test.go` fails when the console's currency list and the backend's differ. Places: `LocationFields` (country → region → district, each searchable and each also taking free text) is in every address form (customer create and edit, seller address, live billing profile), and `CountrySelect` in the tax rate and routing rule rows; the lists are GeoNames' from `GET /app/v1/geo/*`, country names in the page's language, place names without their generic suffix words ("Adıyaman", not "Adıyaman Province"), and the stored address keeps its shape (country code, region and city as text). See [geo-data.md](geo-data.md).
- **Cursors and touch targets.** One rule in the base layer gives every clickable control the pointer (buttons, links, tabs, menu items, options, switches, checkboxes and their labels, selects, `summary`) and every disabled one `not-allowed`; on a phone or a coarse pointer the tapped controls are at least 44 px high.
- **Loading.** Every page is a lazy route, and only English is bundled: the other five languages are fetched when chosen. The first load went from 242 kB to 77 kB gzipped.

A person reaches the same pages as the operator under `/app/t/{tenant}/…`: the console's own pages speak the tenant API with the session as the credential and the tenant as `X-Payrudder-Tenant` (`useTenant` and the apps list read the product API for a person), and the pages whose console version needs operator-only routes (invoices, payments) are the product's own from phase 39. What only the operator may do (the saga, recording a payment by hand, credit notes, reconciliation, moving a subscription between providers, provider accounts, e-invoice accounts) is not offered to a person, and a refused call to `/admin` never ends a person's session. See phase 41.

### The dashboards (Phase 41, part B2)

The dashboard of an app environment (`/app/apps/{app}`), of a tenant for the operator (`/tenants/{id}`) and of the organisation (`/app`, all apps put together) read one gateway endpoint each: `GET /app/v1/apps/{id}/dashboard`, `GET /admin/v1/tenants/{id}/dashboard`; the organisation's page calls the app endpoint for each app (at most twelve) and adds the figures of the same currency.

- **Period and comparison.** 7, 30 or 90 days, the year so far, or a custom range (at most two years), always the tenant's days, compared with the equal period before it (switchable). The choice lives in the address (`?period=&from=&to=&compare=off&cur=`), so a link shares the view.
- **One block per currency, never summed.** A tab per currency (the tenant's own first, then by net revenue); every figure below belongs to the chosen one and is formatted with that currency's own digits (none for yen, three for dinar). The organisation page adds apps only inside one currency.
- **KPIs with their change:** net revenue, MRR (and ARR), ARPU, new customers, churn, failed-payment rate, refunds, open invoices. A change carries an arrow and a sign; the colour only says whether it is good news (churn falling is good).
- **Revenue is net.** Revenue, refunds, tax and expenses come from billing's accounting summary, so the dashboard and the accounting page show the same figure (an invoice counts on the day its payment settled; the old dashboard showed gross). Payments are counted per attempt from the ledger, refunds apart, so a retried decline is visible instead of being hidden in a "count".
- **Charts without a library:** the net-revenue area with the previous period dashed under the same axis, hover and arrow-key tooltip; the payments donut; ranked bars for the top customers (paid most in the period), top packages (MRR) and open invoices by age (0-7, 8-30, 31-60, 61+ days).
- **Usage against limits** (up to ten customers with a subscription, each meter: how many over, how many past 80 %), **upcoming charges** (next 30 days, per currency), **recent activity** (newest invoices, payments and subscriptions) and **health**.
- **States:** skeletons with the shape of the page while loading; the previous answer stays while a new period loads; an error with "Try again"; "nothing yet" with what to do; a section that did not answer is named and the rest stays. Answers are remembered 15 seconds in the gateway (never a degraded one).
- **Backend:** plans-svc `GetCustomerStats` and `GetSubscriptionReport(group_by=plan)`; billing-svc `GetDashboardStats` (top customers, ageing, newest invoices; migration `00024` adds a partial index of open invoices). See phase 41.

## Phase 54: customer payment page, receipts and the invoice inbox

- **Customer sheet.** The payment page is one menu button ("Payment page") in the sheet's actions: copy link, open page (a new tab), regenerate (revokes every link, makes and copies a new one), revoke all. A link is shown nowhere (only a hash is stored); copying or opening makes one valid for 30 days and reuses it while the sheet stays open. Nothing is rendered in the sheet itself; the customer's payments are in its Payments tab.
- **Accounting.** "Add expense" and "Scan receipts" are in the page header with the period. Scanning is bulk and client-side: files (PDF, PNG, JPEG, 8 MB each) are queued and read one by one - pdf.js for a text layer (its worker is a same-origin asset), Tesseract.js OCR (English and Turkish) for photos and scanned PDFs. The OCR worker, its WebAssembly core and the language data are downloaded once from jsdelivr, pinned by the installed package version; the Content-Security-Policy (`public/_headers`) allows that origin for scripts and fetches, and nothing else. Every row of the review table is editable, a field the parser was unsure of is marked, a row can be skipped, and "Save N expenses" uploads each file as an asset (the expense's attachment) and records the expenses.
- **Invoice inbox and rules.** The inbox card shows the address invoices are forwarded to and the number waiting; "Review" fetches them, scans them in the browser and saves what a recurring-vendor rule approves; the rest wait in the same review table (skipping one dismisses it). Rules live in a sheet ("Vendor rules"). The parser is `src/shared/lib/receipt/parse.ts`; add a real document's text to `fixtures.ts` whenever one is misread.

## Onboarding, tours, free credits and trials (Phase 52)

**The first-run wizard** (`features/onboarding`). A person with no app who has never been through it (a new sign-up) gets a screen of its own on `/app` that says why Payrudder exists (meter usage, price it, bill it, get paid) and does the first setup in the same flow: the organisation (its name, and the currency and time zone for the first app), the first app (with its sandbox), the first meter from a template (API calls, storage in GB, seats, AI tokens), the first package with a fixed fee and a price per unit, and a test event: it creates `cus_onboarding` in the sandbox, subscribes it to the package and sends one usage event, reading the answer of the event (the API accepts a request and rejects single events inside it). What it makes is real, made through the same calls the pages use; a step that already ran (the app, the meter) is not run again when the person goes back and forward.

- **Resumable and skippable.** The step and what was made are kept per person in this browser (`payrudder.onboarding.<user id>`, written after every step), so closing the tab and coming back continues where it stopped. "Skip for now" is on every screen. It never opens by itself for somebody who already has an app, a viewer, or somebody who skipped or finished it. `payrudder.noWelcome` = `1` in `localStorage` turns the wizard and the self-starting tour off (support sessions, and the tests that sign fresh people up against the real stack).
- **The "Getting started" card** on the organisation home ticks from the person's data, not from what the wizard remembers: an app, a meter, a published package, the test event, an active sandbox key, an active live environment. Each open item goes to the page where it is done; "Continue setup" reopens the wizard at its step; the card can be hidden and goes away when everything is done.

**The tour engine** (`shared/ui/tour`). A tour is a list of steps (an id, the CSS selector of the element to light up, the i18n keys of its title and body); `pageTour` builds one with the keys `tour.pages.<page>.<step>`. `TourHost` (mounted once, by the frame) dims the page, lights the element of the step and shows a card: arrows move (swapped in right-to-left languages), Escape skips, Tab stays on the card, it is a labelled modal dialog that says "Step n of m", and it passes over an optional step whose element is not on the screen (the sidebar on a phone) or shows a step without an element as a card in the middle. Which tours a person has seen is remembered per person and tour (`payrudder.tour.<user id>.<tour id>`); finishing or skipping marks a tour seen, leaving the page does not. `TourButton` is the icon of a page header: it starts a tour and shows a dot until the person has taken it. The frame shows it for the page the navigation says the person is on (`src/app/tours.ts` maps a navigation key to the tour that lives next to the page, in `features/<page>/tour.ts`), so every page of the sidebar has one; the home's tour (app switcher, sidebar, sandbox switch, user menu) also starts by itself the first time, once the wizard is out of the way. A test fails when a step has no title or body in any of the six languages.

**Free credits.** `GrantCreditsSheet` (credits page and the credits tab of a customer's sheet) grants free credits: how many, why (welcome gift, goodwill, promotion or other, with an optional note; the ledger keeps a stable English phrase), and when they run out (never, in 30, 90 or 365 days, or on a date). It uses the existing grant endpoint (`POST /v1/customers/{id}/credits/grant`), with one idempotency key per attempt.

**Trials.** A package version can carry a default trial (`trial_days`, 0 to 365) that a subscription created without saying otherwise takes: no card is needed, no fixed fee is charged and the first fee is invoiced when the trial ends. The new-subscription form leaves the field empty for "the package's own", takes a number to override it and takes 0 for no trial. A trialing subscription shows when its trial ends in the list and in its sheet, and the subscriptions page reminds of the trials that end within seven days with one click to show them. A **free tier** is a package version with no fixed fee, no usage price and at least one quota: the package form has a "Free tier" box that switches the fee off and asks for a limit. Three days before a trial ends (`PAYRUDDER_TRIAL_REMINDER_DAYS`) the customer is e-mailed and the `subscription.trial_will_end` webhook event is sent, once per trial end; the event is in the webhook endpoint form's list of types.

## Integrations and API keys (Phase 53)

**Integrations** replaced "Payment providers" (`/app/apps/{id}/integrations`, `/app/integrations`; the old `/providers` addresses redirect, keeping `?env=`). The page has three groups, each a row of cards: **Payments** (iyzico, Paddle, bank transfer, and the built-in simulator the sandbox runs on), **E-invoice** (Nilvera, a custom integrator that receives each signed document at an address of the person's own, and the sandbox's simulator) and **E-mail** (Payrudder's own sender, with the switches of which kinds of mail go out, and the tenant's own Nafru Email). A card shows the mark, what the integration is, the live status (not connected, connected and working, a problem, always on, not in use), the sandbox line and a button that opens a side sheet: credentials (password fields, shown once, never read back), a **test** (payments: the provider is asked again; e-invoice: `.../test`; e-mail: a real test mail to an address of the person's choice) and a disconnect. Only the owner connects or changes anything; other members see the state. An environment has one e-invoice integrator, so connecting one replaces the other (the sheet says so). On the organisation screen payment providers can be connected on every app at once; e-invoice and e-mail are set up per app, with a link to each app. Operators keep their own tenant pages (providers with routing rules, e-invoice, mail) under `/tenants/{id}`.

**Marks.** `src/features/integrations/brands.ts` is the one table of who is shown how. A logo is shown only when a licensed or official mark is in `public/brand/providers/` (light and dark files, switched by the theme like the product's own logo) and `public/brand/providers/LICENSES.md` records its source and licence for every file: Paddle (from `simple-icons`, CC0 file, the mark stays Paddle's, nominative use) and Nafru Email (the owner's own product). iyzico and Nilvera have no licensed mark in the repository, so they appear by their plain name; nothing is drawn in a logo's place, and a test pins that list. A generic method (bank transfer, a simulator, a custom integrator) has a general-purpose icon.

**API keys** are made per environment. The keys page is the page of one environment (`?env=`, else where the person last was): the sandbox view lists and makes sandbox keys (`qk_test_`), the live view lists and makes live keys (`qk_live_`), never both from one place, and a link points to the other view. A live key is behind the go-live gate (a confirmed e-mail address, an active live environment), which the page explains. Each key shows its environment, its role and how many of the permissions it holds; "View permissions" lists them. A new key is made in a sheet that names the environment and asks for a **role** (admin, billing, read only, send usage only, custom) and, for a custom key, the **permissions** (read and write per resource, listed by `features/product/apiKeys.ts`, typed from the OpenAPI schema); a fixed role shows its own permissions ticked and fixed. The gateway enforces them: a request that needs a permission the key lacks is `403 gateway.auth.permission_denied`. The secret is shown once, as before. Rotating keeps the role and permissions.

### Shared controls (Phase 50)

One look and a few primitives that every page uses; nothing here is page-specific.

- **Combobox** (`shared/ui/combobox`). The one list with a search box, looking like the region field of an address. One value (`v-model` a string) or several (`multiple`, a `string[]`, chosen values as chips, Backspace and the chip's cross remove, the list stays open); searchable (case and accents ignored, every word must match the label, hint, value or keywords) and shows the first `limit` (10) options until something is typed, with "N more" under them; creatable (`creatable`, or `custom` to accept or refuse the typed text): the text is offered last as "Create “x”" and, in the one-value mode, taken when the field is left. A static list is filtered in the browser (`options`); an API list is `load(query, signal)`: asked when the list opens and after 250 ms of quiet for every change of the text, with a spinner and placeholder rows while it is on its way, only the answer to the last question kept (an older request is aborted through the signal), and a failure shown in the list with "Try again" (`shared/lib/useAsyncOptions.ts`, unit tested with fake timers). Keyboard (arrows, Home, End, Enter, Escape, Backspace) and screen reader (`role=combobox`, `aria-activedescendant`, `aria-multiselectable`, a polite status line with the number of results, the loading and the failure) complete. `SearchSelect`, `CurrencySelect`, `TimezoneSelect`, `CountrySelect`, `LocationFields` and the customer pickers are this component; the short enumerations (statuses, intervals) stay plain selects. `/playground/components` (not in the menu) shows every mode and is what the console tests drive.
- **Filters with several values.** `FilterSelect` takes `multiple`: the model is a `string[]`, the chip shows the first choice and "+N", the list stays open to tick more, an "any" entry (an option with an empty value) and the chip's cross clear it. `useTableState` keeps `filters` as `Record<key, string[]>`; a row passes when it matches any value of a key (the page's predicate still takes one value) and all keys. With `url: true` (or a prefix string, for a key the address already uses such as `env`, or a second table on the page) the filters are written into the address as `?status=open,paid` (a comma inside a value is `%2C`), so a reload, a shared link and "back" bring the same filters. A list the server filters and pages (affiliates) keeps single-value filters.
- **One fill for fields.** The `.field` class in `styles.css` is the fill, border and focus ring of Input, Textarea, NativeSelect, Combobox, FilterSelect and the date trigger (the table's search box is an Input): the tokens `--field`, `--field-border` and `--field-ring`, a white a shade greyer than the cards, defined for light, dark and "system".
- **Date range.** The panel flips and slides to stay on the screen, is never wider than the screen less a margin (375 px phones included: presets above the dates) and scrolls inside itself when short of room. The two dates are the browser's own `<input type="date">`, so a phone shows its wheel and a desktop its calendar; the presets are unchanged.
- **Skeletons** are neutral grey (`bg-foreground/7%`), not blue. **Sheets** clip their children to the rounded corners (the strip of tabs no longer pokes out), and sheets, dialogs, the sidebar, popovers, listboxes and menus use `overscroll-behavior: contain`, so scrolling to the end of one does not move the page behind it.
- **Row actions.** The trigger of a table's actions menu has no chevron; the "view" action's icon is the up-right arrow (`ArrowUpRight`), not an eye (the eye stays for privacy mode and the password field).
- **Failed pages.** `ErrorState` (`shared/ui/error-state`) shows a failure as a state: a title for the kind (not found, no access, signed out, server unreachable, other), the message translated from the API's `error.key`, the request id (`ApiError.requestId`, from the envelope's `request_id`) with a copy button, and "Try again". The main query of a page or card uses it (`<ErrorState :error="q.error.value" @retry="q.refetch()">`); an action's own failure stays an `ErrorText` line. Route level: the router's `defaultErrorComponent` (`app/errors/RouteError.vue`) and `defaultNotFoundComponent` (`NotFound.vue`), and `PageBoundary.vue` around the outlet catches what a page throws while rendering, so the sidebar and header keep working. Strings: `errorState.*` in the six languages.

## The app shell and the scope (Phase 51)

**An app is always selected.** The scope of every list, dashboard and report is **an app or all apps**, and it lives in the address as `?app=<id|all>`. `shared/lib/scope.ts` resolves it: the app of the path (`/app/apps/{app}`, `/app/t/{tenant}`) first, then the address, then the app used last (`localStorage`, `payrudder.app`), then the first app; `null` only while there are no apps. A root search middleware (`retainSearchParams(["app"])`) makes every link keep it, the frame writes it into any scoped address that lacks it (a replace, no history entry), and `/app` without a choice lands in the app used last (`/app?app=all` is the view of every app together: the organisation dashboard).

- **App switcher** at the top of the sidebar (and of the phone drawer; an initial only when the sidebar is folded). The first entry is **All apps**, then the apps, then "New app". Choosing keeps the person on the same page of the other app (`app/layout/scopeNav.ts`): a tenant page goes to the other app's tenant in the same environment, an app's own page (keys, settings...) to the same page of the other app, "All apps" from one of those to the all-apps dashboard.
- **All apps** is `/app/t/all/<page>`: customers, subscriptions, invoices, payments, packages and meters read every app's tenant API in the environment and show one table with the app in the first column (a row leads to the same page in its own app); the pages that only make sense inside one app (reports, credits, pricing, webhooks...) offer the apps. Nothing is summed across apps except by the dashboard, which adds apps only within one currency. The dashboard and the accounting page follow the scope (accounting shows one app's expenses or everybody's).
- **Forms say where they write.** Every create form starts with an **App** field (`app/layout/AppField.vue`, a plain select) preselected with the app the page is about. The rest of a form (customers, packages, currencies) belongs to that app, so choosing another app moves the page to it and keeps the sheet open in the address. "All apps" is never offered; the accounting form's field is data (an expense belongs to an app or to **General accounting**, the whole organisation).
- **Sidebar** (`nav.ts`, `buildNav`), the same for the organisation's pages because an app is selected there too: overview (dashboard, go live); **customers and billing** (customers, subscriptions, invoices, payments, payment links, credits); **usage and products** (usage, meters, packages, pricing and tax, coupons); **money** (accounting, reports, affiliates); **developers** (API keys, webhooks, sandbox tools); **app settings** (app settings, the app's payment providers, e-mail); then the organisation group at the bottom (members, partner portal, organisation payment providers, settings), and **Platform** (the door to the operator console) last, only for operators. It scrolls on its own (`overscroll-behavior: contain`) so a scroll that reaches its end does not carry on into the page.
- **Person's menu** (top right) holds the organisations, settings, sign out and, as sub-menus, the **language** and the **theme** (system, light, dark); they are no longer buttons of the header (the signed-out pages keep theirs).
- **Sandbox / live switch** (`EnvSwitch.vue`) is deliberate: a pill in the header says which environment the pages show and stays on every page of an environment; choosing the other opens a dialog that says that the app itself is not affected, that only that environment's data is shown from now on, and, for the sandbox, that nothing is sent to real payment providers or customers (for live, that it is real). Only its confirm button moves the page, to the same page in the other environment (`envTarget`). The sandbox banner and stripe stay as before.
- **Tour button slot**: an empty `#tour-slot` in the header, where the guided tour (phase 52) mounts its button.
