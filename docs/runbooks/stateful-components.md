# Stateful components: what is backed up, how it comes back, how much can be lost

Plan: [16](../plans/16-backup-alerting.md). One row per thing that holds state, in the order of how much is lost with it. **Objectives (defaults, not agreed): RPO 15 minutes and RTO 1 hour for the Postgres databases; the other rows have the values in their own column, which follow from how each is backed up.** "Verified" says what a script in this repository has actually restored; everything else is a procedure written from the code and the tools' documentation.

## What to read after a restore

1. Is it consistent? `invariants.sh <db>...` (invoice totals vs lines, credit lots vs ledger, receipts vs ledger) and the `counts` line.
2. Is it the right version? `migrations-version.sh <db> <the service's migrations dir>`: `equal` is fine; `behind` is fine (the migration hook brings it up, as after any restore to a time before a deploy; `STRICT=1` fails it); `ahead` means the database knows migrations the code does not, which no migration repairs: deploy the newer image.
3. Do the roles work? `testdata/roles.sh <tenant> <invoices>` is the check the drill makes: the app role sees nothing without a tenant and the tenant's rows with one, the system role sees all, over the network with the roles' passwords. **Starting the services themselves on a restored database was not drilled:** their readiness (`/readyz`) pings Postgres and also Kafka (and RabbitMQ for billing-svc and payments-worker), which the drill's stack does not run; the Postgres half is what `roles.sh` checks. The first step of a game day on a full stack ([failover-game-day](failover-game-day.md)) is to start the services and read `/readyz`.
4. Take a new base backup before relying on the copy ([backup-restore](backup-restore.md#to-a-point-in-time-the-normal-restore), step 5).

## Gaps, in the order they matter

1. **The raw usage events are only in Redpanda.** No copy exists; this is the largest hole in the table. Decision needed (tiered storage, a mirror, or an archive consumer).
2. **No PITR on Kubernetes** (dumps only, RPO 24 h) until the deployment chooses a managed database or pgBackRest/WAL-G.
3. **Backups are not encrypted** by these scripts and the target is whatever the deployment gives them; encryption at rest is the bucket's, the keys are the deployment's.
4. **Nothing was restored from a crash**: every drill stops Postgres cleanly. A game day should `kill -9` the server mid-write once.
5. **No schedule for the ClickHouse backup** is installed; the object copy and the dumps have one.
