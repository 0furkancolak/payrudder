# ADR 0020: Modules with separate commands and queries, error keys, YAML defaults

Status: accepted; applied to new code now and to old code as it is touched.

## Context

Services grew by feature (`grpcapi/changes.go`, `grpcapi/coupons.go`…) with handlers that validate, decide, write and shape the response in one function. Errors are a gRPC code and a sentence. Defaults are scattered over `envDefault` tags.

## Decision

1. **Modules.** A service is a set of modules, one directory per capability (`webhooks`, `coupons`, `creditnotes`, `dunning`). A module has `command/` (changes state, returns an id or an error), `query/` (reads, never writes), its own `store` queries and one file that registers its gRPC handlers. Modules call each other only through their exported command and query functions. No shared "service" or "utils" package.
2. **Handlers are thin.** A handler authenticates (already done by the interceptor), maps the request to a command or query, and maps the result. Rules live in the command.
3. **Error keys.** Every error a client can see has a stable, dotted, lower-case `key` (`billing.credit_note.not_paid`, `plans.subscription.coupon_conflict`) besides the gRPC code and an English message. The key travels as `errdetails.ErrorInfo.reason` through gRPC and as `error.key` in the HTTP body; the console and SDKs translate keys, never messages. Keys are listed in `docs/error-keys.md`, generated from the code, and a test fails if a returned key is not in the list.
4. **Configuration.** Each service embeds `config.default.yaml` with every setting that is public and has a sensible default; environment variables override it; secrets (`*_DSN`, tokens, keys) are never in YAML and are required from the environment. The YAML files are what the docs list as "settings".

5. **Plain SQL only, generated by sqlc.** No query builder, no ORM, no SQL assembled from strings at run time. Every statement is a named query in a `.sql` file of its module and sqlc generates the Go. A filter is part of the statement (`WHERE (sqlc.narg('status')::text IS NULL OR status = sqlc.narg('status'))`), an order is one of a few statements or a `CASE` in `ORDER BY`, never a concatenated column name. A list that needs a total returns it from the same statement: `count(*) OVER() AS _count` on every row, so a page and its total are one round trip and one snapshot. A linter rule (`depguard`) forbids query-builder imports and a test fails on `fmt.Sprintf` used to build SQL.

## Consequences

- All Postgres SQL in the services is now sqlc-generated (plans-svc, billing-svc, payments-worker, assets-svc, notifier, aggregator, ingest-svc, tools/mockpsp, `pkg/outbox`). `tests/sqlguard_test.go` rejects SQL assembled with `fmt.Sprintf` or `+`. Exceptions: analytics-svc ClickHouse queries (sqlc does not support ClickHouse) and DDL in `pkg/testkit/servicedb.go`.

- plans-svc is moved into modules: `customers`, `meters`, `plans`, `subscriptions`, `changes`, `coupons`, `fees`, `providermigrations`, `routing`, `tax`, `reports`, `webhookendpoints` (and `tenants`, `entitlements` for what the others share), each with `command/`, `query/` and one `grpc.go`. `internal/grpcapi` only wires them into `PlansService`; a test fails when a method of the service is served by no module. `internal/store` is the tenant transaction, `internal/convert` stays the mapping package.
- **Subscription report (note, phase 33).** The subscription report is now one fixed sqlc query (`reports.sql`); nothing in it is assembled at run time. Its grouping is chosen by the statement, not by a concatenated column list.
- **Limits of `tests/sqlguard_test.go`.** The test finds SQL built with `fmt.Sprintf` or `+` by reading the Go source of each package, and resolves a query string held in a package-level constant or variable of the same package. It does not follow identifiers from another package, and it does not see function-local variables: SQL put together in a local variable, or passed in from another package, is not checked. Review for those by eye; the rule above still applies to them.
- New code is written in this shape from phase 24; the previous phases' files are moved into modules when a change touches them, to keep each pull request reviewable.
- A rename of an error key is a breaking change and follows the API's deprecation rule.

## Shared packages (phase 49, step 2)

Rules that more than one service applies live once, in `pkg/`, and services do not keep a second implementation.

- **`pkg/period.Valid`/`Parse`** is the definition of a period id (`YYYY-MM`); no service compiles its own pattern.
- **`pkg/usage`** is the rule for a `usage.events.v1` record (`Decode`) and for which meter counts it (`Meter.Matches`/`Value`). The aggregator, limits-svc and analytics-svc all call it. The three copies had diverged, and the stricter rule now holds everywhere: `event_time` is required and valid (limits-svc did not check it, so it could count an event the aggregator dead-letters); the event id is 1 to 64 of `[A-Za-z0-9_-]`, the period is `YYYY-MM`, units are not negative (analytics-svc checked none of these, and only that the id was set). An event invalid by this rule is dead-lettered by the aggregator and analytics-svc and skipped by limits-svc, with reason `INVALID_EVENT` (`DECODE_ERROR` when the bytes are not a UsageEvent). `pkg/usage` has the one table test of the rule.
- **`pkg/cachex`** is the read-through cache of hot-path lookups: bounded LRU, TTL, one load in flight per key, optional negative caching. `pkg/meters` (aggregator, limits-svc) and `pkg/tenantinfo` (aggregator, limits-svc) are built on it, as is ingest-svc's lookup of meters and customers. The two tenant-settings caches that were mutex-plus-map copies had no singleflight and never evicted; they now share one load per tenant and are bounded (10000 entries). A load no longer ends with its first caller's context: it is detached from cancellation and bounded (3 s for meters, 5 s for tenants), because its result is shared by every waiter.
- **`pkg/money` formatting** (`FormatMinor`, `FormatMinorGrouped`, `FormatBig`, `FormatBps`) is the only place an integer amount becomes a decimal string. The e-invoice builder, the gateway's hosted pages, billing's tax line, iyzico's price and `quantity.FormatUnits` all call it. The copies differed at `math.MinInt64` (the gateway's overflowed); the shared one is exact.
- **The successor of a subscription** (plans-svc) is made by one function, `subscriptions/command.SwitchTo`: it ends the old subscription, starts the new one, carries the coupon and publishes both entitlement sets. Plan change inside the subscription module (`replacePlan`), provider cutover and provider sync used to each repeat it. The coupon rule is now one predicate: the coupon follows the subscription, with the periods it has used, whenever the successor is one Payrudder invoices in advance (the only kind `coupons.Redeem` accepts a coupon on); a successor a provider runs or one billed in arrears cannot hold it and leaves it on the ended subscription. The three copies already behaved this way in practice (only a subscription of that kind can have a coupon), so no data changes.
- **UUID request fields.** `errkey.ParseUUID(key, field, raw)` (every service but plans-svc) and `domain.ParseID(field, raw)` (plans-svc, whose errors are field violations) turn a malformed id into InvalidArgument. The five local `parseID`/`parseUUID` helpers, three `invalid` helpers that only served them and about 30 inline `uuid.Parse` blocks are gone; keys and messages are unchanged. Sites with a different message (`app_id is not valid`) or a page token are not this rule and stay.
- **Pagination** (`pkg/page`): `Size` (0 is the default, negative or above the maximum is refused), `Trim` (the extra row a keyset query reads) and the `created_at|id` cursor, used by credit notes, e-invoices, payment links, invoices, expenses, the credit ledger, assets, plans-svc customers, tenants, subscriptions and webhook deliveries. The lists disagreed on an oversize page: customers, subscriptions, deliveries, credit notes, e-invoices and assets refused it, expenses and the credit ledger silently clamped it to 200, and payment links and invoices took a negative size as the default. The stricter rule is now the one rule: refused with InvalidArgument and a `bad_page_size` key (new: `billing.accounting.bad_page_size`, `billing.credits.bad_page_size`, translated in the six console locales). The gateway already refused 1 to 200 on both clamped lists, so no client sees a change. The two internal plans-svc lists billing calls with its configured page size (`ListSubscriptionsFeeDue`, `ListSubscriptionAdjustments`) keep clamping on purpose: a misconfigured batch size must not fail a billing run. The expense (`day.id`) and ledger (`microseconds.id`) tokens keep their own formats.
- **`pkg/testkit`** carries the pieces every integration harness used to copy: `MigratedDB` (database, roles and migrations as the service applies them), `Eventually`, `Logger` (silent unless `ITEST_VERBOSE`), `DockerPause`; its own container starters share `startGeneric` and one set of test credentials. The itests of aggregator, billing, ingest, limits, analytics, notifier, payments-worker, plans and assets use them.
- **Postgres settings** (`pkg/pgxx`): `Settings` (app and system DSN) and `SystemSettings` are embedded in a service config next to `config.Base`, with the variables `PAYRUDDER_PG_APP_DSN`, `PAYRUDDER_PG_SYSTEM_DSN`, `PAYRUDDER_PG_MIGRATOR_DSN`, `PAYRUDDER_MIGRATE_ON_START` unchanged. `CheckMigration` (for `Validate`), `MigrateIfAsked` and `OpenPools` replace the `migrate`, `openPools` and inline migration blocks of seven services. assets-svc was the one that did not check the migrator DSN in `Validate` (it failed after start-up); it does now, as the others always did.
- **Process start-up** (`pkg/app`): `app.Main(name, defaults, start)` loads the configuration, builds the logger, installs the SIGINT/SIGTERM handler, sets up OpenTelemetry and the health registry, calls the service's `start(ctx, cfg, rt)` and flushes telemetry on the way out; on an error it prints `<service>: <error>` and exits 1. `app.NewGroup` runs the workers next to the health endpoint, `Group.ServeGRPC` serves a gRPC server and, on shutdown, marks it NOT_SERVING before `GracefulStop`, and `app.NewGRPCServer` is the server with the tenant interceptors. All eleven `main.go` files use them; what stays in a `main.go` is the wiring that is the service's own. A config struct reaches the shared start-up through `config.Base.Common()`.

## billing-svc modules (phase 49, step 3)

billing-svc has no package of rules outside a module any more. The modules are `accounting`, `billingruns`, `creditnotes`, `credits`, `deadletters`, `dunning`, `einvoices`, `fees`, `hosted`, `invoices`, `payments`, `reports`, `rerating` and `sagas`; `rating` (pure pricing), `rating/inputs` (what rating reads from plans-svc and the aggregator), `tenantevents` (the events a tenant's endpoints receive and the relay that hands them to plans-svc), `workercmd` (queuing a command for a worker), `apierr` (logging and masking an unexpected failure), `replies` (the inbound adapter of worker replies) and `dlq` (the broker adapter of dead letters) are the supporting packages a module may use. `api.New(api.Deps{...})` wires the handlers of the modules into the four gRPC services (a test fails when a method of `BillingService`, `SandboxService`, `BillingAdminService` or `HostedInvoiceService` is served by no module), and `cmd/billing-svc/modules.go` builds their command sides.

- **The saga** is `sagas/model` (the transition table, with the docs diagram test, and the snapshot an invoice freezes) and `sagas/command` (the engine; `Retry`/`Void` for the operator). Modules reach it through its exported commands: `invoices/command.Finalize` starts a saga, `hosted/command` and `payments/command` handle events on it, `credits/command.PurchasePaid` is called from the engine when a credit-pack invoice is paid (a module calling another module's exported command, as above).
- **Billing runs** are `billingruns/command.Manager`: the scheduler (`Tick`: discover due periods, run the chores other modules own, drive the unfinished runs), the watermark, rating and the invoicing stage. The chores are named and registered in `main.go`: fee billing, the credit note refund resend, the expiry of payment links, the promotion reversals and the resume of re-rating jobs.
- **Errors.** `apierr.Internal(ctx, err)` logs the cause and answers a fixed Internal error; `apierr.Wrap` passes a keyed refusal through. A module returns a keyed error or one of these, never a raw database or upstream error. The rules of a package outside a handler return their own sentinel errors (`model.ErrBadPeriod`, `model.ErrNoteNotFound`), and the command that serves the API maps them to keys.
- **A command is a method on a `Commands` value** built from a config (pool, clock, logger, the other modules it needs) where it needs more than a pool. The clock is injected; two places still read the wall clock on purpose (the e-document retry schedule and the credits package), see `docs/code-quality/billing-svc-status.md`.
