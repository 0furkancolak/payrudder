# ADR 0023 — Live is earned, and the environments cannot be confused

- Status: Accepted (phase 45). Builds on [ADR 0011](0011-sandbox-environment.md), which stays true: a sandbox is a tenant, no table has an `environment` column.
- Date: 2026-10-25

## Context

ADR 0011 gives every app a sandbox tenant and a live tenant and keeps them apart with the isolation that already exists between tenants. It is sound, but everything around it was thin: a live tenant could take keys the moment it existed, a half-configured live tenant could be billed, the console could show live zeros next to sandbox data without saying which was which, configuration built in the sandbox had to be typed again for live, and "a sandbox call never reaches a real provider" was one code path.

## Decision

1. **The tenant stays the unit of isolation.** No `environment` column on tenant tables. The new guards sit at the edges.
2. **Fail closed.** A request, command or event whose environment is missing, or disagrees with its tenant's, is refused. `pkg/env` is the one place that parses, compares and requires an environment; there is no default.
3. **Live is earned.** `tenants.status` is `inactive`, `active` or `suspended`. A sandbox tenant is always `active` (a CHECK). A live tenant is created `inactive` and has no API keys and no webhook endpoints, and billing-svc's scheduler does not invoice it, until its go-live checklist is complete and the owner activates it.
   - The checklist is computed on the server: the owner's e-mail is verified; the legal profile is complete (legal name, country, and a tax id where the country needs one: Turkey and the EU); a payment provider is connected in live mode and works; a plan is published; the terms are accepted.
   - Four of the five items are facts in plans-svc's database. The provider item is a fact in payments-worker's database (`GET /admin/tenants/{id}/go-live`: a live-mode account whose sealed settings still open and still build an adapter). The gateway asks payments-worker and passes the answer to plans-svc, which only the gateway can call; the activation request carries no claim about providers. An unreachable payments-worker is a "no".
   - Only an owner activates. Activation recomputes the checklist inside the transaction that decides, on a locked tenant row, so two requests cannot both pass on stale data. A refused activation does not accept the terms.
   - An operator can suspend an active tenant (its keys stop at once: the gateway cache is evicted, and a genuine key of a tenant that is not active is answered `403 gateway.auth.tenant_not_active`, not the `401` of a bad key), reinstate it, or activate an inactive one without the checklist, which needs a written reason and is logged. A suspended tenant is not reactivated by its owner.
   - The database refuses what the code should never write: a trigger rejects a key whose environment disagrees with its tenant's and a live key of a tenant that is not active; another rejects an active webhook endpoint of such a tenant.
4. **Keys carry their environment, and a scope.** `qk_test_` keys belong to sandbox tenants and `qk_live_` keys to live ones; the gateway checks the prefix against the tenant's environment on every request and a disagreement is a hard `401` (there is no mapping that could be talked into it). The environment of a call is the key's tenant's, never a header or query parameter of the caller. A key has a role and permissions (phase 53 replaced the three scopes `full`, `ingest` and `read`, which became the roles `admin`, `ingest_only` and `read_only`): a request that needs a permission the key lacks is `403 gateway.auth.permission_denied`. Sandbox and live keys are made in separate places of the console: the sandbox view makes `qk_test_` keys and only the live view, once the live environment is active, makes `qk_live_` keys; the environment is shown on every key. A key records `last_used_at`, written by plans-svc at most once a minute per key and told by each gateway replica at most once every five minutes per key (bounded memory, off the request path). Rotation issues a replacement of the same role and permissions and sets `expires_at` on the old key (default 24 hours, at most 7 days); the gateway reads `expires_at` from the cached entry, so the old key ends on time without a cache eviction. A key that already ends cannot be rotated again.

5. **A layered environment guard** (`pkg/env`). It is the one place that parses, compares and requires an environment; the string literals "sandbox" and "live" are spelled there and nowhere else. `env.Directory` asks plans-svc for a tenant's environment once and keeps it (an environment never changes: a trigger refuses it), and a worker's check fails closed: no environment, or one that differs, is poison (`workerx.RefuseEnvironment`), a failed lookup is retried.
   - The gateway takes the environment from the key's tenant only.
   - billing-svc stamps each saga command from the invoice snapshot, never defaulting to live, and checks it against the tenant. A CHECK on `invoices` (`invoice_number_series`) ties the number series to the snapshot's environment, and a trigger does the same for credit notes: a sandbox number cannot be on a real invoice whatever wrote the row.
   - payments-worker refuses a command without an environment or against its tenant's, and routes in one place in both directions: a sandbox command is served by the sandbox provider and nothing else; a live command is never served by the mock. `PAYMENTS_LIVE_PROVIDER=mockpsp` needs `PAYMENTS_ALLOW_MOCK_LIVE=true` (or the demo) to start. A provider account has a livemode (iyzico and Paddle tell it from their endpoint): the one that does not match the environment is refused when stored and when used (`payments.account.livemode_mismatch`).
   - invoice-worker refuses a command whose invoice number is of the other series.
   - A sandbox id sent to a live route is "not found", for every resource family (plans-svc and billing-svc each have a test per family, in both directions), and a random walk of the tenant API as the sandbox tenant, with live ids mixed in, leaves a fingerprint of every live row unchanged.

6. **Promoting configuration sandbox → live** (`internal/promote`, `POST /app/v1/apps/{id}/promote`). It copies meters, plans with their prices and entitlements, tax rates, coupons, mail settings and webhook endpoints, and never customers, usage, invoices or payments. It reads each side through the owning module's queries as that side's tenant, decides with pure rules (`promote/query`), and writes only through the modules' commands as the live tenant, so every rule a module has about its objects (validation, quotas, the webhook go-live gate) holds for a promoted object, and RLS keeps each side to its own tenant.
   - **Only adds.** Objects are matched by a stable key (meter code, plan code, tax country, coupon code, webhook URL), so promoting again does nothing. An object that exists in live and differs (a plan whose latest version is not the sandbox's, a tax rate, a coupon's terms, a webhook's event types) is a *conflict*: shown, never overwritten. Mail settings are one object: live takes the sandbox's choice only while it has made none of its own.
   - **Secrets are not copied.** A new webhook endpoint is created with a new signing secret, returned once. An inactive live environment takes no webhook endpoints, so they are *skipped* with the reason; the rest of the configuration goes in, which is how a plan gets published before go-live.
   - **Dry run first.** `dry_run` returns the diff and writes nothing. It also returns a `plan_hash` of the creates, conflicts and skips; sending it back applies exactly that diff, or is refused (`identity.promote.stale`) when the configuration moved since.
   - **Not atomic, but repeatable.** Each module command is its own transaction; a failure is recorded on its change and a second run completes the rest. An applied run writes a row to `config_promotions` (counts and the changes, no secret); a trigger allows only sandbox → live of one app.
   - Owners and admins only; a viewer is refused.

7. **Sandbox lifecycle** (`internal/sandbox`, `POST /app/v1/apps/{id}/sandbox/reset`).
   - A reset is a durable job in plans-svc (`sandbox_resets`, one open job per sandbox, a trigger that allows only a sandbox tenant). A runner (any number of replicas; `FOR UPDATE SKIP LOCKED`, a lease taken over when a replica dies) runs the steps in order: plans-svc's own first (customers, subscriptions and their history, webhook history, coupon counters: with those gone nothing can bill the tenant while the rest is emptied), then ingest-svc, aggregator, analytics-svc, billing-svc and payments-worker. The first failure stops the job and is shown on its step; asking again repeats every step, which is safe because each is idempotent. A step whose service has no address is skipped, not failed.
   - Each service deletes only what it lists in SQL it can be reviewed in (`queries/reset.sql`, the order of the foreign keys), through `SandboxResetService` (`pkg/sandboxreset`: operator only, environment must be SANDBOX, so a live tenant is refused by the service as well as by plans-svc and the database); payments-worker has the same behind its internal token. The configuration stays: meters, plans, prices, tax, coupons, mail settings, webhook endpoints, keys, provider accounts, credit packs, dunning settings. A test per service fails when a table with tenant rows is neither deleted from nor kept on purpose (`sandboxreset.MissingTables`), so a new table cannot be forgotten. The grants for it are narrow: DELETE on the listed tables for the `_system` role, nothing else (the append-only payment ledger included).
   - Numbering starts again (`SBX-…000001`). Events already on the topic can still be read by a consumer after the reset; run it again if one was in flight.
   - Owners and admins; a running reset is returned when asked for again; at most one manual reset per sandbox in `PAYRUDDER_SANDBOX_RESET_COOLDOWN` (5 minutes).
   - **Retention.** A sandbox untouched for `PAYRUDDER_SANDBOX_RETENTION` (default 90 days, 0 = off) — no key used, no customer or subscription made, no reset — is reset by the same job (`kind = retention`), by a sweep each replica runs hourly; the configuration is kept. Work done only through the console on existing data does not count as activity; creating a customer does.
   - **Scenarios.** `GET /v1/sandbox/scenarios` lists the `pm_sandbox_*` payment methods and what each does; `POST /v1/sandbox/invoices/{id}/simulate` sets the invoice's customer to a scenario and runs the invoice's payment again (the scenario stays the customer's payment method; if the payment cannot run again now it says so).

8. **Console** (`web/admin`). The console makes the environment impossible to miss and impossible to change by accident.
   - **Always visible.** Inside an app the header has the app and environment switch; on the organisation home it has the environment switch alone (`OrgEnvSwitch`). The home shows one environment at a time; no page adds live and sandbox together, so there is no cross-environment total to label.
   - **Sandbox is marked.** On every page of a sandbox environment (the home's sandbox view, an app's pages, a sandbox tenant's pages) a stripe across the top of the window and a line under the header say so (`EnvBanner`); live has neither. The line is text, so the colour is never the only signal.
   - **Never silently flips.** The address decides (`?env=`, and `/app/t/<tenant>/...` for tenant pages); `live` is written into the address as well as `sandbox` (`dashSearch`). Without one the console chooses once, from the apps, never from a default that is corrected later: the environment last used in that app (kept per browser, `rememberEnv`), else live when it is active, else sandbox (`defaultEnv`, `defaultOrgEnv`). Until the apps have arrived the shell says nothing and the pages wait.
   - **Live that is not active shows the checklist, not zeros.** An app whose live tenant is `inactive` shows its go-live checklist where the live dashboard would be, and on the home as a card (`AppGoLiveCard`); the organisation totals leave such apps out instead of counting them as zero. The checklist page has the owner's button (terms accepted in the same click) and the promote card: a preview first, then "apply" sends back the hash of the preview.
   - **Sandbox tools** (`SandboxPage`): reset (asks first, follows the job step by step) and the scenario catalogue; an open sandbox invoice has "simulate payment". Keys have a scope, last use, rotation with an overlap, and the live key button waits for an active live environment.
   - **Not yet a person's to do:** the live legal profile and the payment provider are edited on operator pages only; the checklist says so and links to them for an operator. A page where a person can complete them is a follow-up.

## Consequences

- Every place that created a live tenant and then a key for it (the e2e, load, chaos and bench setups, `payrudderctl seed`) now activates the tenant first through `PUT /admin/v1/tenants/{id}/status` with a reason, the way support does. The dev seed (`payrudderctl dev-seed`) never needs it: it works in the sandbox only.
- Tenants that exist when migration `00045` runs keep working: they become `active`.
- billing-svc treats a tenant status it was not sent (plans-svc not yet upgraded) as active, so the two can be rolled out in either order.
- The API key cache (60 seconds) bounds how long a suspension takes if the eviction fails; the eviction itself is immediate.
