# ADR 0026 — Several accounts per integration, named by a key

- Status: Accepted as a default, **not agreed** with the owner (written 2026-11-02 under the owner's instruction of 2026-11-01 to pick the plan's default and say so). Builds on [ADR 0016](0016-provider-capabilities-and-routing.md) (providers, capabilities, routing) and [ADR 0023](0023-live-and-sandbox-guards.md) (live and sandbox).
- Plan: [10 — One integrations page](../plans/10-integrations-page.md). Revisit when plan 22 G7/G8 (a stable `account_id`) is built.

## Context

The owner wants one place where an app lists what it has connected, adds several of the same integration, picks a default, and says which one applies to which country. Payments already worked that way by a naming convention (#242): an account is named by its **key**, the provider's name alone (`paddle`, the primary account, which is what everything stored before labels already is) or the name, a tilde and a label (`paddle~eu`). The registry looks through the label to the provider that builds the adapter; everything else stores and compares the key.

The plan asked whether to keep that or move to a real `account_id` (uuid, label, provider, environment, settings, is_default) with the provider name kept apart.

## Decision

1. **Keep the key.** No `account_id`, no migration of `payment_ledger`, `provider_objects`, `payment_attempts`, subscriptions or invoices. The payment path is where a mistake loses money, and a migration there cannot be rehearsed on a copy from here. The convention is cheap to keep because the primary account's key is the provider's name and so nothing stored before labels changes.
2. **Extend the same key to e-invoice.** `einvoice_accounts.provider` holds the key (`nilvera`, `nilvera~tr`, `webhook~erp`); the primary key is `(tenant_id, environment, provider)`; one account per environment is the default (`is_default`, a partial unique index). Rows that existed are the primary accounts and become the default. A buyer's country can name the account that issues the document (`einvoice_routing`, one rule per country, deleted with the account it names); every other buyer goes to the default. A document records the key it began with (`einvoice_issuances.provider`), and a repeat or a cancel of it goes through that account whatever routing says now: an integrator may already hold the document, and a second one must never issue a second legal document under one UUID. A legal number is unique **within an account** (it was within the only account there was); a seller who runs two accounts keeps their series apart with the integrators, which Payrudder cannot see across.
3. **E-mail has several accounts too (added 2026-11-02, plans-svc migration `00027_mail_accounts` and its tenant twin `00019`).** The same key (`nafru`, `nafru~eu`) in `tenant_mail_integrations.provider`, whose primary key becomes `(tenant_id, provider)`; one account is the default (`is_default`, a partial unique index; the row that was there becomes the default through the column default, because an `UPDATE` in a migration matches nothing under the table's forced row-level security). The first account of a tenant is the default; a default cannot be removed while others exist (409 `plans.mail_integration.default_in_use`). **Routing is by the language of the mail, not by country** (`tenant_mail_routing`: one rule per language of the six, an account, deleted with the account it names): the notifier has no country of the recipient on a mail, but every mail carries `locale` (the customer's, else the app's default, else English), and a mail in a language with no rule goes through the default. The notifier asks `ResolveMailSender(language)` and remembers the answer per tenant and language; plans-svc answers with the account's own key and sender. Sealing keeps the old AAD for the primary account (`mail-integration:<tenant>`) and adds the key for a labelled one (`...:<tenant>:nafru~eu`), in the reseal job too. **DEFAULT (not agreed):** language and not country, and only the one provider (Nafru) as the provider of an account; a second provider type waits for plan 11's contract.
4. **One audit trail.** `provider_account_events` (payments-worker) gains a `kind` (`payment` or `einvoice`) and the actions `default_set` and `routing_changed`, and is read through `GET /app/v1/apps/{id}/integrations/audit`. It is the pattern of `go_live_audit` until plan 22's `audit_events` exists, and moves there then. No setting is ever written to it. The e-mail accounts' changes are plans-svc's and go to **`audit_events`** (`mail_integration.saved`, `.removed`, `.default_set`, `.routing_changed`, never a key nor its hint), which the account's audit log page lists with labels; **they are not in the integrations page's own audit card** (two stores with two cursors: merging them is the work of moving that card to `audit_events`).
5. **The console shows accounts, not provider cards.** The cards stay as the place a provider is first connected and explained; the list below them holds every account of every kind with its default and status, and the rules, the "who takes this customer" tester and the audit sit under it.

## The key as a name: who reads `provider`

This is the trace the plan asked for (2026-11-02, from the code). *Key* means the value is stored or compared as written (`paddle~eu`); *base* means it is looked through to the provider (`paddle`).

| Reader | Key or base | Finding |
|---|---|---|
| `pkg/payments` registry, capabilities, parsers (`Build`, `ParseWebhook`) | base | Looks through the label (`accountkey.go`). |
| `pkg/payments/providers.Lookup` (what a provider can charge) | base | Used by routing validation and subscription creation. |
| payments-worker `provider_accounts`, `provider_account_events`, the resolver cache | key | The primary key of an account. |
| payments-worker `payment_attempts`, `payment_ledger`, `provider_objects`, `provider_subscriptions` | key | Written as the key; the ledger's "one fact once" index includes it. A report grouped by provider shows `paddle~eu` apart from `paddle`. |
| payments-worker webhooks `/webhooks/{provider}/{tenant}/{environment}` | key | Only exercised through the parser lookup (base). A real notification to a labelled account's URL has not been run. |
| iyzico webhooks without a tenant in the URL (`/webhooks/{provider}`) | key, **gap** | The tenant is found from the charge's idempotency key, but which of several iyzico accounts holds the secret that signs it is not known: iyzico with several accounts cannot be told apart. |
| bank transfer | base, **single** | Refused as a further account (`payments.account.single_only`): its details are printed on invoices. |
| plans-svc `routing_rules.provider` | key | **Defect found and fixed here:** the column refused the tilde (`CHECK ... ^[a-z][a-z0-9_-]{0,31}$`), so a rule naming a labelled account could not be saved (an internal error). |
| plans-svc `subscriptions.provider`, `provider_migrations.to_provider`, `domain.ValidProviderName` | key | Same defect, same fix (migration `00010_labelled_accounts`): a subscription could not be sold through a labelled account. |
| plans-svc subscription reports (`group_by=provider`) | key | `paddle` and `paddle~eu` are two rows. Deliberate for now: they are two accounts. |
| billing-svc invoices and payment links (`provider` columns, no check) | key | Stored as written. Hosted pages and payment links offer methods through payments-worker's `invoice-methods`, which asks the account list; a labelled account's methods have **not** been run end to end. |
| gateway `go-live/providers`, `go-live/routing`, `integrations/e-invoice*` | key | The account list, the default and the routing speak keys. |
| console (payments list, filters, the account list) | key | Groups by the key; the page shows provider and label separately. |
| SDK enums | key | The routing `provider` is a pattern (`provider(~label)?`), not an enum of two. |

## Consequences

- Nothing on the payment hot path moved. What is left of the real-`account_id` question is listed above (the iyzico webhook, reports by provider, a webhook to a labelled URL); plan 22 G7/G8 needs the stable id and is the moment to pay for it, with a rehearsal on a copy.
- An e-invoice account is not renamed: its key is its identity (to rename, connect the new label, move the default and routing, remove the old).
- The default cannot be removed while others exist (409 `einvoice.account.default_in_use`): the page asks for another default first, so a live document never finds "accounts, but none is the default".
- Not built: organisation-level accounts that several apps use (the page's organisation screen still connects a payment provider on every app one at a time, as before; the migration it needs is written down below), copying an e-invoice account between apps, health checks of e-invoice and e-mail accounts that run by themselves (a row says what its last test said).

## Organisation-level accounts: why not on the key, and the migration it needs (written 2026-11-02, nothing built)

The plan's "bind one to an app" means **one account used by several apps**, set up once at the organisation. The key convention cannot carry it, and neither can a copy of the e-mail change to the other kinds:

- Every credential row belongs to one tenant: `provider_accounts` and `einvoice_accounts` are keyed `(tenant_id, environment, provider)` and sealed with that in the AAD, `tenant_mail_integrations` with `mail-integration:<tenant>`; row-level security keys on `tenant_id`; the webhook URL carries the tenant (`/webhooks/{provider}/{tenant}/{environment}`) and so does what the worker reads; the ledger, `provider_objects` and subscriptions store the key as a name. A shared account needs a row that no tenant owns, tenants that point at it, credentials sealed to something other than a tenant, a webhook that names the account (iyzico's names neither tenant nor account: ADR above), and a ledger that groups by account across apps. That is the stable `account_id` of plan 22 G7/G8, and doing the organisation part first would be done twice.
- It is one mechanism for three kinds, held by three services (payments-worker for payments and e-invoice, plans-svc for mail; neither knows the other's database), so a single table cannot hold it. An organisation-level mail account alone **could** be built in plans-svc (it owns accounts and mail), but it would leave payments and e-invoice on the old way and be replaced by the general mechanism; it is not built for that reason, not because the data model forbids it.

**The migration (steps, each shippable on its own; the payment-path steps need a rehearsal on a copy of real data and a rollback before they run):**

1. **Add the new shape beside the old.** In each service, `integration_accounts (id uuid, owner_kind 'tenant'|'organisation', owner_id, kind, provider, label, settings_enc, key_hint, ...)` and `integration_bindings (tenant_id, environment, kind, account_id, is_default)`; routing tables (`einvoice_routing`, plans-svc `routing_rules`, `tenant_mail_routing`) gain a nullable `account_id`. Nothing reads them yet.
2. **Backfill, owner = the tenant.** Every existing row becomes an account owned by its tenant plus a binding with the same label and default flag, nothing becomes shared. The sealed box is **re-sealed under the new AAD** by the reseal job (`pkg/secretbox/reseal`, one more place per table), never copied as bytes: the old AAD names the tenant and would not open.
3. **Dual read.** The resolvers (payments-worker's account resolver and its cache, the notifier's `PlansProviders`) read through the binding and fall back to the old row; writes go to both. The webhook route gains `/webhooks/a/{account_id}` beside the old one; a notification arriving on the old URL is still accepted.
4. **Ledger and objects get the id.** `payment_ledger`, `provider_objects`, `payment_attempts`, `provider_subscriptions`, `reconciliation_discrepancies`, `settlement_lines`, `fee_rules` and `provider_account_health` gain `account_id`, written with the key from now on and **backfilled in batches** from `(tenant, environment, provider)` (the slow step: measure it on the copy; the ledger's "one fact once" index keeps the key until the id is NOT NULL). Reports group by account id and show the label.
5. **Cut over, then drop.** Routing and subscriptions reference the account id; the key columns stay one release as the rollback path (a code rollback reads keys again); the old rows are deleted after a clean reconciliation run.
6. **Only then** `owner_kind = 'organisation'`: the console's organisation screen creates an account once and **binds** it to apps (the "connect on every app" loop goes), a tenant's page shows "inherited from the organisation", and removing a shared account asks which apps use it. Credentials of a shared account are sealed to the account id, so an app never holds them.

Rollback: steps 1 to 3 are additive and reversible by dropping the new tables; step 4's columns are nullable until step 5; step 5 keeps the key columns. A data loss window exists only if the old rows are deleted before reconciliation is clean, which is why that is its own step.

**Defaults (not agreed):** per app-environment stays the scope (today); organisation-level accounts wait for the `account_id` work (plan 22 G7/G8) and are built as its last step.
