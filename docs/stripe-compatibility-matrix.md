## 0. The flagged question - answer

**Confirmed (from docs), not just plausible.**

1. Create PaymentIntent, `payment_method` param (https://docs.stripe.com/api/payment_intents/create): "If the payment method is attached to a Customer, you must also provide the ID of that Customer as the customer parameter of this PaymentIntent." and `customer`: "Payment methods attached to other Customers cannot be used with this PaymentIntent."
2. Save-and-reuse guide, "Charge the payment method later" (https://docs.stripe.com/payments/save-and-reuse.md?payment-ui=embedded-components): off-session charge = PaymentIntent with `customer`=Customer ID, `payment_method`=PM id, `off_session=true`, `confirm=true`. Same in https://docs.stripe.com/payments/save-during-payment.md?payment-ui=elements ("use the ID of the Customer ... and the PaymentMethod ID").
3. The same guide: "To set up a payment method for future payments, you must attach it to an object that represents your customer."
4. PaymentMethod object: `customer` "will not be set when the PaymentMethod has not been saved to a Customer" (https://docs.stripe.com/api/payment_methods/object). Whether an unattached pm_ is hard-limited to one use: **UNCLEAR** - no fetched page states it in a sentence (the `setup_future_usage` text says without a Customer "you can still attach the payment method to a Customer after the transaction completes", implying attach is the way to make it reusable).

**Minimum correct flow to charge a stored method later, customer absent** (all from the pages above):
1. `POST /v1/customers` (email/name/metadata) -> `cus_...`; store it per end-customer.
2. Collect + authenticate the method ONCE with the customer present, saving it to that Customer, by either:
   - (a) Checkout Session `mode=setup`, `customer=cus_...`, `currency` (required in setup mode unless allowed_payment_method_types set), `success_url` (hosted page); "Stripe automatically attaches the resulting payment method to that Customer" (save-and-reuse, Checkout variant). Or SetupIntent `customer=cus_...`, `usage=off_session` (default), confirmed client-side (Elements) - https://docs.stripe.com/api/setup_intents/create.
   - (b) Checkout Session `mode=payment` for the first invoice with `customer=cus_...` (or `customer_creation=always`) plus `payment_intent_data.setup_future_usage=off_session` (create-session page, `customer` and `customer_creation` text; PaymentIntent doc `setup_future_usage`).
3. Get the `pm_...`: from `checkout.session.completed` -> `setup_intent` (mode=setup) -> `GET /v1/setup_intents/{id}` -> `payment_method`; for mode=payment, from the PaymentIntent's `payment_method`; or list `GET /v1/customers/{id}/payment_methods`. If no customer was passed to Checkout, attach manually with `POST /v1/payment_methods/{id}/attach customer=...` (save-and-reuse, "Attach the payment method").
4. Later: `POST /v1/payment_intents` with `customer`, `payment_method`, `off_session=true`, `confirm=true`, amount, currency + Idempotency-Key.
5. Handle failure: "If a payment attempt fails, the request also fails with a 402 HTTP status code, and the PaymentIntent status is requires_payment_method ... Notify your customer to return to your application ... direct your customer to a new Checkout Session" (same guide). `authentication_required` error: "If your customer is off session, notify your customer to return to your application and complete the payment" (https://docs.stripe.com/error-codes).
6. SCA: authenticate on-session once, then off-session payments may use exemptions as merchant-initiated transactions; "Exemptions aren't guaranteed" (https://docs.stripe.com/strong-customer-authentication). Needs a stored mandate/consent from the customer (compliance sections of the save guides).

**What the adapter lacks (and the product lacks):**
- `Charge` (L261-293) sends `payment_method` + `confirm` + `off_session` and NO `customer` (L272-278). Docs: a pm attached to a Customer requires `customer`; an unattached pm is not a documented reusable instrument. => Charge cannot be correct for any pm that was saved the documented way.
- No `/v1/customers` call anywhere; no `/v1/setup_intents`; no Checkout `mode=setup`; no `setup_future_usage`; no `customer`/`customer_creation` on the Checkout Session (L360-373 sends `customer_email` only, so mode=payment with default `customer_creation=if_required` creates no Customer and saves nothing).
- `checkout.session.completed` handler (L483-503) reads payment_intent/payment_status/amount/currency/metadata only; it never captures `customer`, `setup_intent`, `payment_method`. For a setup-mode session there would be no `payment_intent` at all.
- Product side: `customers.payment_method` is an opaque tenant-supplied string set through `PUT .../payment-method` (`services/gateway/internal/httpapi/customers.go:36 setPaymentMethod`, on feat/stripe-adapter). Nothing in Payrudder creates or learns a reusable pm_ or a cus_ for Stripe. `Charge` additionally has nowhere to receive a customer id (payments.ChargeRequest has only PaymentMethod, `pkg/payments/payments.go:19-28`).
- Hence today the only working path is a tenant who creates the Customer + pm_ in their own Stripe account and passes only the pm_; that pm_ then fails the "customer required" rule. The `Charge` path is effectively unusable except via a pm_ that was never attached (UNCLEAR whether Stripe accepts it).

## 2. Event/object details the adapter depends on

- `checkout.session.completed` with `payment_status`: `paid` handled; docs list the async events for delayed methods (verified exist). Session object field list for `payment_status` values was not fetched (https://docs.stripe.com/api/checkout/sessions/object not fetched) -> `paid`/`unpaid`/`no_payment_required` semantics UNVERIFIED. `no_payment_required` (setup mode / 0 total) is unhandled in the adapter.
- Duplicates/ordering: https://docs.stripe.com/webhooks - events can be duplicated and are not ordered; "Track event IDs"; "In some cases, two separate Event objects are generated" (dedupe by `data.object.id` + `type`). Adapter returns `Ref.EventID` (good) but also emits both `payment_intent.succeeded` and `checkout.session.completed` for one checkout payment (two notifications for one charge, both carrying `payrudder_key`) - caller must dedupe on key; not verified here.
- Retries: live mode up to 3 days with exponential backoff; sandbox 3 retries over a few hours; manual resend 15 days (Dashboard) / 30 days (CLI); redirects (3xx) count as failures; must return 2xx quickly.
- Snapshot vs thin: https://docs.stripe.com/webhooks "Choose the payload format: Thin (recommended) or Snapshot". The adapter parses snapshot events (`data.object`). The operator must create the destination as **snapshot**, and choose the API version for it. Adapter docs/UI do not say so.
- Event destinations are created through Workbench / `/v2/core/event_destinations` (the old `/v1/webhook_endpoints` still referenced by the docs as `api/webhook_endpoints/create`; deprecation status of the v1 endpoint: UNCLEAR).

## 5. Findings needing code changes (ordered)

1. **Charge lacks `customer`** (L272-278) and the product has no field to carry it. Add a Stripe customer id (`cus_...`) with the payment method, e.g. store `cus_xxx|pm_xxx` or add a field to ChargeRequest, and send `customer=` on the PaymentIntent. Without it, saved/attached methods are rejected.
2. **No flow creates a reusable pm_/customer.** Add: create Customer; Checkout `mode=setup` (or `mode=payment` with `customer`/`customer_creation=always` + `payment_intent_data[setup_future_usage]=off_session`); handle `checkout.session.completed` for setup mode (read `customer`, `setup_intent`; retrieve SetupIntent for `payment_method`; attach if no customer); persist cus+pm to `customers.payment_method`; implement `PaymentMethodLink` for Stripe via a new setup Checkout Session. Store consent/mandate text (compliance sections).
3. **Pin `Stripe-Version`** on every request (e.g. `2026-09-30.endive`) and document that the webhook destination must be a **snapshot** destination created with the same version; payload shape depends on destination version, not on the request header.
4. **Refund ignores `status`**: read `status`/`failure_reason`/`pending_reason`; treat `pending`/`requires_action` as pending, `failed`/`canceled` as failure, rely on `refund.updated`/`refund.failed` for final state.
5. **Status via Search is eventually consistent** (up to 1 min normally, up to 1 h in outages): `not_found` must not be taken as "never charged". Prefer retrieving by stored PI id or retrying the original POST with the same Idempotency-Key inside the 24 h window; after 24 h do not blindly re-POST (key may be pruned -> second charge).
6. **409 / 424 / Stripe-Should-Retry** mapping: 409 `idempotency_key_in_use` -> transient (wait, same key + same params); honour `Stripe-Should-Retry`; cached 500 on a key returns the same 500 until pruned.
7. **Failure classification for off-session**: map `authentication_required` / `authentication_not_handled` / `payment_intent_authentication_failure` to "customer must come back on-session" (send the payment-method-update link), not to ordinary dunning retries; classify hard declines (`stolen_card`, `lost_card`, `pickup_card`, `expired_card`, `fraudulent`...) as no-retry (docs "Next steps" column).
8. Handle `payment_intent.requires_action`, `checkout.session.completed` with `payment_status=no_payment_required`, `setup_intent.succeeded`, `checkout.session.expired`, and disputes (`charge.dispute.created`) or document them as ignored.
9. Currency edge cases: verify the three-decimal "last digit 0" rule against https://docs.stripe.com/currencies (not visible in fetch) and add ISK/UGX "must end in 00" if those currencies can be offered.
10. Cross-check key mode with `GET /v1/balance` `livemode` (response field documented) in `CheckHealth`, instead of relying on key prefix only.
11. Add client-side throttling/backoff awareness for 429 (`Stripe-Rate-Limited-Reason`); keep Search under 20 req/s.
12. Metadata value length for `payrudder_key` (key can be up to 255 chars as an Idempotency-Key): verify Stripe metadata limits before relying on it as the join key.
